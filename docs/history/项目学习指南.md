## 第 0 章：30 秒电梯陈述（先背熟这段）

> 「这是一个**企业级 RAG 知识问答系统**，用 LangGraph 编排工作流，FastAPI 提供接口。
>
> 它不是一个单链路的 RetrievalQA，而是**五层 RAG 架构**：
> L1 数据准备做清洗去重，L2 索引做自适应切片和向量化，L3 检索用**向量 + BM25 双路召回、RRF 融合**，
> L4 生成做**引用溯源、置信度评估和优雅拒答**，L5 评估用命中率、MRR、忠实度闭环回流。
>
> 工作流是 8 节点的 LangGraph 有向图，会先做**意图路由**分流：知识问答走检索、业务查询走工具调用、

> 另外有三个工程上的设计：一是**三级自动降级**，没有 API Key 也能完整跑通；
> 二是**模型抽象层 providers/**，切换模型只改 `.env`，业务代码零改动；
> 三是**可观测性**，自建 span 树 + TTFT 埋点，每次请求的耗时结构都能落到 `logs/trace.jsonl`。」

## 第 1 章：整体架构（必考第一题）

### 1.1 数据流全景

```
                          ┌─────────────── 离线：建索引 ───────────────┐
  data/*.txt|.md|.pdf ──▶ │ L1 准备(清洗/去重) → L2 切片 → 向量化 → 写入 │
                          └───────────────────────────────────────────┘
                                            │
                                     ┌──────▼───────┐
                                     │  向量库(内存/Chroma) │
                                     │  + BM25 倒排索引     │
                                     └──────┬───────┘
                                            │
  用户提问 ──▶ 意图路由 ──▶ 分支 ──▶ 检索/工具 ──▶ 动态路由 ──▶ 生成 ──▶ 答案+引用
                (规则优先)      │                  (Flash/Pro)      │
                               └─▶ 寒暄直出(模板)                   └─▶ L5 评估闭环
```

### 1.2 五层 RAG 架构（这是本项目的骨架，也是最大卖点）

| 层 | 职责 | 入口文件 | 一句话设计理由 |
|---|---|---|---|
| **L1 准备** | 加载→归一化→清洗→去重→元数据 | `📍 app/rag/prepare.py` | 检索质量上限由语料质量决定，噪声必须在源头治理 |
| **L2 索引** | 自适应切片→短片段治理→向量化→幂等写入 | `📍 app/rag/indexer.py` | 机械切片产生「只有标题没正文」的碎片，向量化后是纯噪声 |
| **L3 检索** | 多路召回→RRF 融合→阈值→软回退 | `📍 app/rag/retriever.py` | 单路向量检索在专有名词上必然失效 |
| **L4 生成** | 上下文组装→受控生成→引用→置信度→拒答 | `📍 app/rag/generator.py` | 「不知道」远好过「一本正经地编」 |
| **L5 评估** | 命中率/MRR/忠实度/引用覆盖率 | `📍 app/rag/evaluator.py` | 没有评估的 RAG 只能靠「我问了两句感觉还行」 |

**为什么单独分五层而不是一把梭**：
每一层的失败模式不同，分层后能单独定位、单独优化、单独评测。
比如检索不准，你能确定是切分切碎了（L2）还是召回路没覆盖（L3），而不是对着一个黑盒瞎猜。

### 1.3 LangGraph 8 节点工作流 `📍 app/graph/workflow_graph.py`

```
memory_load 记忆加载
     ↓
intent_recognize 意图路由 ──┬─→ knowledge_retrieve 知识检索 ─┐
                           ├─→ tool_invoke 工具调用 ────────┼─→ model_route 动态路由
                           ├─→ smalltalk_reply 寒暄直出 ────┤        ↓
                           └─→ (unknown) ──────────────────┘   generate_answer 生成
                                                                     ↓
                                                              ┌──异常?──┐
                                                              ↓         ↓
                                                        human_fallback  END
```

**8 个节点** `📍 app/graph/nodes.py`：

| 节点 | 职责 | 设计要点 |
|---|---|---|
| `memory_load` | 加载长期记忆 | 独立成节点，可在前端看耗时，也便于单独降级 |
| `intent_recognize` | 意图路由 | 规则优先 + LLM 兜底，规则拦截约 80% 输入 |
| `knowledge_retrieve` | RAG 检索（L3） | 检索失败不转人工，交给 L4 诚实回答 |
| `tool_invoke` | 业务工具 | 工单查询 / 员工信息 / 制度精确查询 |
| `smalltalk_reply` | 寒暄直出 | **模板回复，不检索不调模型** |
| `model_route` | 动态路由 | 按复杂度选 Flash / Pro |
| `generate_answer` | 受控生成（L4） | 引用 + 置信度 + 拒答 |
| `human_fallback` | 异常兜底 | 转人工话术 |

**两个关键拓扑决策**（面试常追问）：

1. **`model_route` 为什么放在检索之后、生成之前？**
   它要用「检索难度」作为决策信号（证据越弱越该升档），必须等证据到手才能判断；
   放在生成之前则保证档位在调用模型前就已确定。

2. **`smalltalk_reply` 为什么单独成支？**
   借鉴 Rasa 的 RulePolicy 和 FastGPT 的「指定回复」节点。
   寒暄不该走检索（只会命中垃圾片段），也不该走 L4 生成
   （无检索文档会触发"知识库中没有找到…"的拒答文案——用户说"你好"被回一句"知识库没找到"是灾难级体验）。

## 第 2 章：逐模块深挖

### 2.1 L1 数据准备 `📍 app/rag/prepare.py`

**流水线**：加载 → 归一化 → 清洗 → 质量校验 → 近重复去重 → 元数据注入

**做了什么**：

```python
# 归一化顺序很重要（这行能体现你真的读过代码）
text = unicodedata.normalize("NFKC", text)   # 必须先做全角转半角
text = _CONTROL_CHARS.sub("", text)          # 去控制字符
text = _PAGE_NOISE.sub("", text)             # 去"第 3 页 / 共 10 页"、纯分隔线
text = _MULTI_SPACES.sub(" ", text)          # 压空格
text = _MULTI_BLANK_LINES.sub("\n\n", text)  # 压空行
```

> **追问点**：为什么 NFKC 必须放在最前面？
> 因为全角空格（U+3000）会逃过后续的空白压缩规则，导致指纹把「同样内容、不同输入法」判成两篇文档。

**两级去重**：
1. **精确去重**：归一化文本的 sha1 指纹 `content_fingerprint()`
2. **近重复去重**：字符级 Jaccard 相似度 ≥ 0.95

> **追问点**：为什么近重复用 Jaccard 而不是向量相似度？
> 数据准备阶段还没有 embedding；且 Jaccard 对排版差异（空格/换行）不敏感，
> 能稳定识别「同一段话的两种排版」这类真实重复。
> （诚实补充：O(n²) 复杂度，语料到万级需要换 MinHash/SimHash 分桶——代码注释里已写明。）

**元数据注入**：`file_type / file_name / char_count / fingerprint`
这些字段会被 L2 切片继承，最终成为 L4 引用溯源和 L5 评估归因的数据基础。

### 2.2 L2 索引构建 · 切分策略 ⭐⭐⭐（面试高频）

`📍 app/rag/indexer.py`

```python
RecursiveCharacterTextSplitter(
    chunk_size=300,        # 每片约 300 字符
    chunk_overlap=60,      # 相邻片重叠 60 字符
    separators=["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""],
    length_function=len,
)
```

**必答三连**：

| 问题 | 答案 |
|---|---|
| **chunk_size 为什么 300？** | 面向企业制度类文档调优。300 字符约等于一个完整的条款段落——足够承载一个独立语义单元，又不会把多个不相关条款揉进同一片。太大会稀释向量语义（一片讲年假又讲报销，跟哪个 query 都不够像），太小会丢失上下文（"需提前 3 天申请"脱离主语就没意义）。 |
| **chunk_overlap 为什么 60？** | 20% 的重叠率。目的是防止关键句被从中间切开。60 字符对中文约等于 2 个短句，足以兜住一个被边界切断的句子。 |
| **separators 为什么这样设？** | 默认英文分隔符列表以空格和句号为主，**对中文不友好**——中文没有空格分词，会在任意位置断开。这里显式加入中文句末标点 `。！？；，`，让切分优先在语义边界发生。 |

**本项目的独门设计：短片段合并** `indexer.py:50`

> 机械切片会产生「3. 考勤」这类**只有标题没有正文**的碎片，
> 它们向量化后是纯噪声——既答不了问题，又会挤占 Top-K 名额。

```python
MIN_CHUNK_CHARS = 40               # 短于 40 字符视为碎片
MERGE_SOFT_LIMIT_RATIO = 1.3       # 合并软上限 = 300 * 1.3 = 390 字符
```
合并逻辑：过短片段向前合并，只要不超软上限；首片段过短则暂存等下一个「收养」；
全程只有一个过短片段则兜底保留（宁可留一个短片段，也不要丢内容）。

> **这是极好的面试素材**：这是你实测发现的问题，不是抄来的。

**chunk_id 为什么用内容哈希而不是位置序号** `indexer.py:107`

```python
digest = hashlib.sha1(content.encode("utf-8")).hexdigest()[:16]
return str(uuid.uuid5(uuid.NAMESPACE_URL, f"{source}::{digest}"))
```

> 位置型 ID（`uuid5(source::chunk_index)`）是「伪增量」：
> 同一文档前插一段后，后续所有 chunk 序号偏移，ID 全变，
> 导致重复入库时本应不变的片段被误删重写，破坏向量库的增量语义。
> 内容哈希让「内容未变的 chunk」ID 稳定，只有真正变化的片段才更新。

**幂等写入**：`add_document()` 先 `delete_by_source(文件名)` 再写入——
同一文档重复上传是**覆盖**而非累积膨胀。

### 2.3 Embedding · 模型抽象层 ⭐⭐⭐

`📍 app/providers/embeddings.py`

| 项目 | 当前值 |
|---|---|
| 模型 | **BAAI/bge-m3**（SiliconFlow 提供 OpenAI 兼容接口） |
| 维度 | **1024** |
| 查询前缀 | `为这个句子生成表示以用于检索相关文章：` （bge 系列的标准用法） |
| 降级方案 | 本地哈希向量（零依赖，1024 维，L2 归一化） |

**两个模式**：
- `APIEmbeddings`：httpx 直连 `/embeddings`，分批（32 条/批），L2 归一化
- `LocalHashEmbeddings`：hashing trick + 亚线性 TF + IDF 加权 + L2 归一化，**无 API Key 时自动降级**

> **追问点**：本地哈希向量的 IDF 为什么关键？
> 不做 IDF 加权时，"的 / 员工 / 系统"这类高频词会淹没 "年假 / VPN / 报销" 等真正有区分度的关键词，
> 导致段落级检索失准。IDF 表在全量建索引时基于全语料统计并持久化。

**★ 模型抽象层设计（这是本项目最能体现工程素养的部分）**

```
app/providers/
├── base.py          # 抽象接口：Embedder(mode/dim/embed_documents/embed_query)、Reranker
├── embeddings.py    # 实现：APIEmbeddings / LocalHashEmbeddings / CachedAPIEmbeddings
├── llm.py           # 实现：ChatOpenAI 兼容 + 限流重试包装
├── rerank.py        # 实现：CrossEncoder
└── __init__.py      # 统一入口：get_embeddings() / get_chat_model() / rerank_docs()
```

**消除的三处模型特定硬编码**（面试可以直接讲这个重构故事）：

| 原来的写法 | 问题 | 重构后 |
|---|---|---|
| `if "bge" in model.lower(): 拼前缀` | 把 bge 模型知识写死在代码里 | → `EMBEDDING_QUERY_PREFIX` 配置项，换模型清空即可 |
| 温度不兼容自愈逻辑 | 为某个模型写的迁就代码 | → 删除，temperature 纯配置，参数错直接报错暴露 |
| `isinstance(emb, LocalHashEmbeddings)` | 新增 provider 就得改判断处 | → `Embedder.mode` 属性（`"api"` / `"local-hash"`） |

> **面试话术**：
> 「所有模型相关的部分都收敛到 `app/providers/`，业务代码只依赖抽象接口。
> **切换模型只需要改 `.env`，业务代码零改动。**
> 换 LLM 改 `LLM_MODEL_NAME` / `LLM_BASE_URL` / `LLM_API_KEY`；
> 换 Embedding 改 `EMBEDDING_MODEL_NAME` / `EMBEDDING_BASE_URL` / `EMBEDDING_QUERY_PREFIX`。
> 新增一个 provider（比如 Ollama、ONNX 本地向量）只需要实现 `Embedder` 接口并在工厂注册，
> 不需要动任何检索或生成逻辑。」

**Embedding 缓存** `utils/cache.py`：
查询向量内存 LRU + TTL（600s / 1000 条），文档向量内容哈希持久化。
**缓存 key 含模型名，换模型自动失效**，避免跨模型的脏向量。

**query embedding 复用** `core/request_ctx.py`：
同一个 query 只 embed 一次，通过 contextvars 在检索和动态路由之间共享，省掉一次约 400ms 的重复调用。

### 2.4 向量数据库 `📍 app/db/vector_db.py`

**双后端**，统一接口 `add / search / delete_by_source / count / clear / list_sources`：

| 后端 | 实现 | 适用场景 |
|---|---|---|
| **memory**（默认） | numpy 暴力余弦检索 + npz/json 落盘 | 零依赖，万级片段内性能充足 |
| **chroma** | HNSW 近似检索 | 生产环境海量文档 |

```python
# 暴力检索核心：向量已 L2 归一化，点积即余弦
scores = (self._vectors @ q) / q_norm
top_idx = np.argsort(-scores)[:k]
```

> **必答题**：数据量从 1000 条变成 100 万条，需要换什么？
> 「当前默认用内存向量库做暴力检索，万级片段内 latency 可接受（毫秒级）。
> 到 100 万条时暴力检索会退化成 O(N) 全量扫描，需要换成 **Chroma（HNSW）或 Milvus**——
> HNSW 是近似最近邻，检索复杂度降到 O(log N)，代价是召回率略低于暴力且内存占用更高。
> 本项目已经预留了这个切换点：`VECTOR_DB_TYPE=chroma` 改一个环境变量即可，
> 因为两个后端实现了同一套接口，上层检索逻辑零改动。
> 如果到千万级且需要分布式、标量过滤、多租户，会考虑 **Milvus**。」

> Chroma 后端有一个细节加分：Chroma 返回的是 L2 距离，
> 代码里做了 `score = 1 - dist²/2` 转换成余弦相似度（归一化向量下的等价变换），
> 保证两个后端返回的 score 语义一致。

### 2.5 L3 检索 · 混合召回 + RRF ⭐⭐⭐（本项目技术含量最高的模块）

`📍 app/rag/retriever.py`

**三路并发召回**（借鉴 Dify 的 `ThreadPoolExecutor` + `as_completed`）：

| 路 | 方式 | 擅长 |
|---|---|---|
| **dense** | 向量余弦检索 | 语义改写、同义表述（"怎么请假" → "休假申请流程"） |
| **lexical** | BM25 倒排索引 | 专有名词、制度条款精确字符（"年假" 必须命中 "年休假" 章节） |
| **rewrite** | 查询改写变体（默认关闭） | 扩展召回 |

**为什么用 RRF 融合而不是加权求和分数**（这是必背的）：

```
score(d) = Σᵢ wᵢ / (k + rankᵢ(d))     k = 60（SIGIR 2009 论文经验常数）
```

> 不同召回路的分数**根本不在同一量纲上**——
> 向量余弦相似度落在 0~1（且不同 embedding 供应商分布差异极大：bge-m3 常在 0.05~0.15，OpenAI 常在 0.3~0.9），
> BM25 分无上界。直接加权求和需要归一化，而**归一化参数会随语料漂移，极不稳定**。
>
> **RRF 只使用「排名」，完全绕开量纲问题**，对 k 不敏感、跨数据集稳健，
> 已成为 Elasticsearch / OpenSearch / Azure AI Search 的默认融合算法。

权重：`DENSE_WEIGHT=0.7`，`LEXICAL_WEIGHT=0.3`（向量为主，词面为辅）。

**中文词面匹配的两个坑**（`retriever.py:67` 的注释非常精彩，建议精读）：

```python
_CJK_STOP = set("的了是有着和在就都而我你他她它们这那吗呢吧啊很太最更也很还再又只才不没无"
                "给让向往把被对从到以为及其或与个们多少怎如何什么可以请问谢谢")
```

1. **必须过滤虚词**：中文没有空格分词，直接取字符集会把「的/了/是/有/多/少」卷进来，
   导致几乎所有片段都拿满分，词面路**彻底失去排序能力**。
2. **查询覆盖度而非匹配数量**：用 `|q∩c| / |q|`，长查询才不会天然占便宜。
3. **连续子串奖励 +0.3**：文档里原样写着「年假」应严格优于只有字符重合的「年休假」。
4. **中英分别计算取 max**：「VPN 连不上」里判别性关键词是英文那半个查询，
   若检测到一个分支就 return，另一路信号会被整个丢弃，词面路会**静默失效**。

**BM25 分词** `📍 app/rag/lexical.py`：中文同时产出**单字 + bigram**
- 单字：让「年假」能命中「年休假」（跨字组合，bigram 覆盖不到）
- bigram：提升短语精确度
- 参数：k1=1.5（词频饱和），b=0.75（文档长度归一化强度）
- **增量更新**：add/remove 只增删受影响文档的倒排项，避免每次全量重建

**阈值决策 + 软回退**（幻觉治理的关键）：

| 机制 | 配置 | 行为 |
|---|---|---|
| 检索阈值 | `SCORE_THRESHOLD`（默认空→自适应） | 本地哈希 → 0.08；真实神经向量 → **None（排序取 Top-K，不硬门禁）** |
| 软回退门槛 | local-hash → 0.05 / api → 0.04 | Top1 仍低于此值 → 判定知识库确实无答案，返回空 |
| 软回退 | 自动 | 阈值过滤后无结果 → 退回向量 Top3，但保留抑制门槛 |

> **追问点**：为什么真实神经向量下阈值设为 None？
> 不同供应商分数尺度差异极大（text-embedding-3-small 常 0.3~0.9，bge-m3 常 0.05~0.15），
> **套用固定阈值会导致检索恒为空**。排序取 Top-K 是唯一跨模型稳健的做法。

**去重只去「内容完全一致」**：
> 同源合并会把同一文档的不同章节（年休假 / 发薪）误并为一，导致具体问答召回错误片段——这是踩过的坑。

**候选集大小**：`candidate_k = min(max(top_k * 4, 30), store.count())`，先宽召回再精筛。

### 2.6 Rerank 精排 `📍 app/rag/rerank.py`

- **状态**：默认**关闭**（需 sentence-transformers 依赖，未安装自动降级为「不精排」）
- 模型：`BAAI/bge-reranker-v2-m3`，`RERANK_TOP_N=10`
- **设计**：cross-encoder 对 Top-N 候选二次评分重排，**只改顺序 + 附 rerank_score，不改 fused 分**
  ——置信度仍基于原始 RRF 分，保持跨模型可比

> 与 `reorder.py`（零模型交错重排，缓解 lost-in-the-middle）**正交**：

> reorder 是零成本的，只改变喂给 LLM 的顺序。

### 2.7 L4 生成 · Prompt 设计 ⭐⭐⭐（必考）

`📍 app/core/prompts.py` + `📍 app/rag/generator.py`

**Prompt 原文**（熟读，面试会让你背）：

```
你是专业的企业内部智能助手，请严格基于以下参考内容回答用户问题。

硬性约束：
1. 只使用参考内容中的信息，禁止编造、禁止臆测；
2. 每个关键结论后，用方括号标注其依据的片段编号，例如"年休假为 5 天[1]"；
3. 若参考内容不足以回答，直接回答"知识库中没有相关信息"，并给出建议；
4. 回答简洁、条理清晰，必要时分点陈述；
5. 涉及制度条款时，明确说明信息来源于哪份文档。

长期记忆（关于该企业与用户的已知背景，可作为上下文参考）：{memory_context}
参考内容：{context}
对话历史：{chat_history}
用户问题：{user_query}
```

**四个控制点**（这是你区别于普通 demo 的地方）：

1. **引用编号制度**：上下文组装时给每片编号 `[1][2][3]`，要求模型在结论后标注依据编号。
   > 没有编号制度时，模型会把多份文档的信息混着说，出错后**无法定位是哪份文档的问题**。

2. **幻觉抑制**：prompt 明确「只使用参考内容、不足则直说没有」。
   > 这是**成本最低且最有效的**幻觉治理手段，比事后校验更划算。

3. **优雅拒答**：置信度 < `REFUSE_THRESHOLD`（0.25）且无工具结果 → 直接拒答。
   ```
   知识库中没有找到能够回答该问题的相关信息。
   您可以：换一种说法再问一次，或联系行政 / IT 服务台获取人工帮助。
   ```

4. **长期记忆与检索证据分离注入**：
   > 参考内容是本轮检索到的**硬证据**，长期记忆是跨会话累积的**背景认知**，
   > 后者**不得作为事实依据被引用**——prompt 里明确区分了这两者。

**置信度为什么用 RRF 融合分而不是原始向量分** `generator.py:129`：

```
confidence = Top1 的 fused 分 / RRF 理论上限
RRF 理论上限 = (w_dense + w_lex) / (k + 1) = (0.7 + 0.3) / (60 + 1) ≈ 0.0164
```

> 向量分的绝对尺度随 embedding 供应商剧烈漂移，无法设定跨模型稳定的阈值。
> 而 RRF 分数只取决于「排名」，其**理论上限是一个常数**，用实测分除以上限即得**跨模型可比的归一化置信度**。

置信度调整规则：软回退片段 ×0.6（证据本身就弱）｜词面精确命中 +0.1｜有工具结果 +0.2。

**流式输出**：`stream_answer_tokens()` 逐 chunk yield，支持 SSE 打字机效果。
两级容错：429 → 回退带退避的 `_generate`；流式全程空 → 降级为一次性生成（部分供应商对超频流式请求静默返回空流）。

### 2.8 L5 评估迭代 `📍 app/rag/evaluator.py`

| 指标 | 定义 | 作用 |
|---|---|---|
| **HitRate@K** | Top-K 里有没有命中期望关键词 | 召回能力的下限指标 |
| **MRR** | 首个命中结果的排名倒数 | 衡量「好结果排得够不够前」 |
| **Faithfulness** | 答案字符二元组被上下文覆盖的比例 | **零成本幻觉粗筛** |
| **引用覆盖率** | 答案里带引用标记的比例 | 溯源能力 |

> **追问点**：忠实度为什么不用 LLM-as-judge？
> 严格做法是用 LLM 逐句核对，但那需要额外模型调用，对限频账号不现实。
> 这里用**字符二元组覆盖率**做零成本启发式：答案中大量出现上下文里根本不存在的二元组合时，基本可判定为编造。

还有 `suggest_improvements()`：命中率 < 0.7 时自动给出调优建议（优先补语料、其次检查切片是否切碎），**形成 L5 → L1/L2 的闭环**。

### 2.9 记忆系统 `📍 app/memory/`

参考 HKUDS/nanobot 的「记忆分层」理念：

| 层 | 内容 | 特点 |
|---|---|---|
| **短期** `short_term.py` | 当前会话活跃窗口 | 滑动窗口 + 字符预算 + 问答成对裁剪。快、会过期 |
| **长期** `long_term.py` | `MEMORY.md`（业务事实）/ `USER.md`（用户画像）/ `SOUL.md`（人格） | 慢、持久、跨会话累积 |

**两阶段流转**：
```
会话超阈值 → Consolidator 压缩归档 → history.jsonl（追加写 + 游标）
                                          ↓
                          Dream 蒸馏（LLM 提炼）→ 增量写入 MEMORY.md / USER.md
```

> **追问点**：为什么不每轮对话都读写长期记忆？
> 短期记忆在内存/Redis 里，零成本；长期记忆涉及文件 I/O 与（可选的）大模型调用。
> 把两者分开，才能让"记住东西"这件事**既及时又便宜**——绝大多数轮次只走短期记忆。

### 2.10 意图路由 `📍 app/core/intent_router.py`

**三层结构**（业界 Agent 系统的通行做法）：

| 层 | 方式 | 说明 |
|---|---|---|
| 1. 规则层 | 正则命中 | **零延迟、零成本、100% 可复现**，拦截约 80% 输入 |
| 2. LLM 层 | 规则未命中才调用 | 处理真正需要语义判断的输入 |
| 3. 兜底层 | 返回 `knowledge` | 宁可多检索一次，也不要把用户问题直接掐断 |

```python
# 优先级：寒暄 > 工具 > 知识
_TOOL_RULES = [(r"\bT\d{3,}\b", "tool", 0.95, "工单编号"), ...]
_KNOWLEDGE_RULES = [(r"(制度|规定|政策|流程|手册|规范|标准|条款|细则|办法)", "knowledge", 0.85, ...), ...]
```

> **为什么要规则优先（面试必讲的成本意识）**：
> 「原实现每轮对话都要先调一次大模型问'这是 knowledge/tool/unknown'。
> 在一个只有三选一、且大量输入是『查工单 T123』『年假多少天』这类**模式极其固定**的问题上，
> 这是最昂贵的选择方式：一次完整的网络往返 + 一次计费调用，只为拿回一个标签。
> **对限频账号（如免费档 3 RPM）尤其致命——意图识别会吃掉一半配额。**」

**并发预热优化** `intent_router.py:202`：
规则未命中时，LLM 分类（约 1.5s）与 query embedding（约 0.4s）**并发执行**，
总耗时从「1.5s + 0.4s」压到「max(1.5s, 0.4s)」。
> query 向量必须在**主线程**预热：contextvars 是 per-context 的，子线程 set 的值主线程读不到。

### 2.11 动态路由（Flash / Pro 选型）`📍 app/core/model_router.py`

**分层结构**：
```
L0 前置闸门 → L1 规则层(<1ms) → L2 分类器(prototype/bert/none) → 信号融合 → 阈值决策 → L3 级联(默认关)
```

**三个关键设计取舍**：

1. **打分与决策分离**：分类器只产出 0~1 的「难度分」，是否升档完全由阈值决定。
   > 「调成本」只需要动一个数，不需要重新训练或改规则。（借鉴 RouteLLM）

2. **信号融合取 `max` 而非加权和**：
   > 检索难度分和分类器分都可能单独构成升档理由，取平均会让
   > 「证据很弱但分类器觉得简单」这类请求被错误压成 Flash。
   > （借鉴 vllm-project/semantic-router：`d(t) = max(|d_vis|, |d_sem|)`）

3. **会话粘性只锁降级、不锁升级**：
   > 追问（"那如果…呢""还有例外吗"）通常比首问更难，沿用上轮档位会把用户锁死在 Flash；
   > 但上轮已用 Pro 时沿用 Pro 是安全的。

**分类器可插拔**：`prototype`（零依赖，复用现有 embedding 做原型打分）/ `bert`（需 transformers）/ `none`。
**abstain 机制**：`|score - threshold| < 0.08` 时判定「分类边界过近、不敢定档」，走默认档。

### 2.12 可观测性 · span 树 + TTFT `📍 app/core/tracing.py`

**span 树**：栈式嵌套 contextmanager，每请求一行 JSON 写入 `logs/trace.jsonl`

```json
{"trace_id": "3a6ed2391bb24181", "ts": "...", "elapsed_ms": 10337.14,
 "spans": [{"name": "chat_request", "duration_ms": 10337, "children": [
   {"name": "memory_load", "duration_ms": 3.62, ...},
   {"name": "generate_answer", "duration_ms": 10257,
    "attrs": {"ttft_ms": 10236, "chunks": 8, "answer_chars": 15}, ...}]}]}
```

**TTFT（首 token 延迟）埋点** `StreamStats` in `generator.py:44`：

> 一次 LLM 生成的时间 = **首 token 延迟**（网络往返 + 排队 + 模型调度）+ **后续逐 token 产出**。
> **两者慢的根因完全不同**——前者是网络/供应商排队，后者是模型吐字速度或输出过长。
> 只有分开记，换模型时才能直接定位「慢在哪」，而不是被一个总耗时黑盒误导。

对齐 OpenTelemetry 规范：**trace = 一棵树，根 span = 端到端延迟**（`chat_request`）。
contextvars 跨线程透传让 worker 线程里的节点 span 正确挂到根 span 下。

**LangSmith**：可选接入，设置环境变量后 LangChain 每次调用自动上报，业务代码零改动。

> 换非 bge 模型时清空配置即可，代码零改动。
>
> 无 API Key 时会自动降级为**本地哈希向量**（1024 维，hashing trick + TF-IDF + L2 归一化），
> 保证任何环境都能跑通完整链路。」

### Q5. 「向量数据库怎么选的？检索时用的什么算法？HNSW 还是暴力搜索？」

> 见 2.4。要点：**双后端**（memory 暴力 / chroma HNSW）、统一接口、一个环境变量切换、
> 百万级迁移方案、Chroma 的 L2→余弦转换细节。

### Q6. 「你的 System Prompt 怎么写的？怎么防止模型胡说八道？」

> 见 2.7。要点：五条硬性约束 + **引用编号制度** + **置信度拒答** + **记忆与证据分离**。
>
> 「防幻觉我做了**四道防线**，从便宜到昂贵：
> 1. **Prompt 约束**（零成本，最有效）：'只使用参考内容，禁止编造'；
> 2. **引用编号**（零成本）：强制标注依据片段，让编造变得可检测；
> 3. **置信度拒答**（零成本）：低于阈值直接说'没找到'，而不是硬凑无关片段；
> 4. **软回退门槛**：Top1 分数仍低于 0.04 时判定知识库确实无答案，返回空结果。
>
> 为什么不用更严格的 LLM-as-judge：它需要额外模型调用，对限频账号不现实。
> 我在 L5 用**字符二元组覆盖率**做零成本幻觉粗筛——
> 答案里大量出现上下文中根本不存在的二元组合时，基本可判定为编造。」

### Q7. 「如果文档解析失败怎么办？检索不到相关内容怎么办？」

> 「**文档解析失败**：`doc_loader` 每个文件独立 try-except，单文件失败只跳过该文件并记录日志，
> 不影响整批入库。L1 还有质量校验，过短（<10 字符）和空的文档会被直接丢弃。
>
> **检索不到内容**：分两种情况——
> - **零命中**：软回退机制生效，但如果连 Top1 向量分都低于 0.04，
>   判定「知识库确实没有答案」，直接返回空，由 L4 给出诚实回答，**而不是硬凑无关片段**；
> - **有命中但置信度低**（< 0.25）：L4 优雅拒答，给出转人工建议。
>
> **其他失败路径**：
> - 检索/意图/路由任一节点异常 → 该节点局部降级，**不阻断主流程**
>   （比如意图路由失败默认走 knowledge，动态路由失败回落默认档位）；
> - 生成失败 → `human_fallback` 节点转人工，附异常信息；
> - **三级自动降级**：无 API Key → Mock LLM；Embedding 接口不可用 → 本地哈希向量；
>   Redis 不可用 → 进程内内存缓存；Chroma 不可用 → 内存向量库；Rerank 未安装 → 跳过精排。
>   
> **核心原则：任何单点故障都不能击穿整个服务。**」

### Q8. 「怎么部署的？用的什么服务器？并发量多少？」

> 「**FastAPI + Uvicorn**，Docker 打包，docker-compose 一键编排（应用 + Redis）。
> Dockerfile 里分层优化（先装依赖利用缓存）、非 root 依赖最小化、配了 `HEALTHCHECK` 探活。
>
> 并发方面：**FastAPI 是 ASGI 异步框架**，同步的 LLM 调用我用
> `asyncio.to_thread` / `iterate_in_threadpool` 丢到线程池，避免阻塞事件循环。
> 入站有按 IP 的限流（20 次/分钟）。
>
> 无状态设计：会话历史存在 Redis（不可用时降级为进程内内存缓存），
> 应用本身无状态，可以水平扩展多个副本。
> 向量库在内存模式下是多副本各自持有索引的，
> 生产环境要水平扩展的话会切到 Chroma 或 Milvus 做共享存储。
>
> **我没做过的**：没有上 K8s、没有压测过确切的 QPS 数字——
> 目前是本地和 Docker 部署验证，没有真实线上流量。
> 如果要评估容量，我会先用 L5 的评测集跑基线，
> 再用 locust 压测找瓶颈点（我预计瓶颈在 LLM 调用，因为单次生成 1~10s 量级）。」

> 💡 **同样，承认没做过压测比编一个 QPS 数字安全得多。**

## 第 4 章：5 个快速检验（不看代码自测）

> 长文本里给的 5 个检验题，这是本项目对应的标准答案。

**Q1. 你的文档切分 chunk_size 是多少？为什么选这个值？**
→ 300 字符，overlap 60。面向企业制度类文档——约等于一个完整条款段落，
既够承载独立语义单元，又不会把多个不相关条款揉进同一片。
实测对比过 100（切碎，失去上下文）和 1000（语义稀释）。

**Q2. 用的 Embedding 模型叫什么？输出维度多少？为什么选择它？**
→ BAAI/bge-m3，1024 维。中文语义检索第一梯队，SiliconFlow 提供 OpenAI 兼容接口，
代码零改动即可接入。查询前缀配置化，不硬编码模型知识。

**Q3. 向量数据库选的什么？如果数据量从 1000 条变成 100 万条，需要换什么？**
→ 默认内存暴力检索（numpy 点积，万级内毫秒级），生产切 Chroma（HNSW，O(log N)）。
百万级改 `VECTOR_DB_TYPE=chroma`；千万级 + 分布式需求上 Milvus。
两个后端同接口，上层零改动。

**Q4. 你的 Prompt 里有没有防幻觉的约束？具体怎么写的？**
→ 有，五条硬性约束，核心是
「1. 只使用参考内容中的信息，禁止编造、禁止臆测；
2. 每个关键结论后用方括号标注依据的片段编号；
3. 若参考内容不足以回答，直接回答'知识库中没有相关信息'」。
外加引用编号制度、置信度拒答（<0.25）、软回退门槛（<0.04）三道补充防线。

**Q5. 如果用户上传了一个扫描版 PDF（图片），你现在的系统能处理吗？如果不能，怎么解决？**
→ **不能**。当前 `PyPDFLoader` 基于文本抽取，扫描版 PDF 没有文本层，抽出来是空的。
方案：加 OCR 层（PaddleOCR / Tesseract）或多模态版面理解；
工程上在 L1 加抽取质量校验（字符数异常少 / 乱码比例超阈值 → 标记走 OCR 重抽或人工介入），
现有的 `MIN_DOC_CHARS` 和 `quality_report()` 就是这个校验的雏形。

## 第 5 章：3 个故事素材（主动讲，别等问）

### 故事 1 · 遇到的 Bug 及解决 ⭐ 最有说服力

**「span 树耗时统计跟实际回消息时间对不上」**

> 「我给系统做了 span 树做耗时观测，但发现一个怪现象：
> 用户明显等了 10 秒以上，但 span 树记下来的总耗时只有 380 毫秒。
>
> 我一开始怀疑是计时口径有问题，就去查 `logs/trace.jsonl` 的真实记录，
> 发现每条 trace 里只有 4 个 span：memory_load、intent_recognize、knowledge_retrieve、model_route——
> **完全没有 generate_answer**。
>
> 顺着代码往下挖，发现流式接口里 `begin_trace()` / `end_trace()` 被包在了
> `_pre()` 这个内层函数里，而 `_pre()` 只跑前置节点。
> **生成循环是在 `end_trace()` 之后才执行的**，所以整个 LLM 生成阶段——
> 占了实际耗时的 97% 以上——从来没被 span 捕获过。
>
> 而且还有第二个问题：所有 span 是**平铺**的，没有单一根 span 代表整个请求，
> 持久化时用 `max(start_ms + duration_ms)` 算总耗时，自然只取到前置节点那几百毫秒。
>
> 修复分三步：
> 1. 把 `begin_trace()/end_trace()` 提到请求级作用域，所有异常和取消路径都保证 `end_trace()`；
> 2. 引入单一根 span `chat_request` 覆盖完整生命周期（历史加载 → 工作流 → 持久化 → 记忆整理）；
> 3. 流式生成循环单独包一个 `generate_answer` span。
>
> 这里有个技术前提需要验证：`asyncio.to_thread` 和 `iterate_in_threadpool` 会不会把
> 主协程的 contextvars 拷进子线程——我写了测试脚本实证过会，
> 所以主线程开根 span、worker 线程里开子节点 span 能正确挂载成树。
>
> 修复后我又往前走了一步：光知道生成慢还不够，
> 我在生成阶段加了 **TTFT（首 token 延迟）埋点**，
> 把耗时拆成「等首 token」和「逐 token 吐字」两段——
> 这两者慢的根因完全不同，前者是网络/排队，后者是模型吐字速度。
>
> 正是因为有了这个埋点，后面排查 10 秒延迟时我才能一眼定位：
> **TTFT 占了 10236ms，而吐字只用了 21ms**——
> 说明根本不是模型慢，是在等配额。然后我做了对照实验：
> 等配额恢复后用裸 httpx 直连测，TTFT 只有 0.85 秒。
> 结论是这个测试账号的限流是 **RPM=3**，服务端超限时不报 429 而是 hold 住连接等配额窗口，
> 所以日志里干干净净什么异常都没有，但用户就是干等 10 秒。」

> 💡 **这个故事展示了**：问题定位能力、读源码能力、可观测性意识、对照实验方法、不甩锅给「模型慢」的严谨。

### 故事 2 · 做的优化

**「从纯向量检索到混合召回 + RRF 融合」**

> 「最初是纯向量检索，有个很典型的失败案例：
> 用户问『年假有多少天』，文档里写的是『年休假』，
> 向量路能召回语义相关的片段，但排序时经常把无关的段落排到前面——
> 因为小语料上向量分布很挤，区分度不够。
>
> 我先加了一版词面打分，但只是对**向量候选集**重打分，
> 也就是说**向量池之外的纯词面命中根本进不来**。
> 后来改造成**独立召回路**：建了 BM25 倒排索引，跟向量库并行召回。
>
> 融合时我踩了个坑：一开始想加权求和，
> 但向量分落在 0~1（bge-m3 常在 0.05~0.15），BM25 分无上界，
> **两者根本不在同一量纲**，归一化参数还会随语料漂移。
> 最后换成 **RRF（Reciprocal Rank Fusion）**——只用排名不用分数，
> 完全绕开量纲问题，这也是 Elasticsearch 和 Azure AI Search 的默认做法。
>
> 中文词面匹配本身也有坑：中文没有空格分词，
> 直接取字符集会把『的/了/是/有/多/少』这些高频字卷进来，
> 导致几乎所有片段都拿满分，词面路**彻底失去排序能力**。
> 我加了虚词过滤表，并改成用**查询覆盖度**（`|q∩c| / |q|`）而非匹配数量，
> 再给连续子串命中加 +0.3 的区分度奖励——
> 这样文档里原样写着『年假』会严格优于只有字符重合的『年休假』。
>
> 还有一个细节：中英文要**分别计算再取 max**。
> 像『VPN 连不上』这种，判别性关键词是英文那半个查询，
> 如果检测到一个分支就返回，另一路的信号会被整个丢弃，词面路会**静默失效**。」

### 故事 3 · 边界情况处理

**「软回退 + 优雅拒答，以及如何避免好心办坏事」**

> 「我加了 Fallback 机制，但这里有个反直觉的教训——
> **回退本身也可能制造幻觉**。
>
> 第一版是『检索无结果就退回向量 Top-3 兜底』，
> 结果用户问一个知识库里根本没有的问题，系统还是硬凑了 3 个完全无关的片段喂给模型，
> 模型就**一本正经地编了个答案**。这比直接说不知道糟糕得多。
>
> 所以我加了两道闸：
> 1. **软回退门槛**：即使要回退，Top1 向量分仍低于 0.04 时，
>    判定『知识库确实没有答案』，**直接返回空**，由生成层给出诚实回答；
> 2. **优雅拒答**：置信度低于 0.25 且无工具结果时，直接返回拒答话术 + 转人工建议。
>
> 另一个边界是**寒暄**。第一版把寒暄也走生成，
> 结果用户说『你好』，系统因为没有检索文档、置信度 0，
> 回了一句『知识库中没有找到能够回答该问题的相关信息』——灾难级体验。
> 我把它改成独立的 `smalltalk_reply` 节点：**模板直出，不检索、不调模型**，
> 借鉴 Rasa 的 RulePolicy 和 FastGPT 的指定回复节点。
> 顺带还有个收益：寒暄零模型调用，对限频账号省下了实实在在的配额。
>
> 还有一层更底边的：**三级自动降级**。
> 没有 API Key 时用 Mock 模型、Embedding 接口挂了用本地哈希向量、
> Redis 挂了用进程内内存缓存、Chroma 挂了用内存向量库、Rerank 没装就跳过精排。
> 设计原则是**任何单点故障都不能击穿整个服务**——
> 宁可质量降级，也不能不可用。」
