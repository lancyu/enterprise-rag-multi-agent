## 二、开源项目调研 + 可落地方案

调研对象：**LlamaIndex**（重排/后处理）、**Dify**（并发召回 + rerank 工厂，源码已在本地下）、**OpenTelemetry + Langfuse/LangSmith/Phoenix**（可观测）、**ragas**（评估指标）。

### 2.1 重排序 —— 两阶段漏斗

业界共识是「bi-encoder 粗召回 → cross-encoder 精排」两级漏斗。LlamaIndex 提供 `SentenceTransformerRerank` / `CohereRerank` / `LongContextReorder`；Dify 用 `RerankRunnerFactory` 抽象出 `RerankModelRunner`（模型精排）与 `WeightRerankRunner`（加权重排）两种模式。

- **我已有的 reorder** = `LongContextReorder` 同类，零成本、零延迟，但**只改顺序不改分数**，不提升「真正该进 Top-K 的片段」。
- **可落地**：候选 30 → RRF 融合取 top-20 → cross-encoder 精排 → 取 top-5。但 cross-encoder 在 CPU 上重排 20 条约 **80–120ms**，且需引 `sentence-transformers`。**建议 demo 阶段做成可选开关 + 本地 `bge-reranker-base`，默认关闭**，先用 reorder 顶着。

### 2.2 可观测性 —— 自研 span 树（不引依赖）

OpenTelemetry 是事实标准（trace = span 树，`gen_ai.*` 属性），Langfuse/LangSmith 都基于它。落地不引入重依赖的方案：

1. `span()` 升级为**栈式 parent/child**（contextvars 维护当前 span 栈，自动嵌套）；
2. span 携带结构化字段：`name / start / end / attrs`（检索附 chunk 数+top 分，生成附 token 用量）；
3. 请求结束时把整棵 span 树挂到响应 `trace` 字段，前端渲染**瀑布图**；
4. 追加写 `logs/trace.jsonl`，支持离线回放（Langfuse 的 replay 思路）。

### 2.3 并发 —— 消除串行叠加

Dify 的 `ThreadPoolExecutor` 多路并发我已落地在检索内部。**进一步**：`意图分类 LLM` 与 `检索 embedding` 互不依赖，可在 `intent_recognize` 前并发预热 embedding（缓存命中后后续零成本），把「分类 + 检索」的串行 1.9s 压成并发 1.5s。

### 2.4 RAG 完整设计（检索 / 重排 / 生成 / 评估）

**① 检索（已落地）**：三路并发召回（dense 向量 + lexical BM25 倒排 + rewrite 默认关）→ RRF 融合（k=60，权重 0.7/0.3）→ 阈值过滤（fused 分）→ 内容去重 → 软回退。词面索引中文「单字+bigram」分词，索引落 json、增量维护。

**② 重排**：当前 `reorder`（交错重排缓解 lost-in-the-middle）；**增强项**为 cross-encoder 精排（可选开关）。

**③ 生成**：`build_context` 编引用号 → `prepare_generation`（置信度 = RRF 分归一化 + 词面命中加成，低于阈值优雅拒答）→ 受控生成（prompt 强约束「只用参考内容、不足则直说」）→ 引用抽取。已含引用溯源、幻觉抑制、拒答三板斧。

**④ 评估（L5）**：离线 `HitRate@K` + `MRR`；线上反馈 jsonl + 好评率；`faithfulness`（字符二元组覆盖，零成本幻觉粗筛）+ `citation_coverage`；`suggest_improvements` 规则化调优建议。**缺失**：`answer_correctness` / `context_precision`（需 LLM-as-judge，ragas 已有，限频账号暂缓）。

## 五、响应缓慢分析 + 耗时统计方案

### 5.1 瓶颈定位（详见上方耗时分布图）

一次真实 API 模式的问答，**延迟几乎全部来自外部网络调用**，本地毫秒级环节（记忆加载 2ms、BM25 5ms、RRF 1ms、存储 3ms）可忽略：

| 环节 | 典型耗时 | 触发条件 |
|---|---|---|
| **生成（LLM 流式）** | ~2500ms | 每次必走 |
| **意图分类（LLM 兜底）** | ~1500ms | 规则未命中时（约 20% 输入） |
| **动态路由打分（embedding）** | ~400ms | prototype 分类器再 embed 一次 |
| **检索 Embedding** | ~400ms | 缓存未命中时 |
| 其他毫秒级 | ~10ms | 恒有 |

**三大根因**：
1. **一次请求串行叠加 2–3 次 LLM/embedding 调用**（分类 + 检索 embed + 生成），总延迟 3–8s；
2. **限频账号（RPM=3）** 一旦触发 429，指数退避重试会让单环节延迟放大数倍；
3. **动态路由 prototype 打分重复 embed query**，与检索的 embed 是同一份工作做了两次。

### 5.2 优化建议（按 ROI 排序）

1. **复用 query embedding**：检索阶段算好的 query 向量传给动态路由打分，省掉 400ms 重复调用（收益最直接）；
2. **意图分类与检索并发**：两者无依赖，`asyncio.gather` 化，1.9s → 1.5s；
3. **Embedding 缓存命中**（已实现）：重复提问零成本；
4. **语义缓存**（增强）：相似问直接复用历史答案，绕开整条链；
5. **流式已实现**：首 token 延迟已优化，剩余是 TTFT 问题，靠上面 1–2 项压。

### 5.3 耗时统计与展示（trace 级）

现状：节点 `_trace` 有 `elapsed_ms` 并返回前端；`span()` 只打日志。**增强设计**（本轮不实施）：

- `span()` 升级为**嵌套 span 树**（contextvars 栈式 parent），每个 span 记录 `start/end/attrs`；
- 响应 `trace` 字段携带整棵树 + 各 span 耗时 + 生成 token 用量；
- 前端把 `trace` 数组渲染成**瀑布图**（每节点一行，横向条长度=耗时，可点开看 span 明细）；
- 追加 `logs/trace.jsonl` 持久化，`/routing/stats` 类接口支持按 `trace_id` 查询慢请求。
