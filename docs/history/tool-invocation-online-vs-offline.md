# 工具调用的决策分层：在线分析与离线抽取的适用边界

> ⚠️ **本文写作于「单 Agent 架构」时期，其中提到的部分模块已随多 Agent 重构删除**
> （`core/{intent_router,model_router,complexity_scorer,query_signals,intent_catalog,cascade,smalltalk}.py`、
> `tools/{rule,ticket,user}_tool.py`、`api/routing.py`，存档见 `_archive/`）。
> **当前架构以 [`docs/multi-agent-architecture.md`](multi-agent-architecture.md) 为准**；
> 本文的**问题分析、实测数据与判定方法仍然有效**，读时把模块名当作"当时的现场"。


> 本文回答三个问题：
> ① 「查询员工」「查询表单」这两类能力在企业知识库场景下的局限；
> ② 它们是否确有必要；
> ③ 「意图路由的核心目的是减少大模型开销、因此通常应把工具选择与参数抽取交给
> 模型在线完成」——这个理解是否成立。
>
> 所有结论均附实测证据，复现命令见 §7。

---

## 1. 结论速览

| # | 结论 | 置信度 |
|---|---|---|
| C1 | **「查询表单」这个能力在本项目中不存在**。全仓库 `表单` / `form` 零命中；最接近的是 `ticket_lookup`（工单 / 报修单 / 申请单状态查询）。讨论它要先确定指的是「单据状态」还是「表单模板」——两者该走完全不同的通道 | 高（实测） |
| C2 | **两类能力都确有必要**，但理由不是「方便」，而是**数据结构与知识库根本不同**：员工属性是**活的、精确匹配的、有权限边界的**；单据状态是**每个实例独有的可变状态**。二者都不是「一堆文档」能被语义检索命中的对象 | 高 |
| C3 | **当前实现是演示级，不是可用级**。员工库仅 5 条 mock，工具无身份参数、无权限、无审计 | 高（实测） |
| C4 | 你的理解**方向正确，但有三处需要校正**：目的被窄化、把「离线/在线」当成二分法、以及把一个受约束的工程取舍误当成普适判断 | 见 §4 |
| C5 | 真正的分水岭不是「在线 vs 离线」，而是**槽位的来源**。槽位有三类来源，其中只有第一类适合离线抽取 | 见 §5 |

## 2. 事实清点：两类能力的真实边界

### 2.1 「查询员工」——声明的能力远大于可服务的范围

能力声明在 `app/core/intent_catalog.py:150-268` 的 `INTENT_CATALOG` 里
（`employee_lookup` 条目），`channel=tool`、`detector=employee`，
且**显式声明了一条示例问句：「我的分机号是多少」**。

工具实现在 `app/tools/user_tool.py`，参数抽取靠 `extract_identifier`
（`app/tools/user_tool.py:25-60`）：先匹配 `_ALIASES` 的 **5 个中文姓名**，
再兜底匹配拉丁账号正则。

实测（§7 命令 A、B）：

| 问句 | 员工意图判定 | 抽到的标识 | 实际去向 |
|---|---|---|---|
| 张三在哪个部门 | ✅ | `张三` | 正常返回「技术部」 |
| 四月在哪个部门 | ✅ | **空** | ❌ 回退知识检索 |
| 我的分机号是多少 | ✅ | **空** | ❌ 回退知识检索 |
| 张伟在哪个部门 | ✅ | **空** | ❌ 回退知识检索 |

注意第三行：**它是能力目录里白纸黑字声明的示例问句，却走不通**。
这不是「长尾没覆盖」，而是**声明的能力边界与实际可服务范围不一致**——
比抽不出「四月」严重得多，因为它说明这条能力从来没有被端到端验证过。

同时 `query_user_info(user_identifier)`（`app/tools/user_tool.py:50`）**没有请求方参数**：
谁问、能不能问、问过谁，一概没有记录。而知识侧的权限体系
（`app/core/source_acl.py:24` 的 `resolve_allowed_sources`，经
`app/core/rag_engine.py:37-50` 落到 `retrieve()`）**完全覆盖不到工具通道**。

### 2.2 「查询表单」——不存在，且「表单」是个歧义词

全仓库搜索 `表单` / `form_query` / `fill_form` 均为 0 命中。最接近的是
`ticket_lookup`（同上目录文件里的 `ticket_lookup` 条目），关键词
`("工单", "报修单", "申请单", "订单")`，抽参数靠
`app/core/query_signals.py:81` 的 `TICKET_ID_PATTERN = T\d{3,}`。

实测（§7 命令 C）：

| 问句 | 判为工单意图 | 抽到编号 | 实际去向 |
|---|---|---|---|
| 工单 T20240101 什么状态 | ✅ | `T20240101` | 正常返回状态 |
| 我的工单进度 | ✅ | **空** | ❌ 回退知识检索 |
| 报修单处理到哪一步了 | ✅ | **空** | ❌ 回退知识检索 |
| 我提交的申请单通过了吗 | ❌ **根本没识别** | 空 | ❌ 回退知识检索 |

两个发现：

1. **「我的工单进度」抽不出东西，不是规则写得不好，而是句子里根本没有这个信息。**
   编号在系统里、在会话身份上，不在用户的这句话里。**任何离线规则都不可能抽到它**——
   这是原理性边界，不是覆盖率问题。
2. 「我提交的申请单通过了吗」连意图都没识别到：`TICKET_STATUS_PATTERN`
   要求 `(工单|订单|申请单|报修单).{0,6}(状态|进度|查询|到哪)`，「通过了吗」不在枚举里。
   这正是**开放语言 vs 闭集正则**的典型失配。

### 2.3 一个共同的坏出口

三条失败路径最终都汇入 `_fallback_to_knowledge`（`app/graph/nodes.py:215-248`）：
把 `tool_result` 清空、`intent_type` 改写成 `knowledge`，然后拿原问题去检索。

实测「四月在哪个部门」返回的答案里带着一句「建议：联系人力资源部咨询」——
这句话**只是检索碰巧命中了 HR 文档**，不是答案，但用户会以为系统真的查过了。
更隐蔽的是观测口径：这条请求在 `intent_source` 里被记为 `rule+tool_fallback`，
在 `intent_type` 里被记为 `knowledge`，**同一请求同时计入「工具意图」和「知识检索」**，
所以「工具能力到底好不好用」这个指标永远看不出问题。

## 3. 必要性判断

### 3.1 判断标准：这个问题的答案，在不在「文档」里

知识库检索擅长的是「**关于**某件事的表述」，不擅长「**某条**具体记录」。
据此可以一刀切开：

| | 员工属性查询 | 单据 / 表单状态查询 | 制度咨询 |
|---|---|---|---|
| 答案形态 | 某人的一条记录 | 某个实例的当前状态 | 一段通用表述 |
| 是否可变 | 会变（调岗、换分机） | **高频可变**（每分钟都在流转） | 低频可变（有版本） |
| 检索能否胜任 | ❌ 语义相似≠精确取值 | ❌ 完全无解，语料里根本没有 | ✅ 正是它的强项 |
| 是否有权限边界 | **有**（他人邮箱/分机/汇报关系） | **有**（只能看自己的单） | 较弱 |
| 结论 | **必要** | **必要，且更刚需** | 不需要工具 |

**「单据状态查询」比「员工查询」更刚需。** 因为员工信息偶尔还能在组织架构文档里
碰巧被检索到（虽然不可靠），而「我这张报销单到哪了」在知识库里**一定不存在**——
它甚至不是「检索质量差」，是**检索的对象错了**。此时回退检索不是降级，是**答非所问**。

### 3.2 「查询表单」必须先把歧义拆开

用户说的「查表单」至少有两种意思，而它们的正确归宿**恰好相反**：

| 用户意图 | 例子 | 正确通道 |
|---|---|---|
| 查**我这张单子**的状态 | 我的报销单批了吗 | **工具**（需身份 + 业务系统 API） |
| 查**表单模板 / 要填什么** | 报销单要填哪些字段 / 模板在哪下载 | **知识**（是稳定的制度性表述） |

二者用词高度重叠（都会出现「报销单」），**词面规则区分不了**。
这是「同一个词映射到不同通道」的经典情形，也是后文 §4 校正二的具体例子。

### 3.3 结论：方向必需，但当前四个前提一个都不满足

员工查询要在企业里真正可用，必须同时具备：

1. **接入真实目录数据源**（LDAP / HR 系统），而不是 5 条硬编码 mock；
2. **身份与授权**——「谁能查谁」必须可判定，且写审计；
3. **参数抽取可靠**——现在 5 个名字之外全崩；
4. **话术诚实**——当前数据源只有 5 条 mock，却回「未查询到 四月的员工信息」，
   这在语义上等于宣称「我们查过了，全公司没有叫四月的」。**这是不诚实的**。

单据查询同理：需要业务系统 API（`ticket_tool` 已有 `TICKET_USE_REMOTE` 开关，
`user_tool` 连这个开关都没有）+ 身份绑定（「我的单」需要知道「我」是谁）。

## 4. 校正你对「意图路由设计初衷」的理解

你的原话可以拆成两个断言：

- **A**：意图路由的核心目的是「提前分析并决定调用哪些工具，以减少大模型开销」；
- **B**：通常情况下应把工具选择与**参数抽取**交给大模型在线完成，而不是离线抽取。

### 4.1 断言 A：方向对，但把目的窄化成了一条

**证据支持的部分**：本项目把这个目的写得很直白——
`app/core/intent_router.py:150-152` 的 `llm_free_rate` 注释是
**「零大模型调用比例——本设计的核心收益指标」**，
`to_dict()` 里也把它作为首要统计项。所以「省调用」确实是**主要收益**。

**被窄化的部分**：意图路由在这里实际做的是**三件事**，省钱只是其中一件：

| 它在做的事 | 具体表现 | 省钱能否解释 |
|---|---|---|
| **分链**（不只是选工具） | 4 个出口：knowledge / tool / smalltalk / 直达 | ❌ 寒暄走模板直出，首要目的是**避免拒答文案误伤**，不是省钱 |
| **守边界** | `CHANNEL_KNOWLEDGE` 只有 4 个业务域；域外问题有明确的拒答路径 | ❌ 这是**可控性**，与成本无关 |
| **让路由可验证** | 规则可枚举、可单测、可用 `preview` 查「为什么这样路由」 | ❌ 这是**可解释性/可审计** |

对照组恰好能说明问题：`ai-career-copilot` 的 planner
（`backend/agents/planner.py:58-64`）**每轮必调一次 LLM 做意图分类**，
它的 `_INTENT_PLAN`（`:21-29`）同样是「意图 → 工具链」的映射。
两个项目**架构目标相同**（都是选链路），差别只在**用什么实现**。

所以更准确的说法是：

> 意图路由的核心目的是**把「这次请求该走哪条处理链」变成一个可判定、可解释、
> 可测试的决策**。减少大模型开销是它的**主要收益**（在本项目的配额约束下尤其重要），
> 但不是它的全部目的，也不是唯一衡量标准。

### 4.2 断言 B：作为一般原则成立，但结论被过度推广了

「通常应交给模型在线抽取」在**通用工程实践**里是对的，理由是结构性的：
开放词表的槽位（人名、模糊标题、自然语言日期）**不可能被规则枚举完**，
而且每新增一个取值就要改代码，维护成本随业务线性增长。

但有两点必须补上：

**第一，本项目采用离线抽取是受硬约束所迫，不是理解错了。**
上游 LLM 配额极严（RPM 个位数级别，见 `docs/deployment.md` 与
`docs/history/production-readiness-review.md` 的容量说明），
「每句都先问一次模型」在这里是不成立的方案。此时离线抽取是一个**被约束逼出来的、
合理的**选择。真正错的地方是后面这条 ↓

**第二，错的是「离线抽取用在了开放词表槽位上」，不是「用了离线」本身。**
本项目所有槽位抽取都是离线的——`extract_identifier` 是别名表 + 正则
（`app/tools/user_tool.py:25-60`），`find_ticket_ids` 是正则
（`app/core/query_signals.py:81`），`query_enterprise_rule` 是子串匹配。
但其中**「工单编号 T\d{3,}」这类槽位，离线抽取是正确且更优的**：格式封闭、
零成本、零延迟、可单测；换成让模型抽，只会更贵更慢更不稳。
**把「离线抽取」整体判为错误，会把对的部分一起否定掉。**

### 4.3 断言 B 还隐含一个二分法，而它其实可拆

「在线分析 vs 离线抽取」把两件可独立选择的事混成了一件。一次工具调用实际包含：

1. **准入**：这句话该不该走工具？走哪个工具？
2. **取值**：这个工具需要的参数从哪来？
3. **结果利用**：拿到工具结果后，要不要再过一次模型？

这三层可以各自独立地选在线或离线，**组合出的是 2³ 种方案，不是 2 种**。
把它们当成一个开关，就会推出「要么全离线、要么全在线」的错误结论——
而正确答案通常是**混合**。

## 5. 真正的分水岭：槽位从哪来

把「取值」这一层再拆开，槽位有**三类来源**，它们的可离线程度天差地别：

| 槽位来源 | 例子 | 离线抽取 | 原因 |
|---|---|---|---|
| **① 句内 · 格式固定** | 工单号 `T20240101`、身份证号、日期 | ✅ **应该离线** | 格式封闭可枚举，规则零成本零延迟且可单测 |
| **② 句内 · 开放词表** | 人名「四月」「张伟」、部门名、模糊标题 | ⚠️ **抽不全** | 取值集合开放且持续新增，规则只能靠穷举，结构上不可能覆盖完 |
| **③ 句外 · 身份 / 会话** | 「**我的**工单」「**他的**邮箱」中的「我 / 他」 | ❌ **永远抽不到** | **这个信息根本不在这句话里**，它在会话身份或上下文里 |

第 ③ 类是本节最关键的一条，因为它划出了**语言抽取的绝对边界**：
无论用规则还是用大模型，都无法从「我的工单进度」这七个字里得到工单号。
它需要的是**外部上下文注入**（当前登录用户的 ID），而不是更强的抽取器。

这解释了实测里最反直觉的一行：

```
我的分机号是多少   →  员工意图 ✅   抽到标识：空   →  回退知识检索
```

它既是「能力目录里声明的示例问句」，也是**语言抽取在原理上无解**的一类问句。
修它不需要更强的模型，需要的是**把身份接进链路**。

### 5.1 抽取失败 ≠ 目标不存在 ≠ 不该走这条链

当前实现把三件事当成了一件：

| 情况 | 性质 | 正确响应 | 现状 |
|---|---|---|---|
| 抽不出人名（语言问题） | 需要更强的抽取或澄清 | 追问「您想查询哪位同事？」 | ❌ 回退检索 |
| 抽出了人名但库里没有 | 数据问题（存在性） | 诚实说「未收录该员工」 | ❌ 回退检索 |
| 这句话本来就不是工具查询 | 路由问题 | 交给知识链 | ✅ 这是唯一正确使用回退的场景 |

**注意第二行**：即使接入在线抽取，「四月」也依然查不到——因为员工库里根本没有这个人。
**在线抽取能解决「抽不出来」，不能解决「库里没有」。**
把这两件事混为一谈，就会误以为「上了大模型抽取就没事了」。

## 6. 适用场景对照

### 6.1 七维判据

| 判据 | 偏向离线 | 偏向在线 |
|---|---|---|
| 动作空间 | 闭集且稳定（本项目 2 个工具） | 数量多、边界模糊（>10 个） |
| 槽位来源 | ① 格式固定 | ② 开放词表 / ③ 需上下文推导 |
| 调用预算 | 极紧（RPM 个位数） | 宽松 |
| 错误代价 | 只读、可澄清 | 写操作 / 不可逆 / 涉他人隐私 |
| 长尾覆盖要求 | 低（问法收敛） | 高（C 端自由表达） |
| 可审计要求 | 高（合规、金融、医疗） | 一般 |
| 延迟要求 | 极低（寒暄、模板） | 可容忍一轮往返 |

### 6.2 一个反直觉但很重要的推论

**如果只买得起一次大模型调用，应该花在「取值」而不是「准入」。**

理由是比较两者的**边际收益**：

- **准入**是闭集分类。规则可以做到很高的覆盖率（本项目 4 个出口都有确定性判据），
  而且**判错的代价可以被「澄清」兜住**——最坏情况是多问一句。
- **取值**在开放词表上，规则的覆盖率**结构性为 0**——
  不是「覆盖得少」，是「新名字一个都覆盖不了」。而它判错的代价当前是**静默地换了个分支**，
  用户拿到一段无关内容还以为是答案。

也就是说：**准入可以离线，取值不该离线**。
这与 §5 的三类槽位表完全一致——准入对应「闭集」，取值对应「开放词表 + 上下文」。

### 6.3 结论：该在线的在线上，该离线的离线

```
准入（该走哪条链）  →  离线规则为主        ← 闭集、高频、需可解释、判错可兜
取值（槽位内容）    →  按来源分流：
                        ① 格式固定  → 离线规则
                        ② 开放词表  → 规则先抽 → 抽不到才在线抽一次 → 仍不行则澄清
                        ③ 身份会话  → 上下文注入（不是抽取问题）
结果利用            →  在线（工具结果仍需模型组织成话）  ← 本项目已是如此
```

**最后一行值得单独说明**：本项目的工具通道并不是「零模型调用」——
`app/graph/workflow_graph.py:33-81` 的图里，边是
`tool_invoke → model_route → generate_answer`，
拿到工具结果后**仍然要过一次模型**才成文。
所以「减少大模型开销」准确的表述是：
**省掉「每句一次的选路调用」，而不是「整轮零调用」。** 指标口径应当写清楚这一点。

```bash
# A. 员工问句的意图判定与参数抽取
PYTHONPATH=. ./.venv/bin/python -c "
```

## 9. 二次校准：三处需要修正的论证前提

> 本节是对 §4 的追加。**结论不变，但证明路径要换两处**，并补上一笔此前没算的账。

### 9.1 「省 LLM 开销」这件事，目前的度量只覆盖 18%

`llm_free_rate` 的定义（`app/core/intent_router.py:139-173` 的 `_RouteStats`）：

```python
return round((self.total - self.by_llm) / self.total, 3)
```

`by_llm` 只统计**路由层灰区仲裁**的次数。而 `generate_answer` 的那次调用
——`app/graph/workflow_graph.py:33-81` 里 `tool_invoke → model_route → generate_answer`
是**无条件边**——**不在任何指标里**。

以 100 次实质提问为基准：

| 环节 | 调用次数 | 是否被指标统计 |
|---|---|---|
| 路由层灰区仲裁 | 22 | ✅ |
| 答案生成 | 100 | ❌ |
| **合计** | **122** | **仅 18% 被统计** |

README 第 14 行把它表述为「78% 查询零模型调用」。**精确说法是
「78% 的查询在路由环节零调用」**——两者差的正是那次生成调用。

> 这不是抠字眼：如果「降低 LLM 开销」确实是核心目标，那么**占比 82% 的生成调用
> 从未被度量过，也就从未被优化过**。指标量到哪里，优化才发生在哪里。

### 9.2 成本账：急切的在线抽取会让工具路径调用数翻倍

工具路径今天的调用构成**恰好是 1 次**：

```
路由（纯规则 0）→ 工具（纯函数 0）→ model_route（纯规则 0）→ generate_answer（1）
```

若按「意图定完后一律交 LLM 抽参」实现，同一路径变成：

```
路由（0）→ LLM 抽取（1）→ 工具（0）→ generate_answer（1）  =  2 次
```

**净增 100%，且恰好增在最需要控制成本的那条路径上。** 在 RPM 只有个位数的账号下，
这不是优化，是自伤。

→ 所以「把取值交给 LLM」若要成立，**必须同时砍掉结果利用层的生成调用**：
工具返回的本就是确定性事实（「技术部」「8021」），不需要模型再组织一遍。

**真正的省钱一刀在结果利用层，不在抽取层。** 抽取是「花钱买覆盖率」，
结果利用是「白花的钱」。

### 9.3 惰性升级的触发信号，正是今天被丢掉的信号

§6.3 提出的「规则先抽 → 抽不到才在线抽一次」有一个**此前没点明的前置条件**：
**「抽不到」这个信号必须被保留下来。**

而今天它被丢掉了——`app/graph/nodes.py:158-212` 的 `tool_invoke_node` 把
「句式命中但抽不出对象」直接并入 `_fallback_to_knowledge`，与
「这根本不是员工查询」共用出口。

这两种情况的**触发条件是完全相同的**：

```
looks_like_employee_query(q) is True   AND   extract_identifier(q) == ""
```

这是一个**零成本、高精度**的升级判据。修好出口分离之后，
「澄清」与「在线抽取」就是同一个位置上的两种响应：

```
抽到          → 查库返回
抽不到        → 在线抽取一次 → 抽到就查库，仍抽不到则澄清
不是员工问句   → 交回知识链（唯一该用 fail-open 的场景）
```

**也就是说：你要的架构，前提是先修出口分离。** 顺序反了的话，
升级触发条件会被 `_fallback_to_knowledge` 吃掉，永远不会触发。

### 9.4 两处前提性裂缝

**裂缝一：准入与取值不是两个独立阶段。**

`app/core/intent_catalog.py:96-97` 的 `_detect_employee` 是：

```python
return 0.9 if looks_like_employee_query(query) else None
```

它**只看句式**，不看「这个人认不认识」。于是系统会以 0.90 的置信度宣布
「这是员工查询」，而此时它**完全不知道能不能把这个人绑出来**。
「先定意图、再抽参数」这个两步模型在这里是漏的：准入判定与槽位绑定
在语义上耦合，却被拆成了两段。

**裂缝二：第 ③ 类槽位是反例。**

`INTENT_CATALOG`（`app/core/intent_catalog.py:150-268`）把「我的分机号是多少」
写成了 `employee_lookup` 的示例问句。但工具签名是
`query_user_info(user_identifier)`（`app/tools/user_tool.py:69-86`）
——**只有一个参数，没有请求方身份**。

这句话缺的不是「更强的抽取器」，而是**当前登录用户是谁**。交给 LLM 一样抽不到：
值不在句子里。**所以「上了大模型抽取就能解决覆盖问题」这个推论不成立**——
它只能覆盖第 ② 类，覆盖不了第 ③ 类。

### 9.5 若采纳，三条必守护栏 + 一个结构建议

| # | 护栏 | 理由 |
|---|---|---|
| 1 | **抽取结果必须能在原句原文定位**（span grounding） | 规则天然满足、LLM 不满足。不校验的话，「王小明在哪个部门」可能被抽成「王五」并返回**另一个人的部门**——静默错答比不答更糟 |
| 2 | **身份 / 会话类槽位永不走 LLM** | 这类值必须来自受信任上下文（登录态），不能来自模型输出，否则等于让模型决定「查谁的 PII」 |
| 3 | **LLM 抽取必须在开关之后** | 否则 337 条测试要么打满配额，要么全部退化为 mock，路由的可回归性归零 |

**结构建议：参数字典化。** 让每个工具在目录里声明自己的参数与**来源**：

```
employee_lookup.query_user_info:
    user_identifier : free_text    ← 规则先抽，抽不到才在线
    requester_id    : request_ctx  ← 永不走 LLM
ticket_lookup.query_enterprise_ticket:
    ticket_id       : literal      ← 规则，零成本零延迟
```

这样「离线还是在线」不再是**全局架构选择**，而是**逐参数的声明式策略**——
可单测、可审查。它延续的正是本项目最强的那条设计原则：
**「新增能力只加一条声明」**（`docs/history/intent-routing-redesign.md`）。
