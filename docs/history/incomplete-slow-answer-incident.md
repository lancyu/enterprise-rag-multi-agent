# 故障复盘：回答不完整 + 很慢

> ⚠️ **本文写作于「单 Agent 架构」时期，其中提到的部分模块已随多 Agent 重构删除**
> （`core/{intent_router,model_router,complexity_scorer,query_signals,intent_catalog,cascade,smalltalk}.py`、
> `tools/{rule,ticket,user}_tool.py`、`api/routing.py`，存档见 `_archive/`）。
> **当前架构以 [`docs/multi-agent-architecture.md`](multi-agent-architecture.md) 为准**；
> 本文的**问题分析、实测数据与判定方法仍然有效**，读时把模块名当作"当时的现场"。


**现象**：回答能出来，但（a）写到一半就断，（b）首字要等十几秒甚至几十秒。
**日期**：2026-09-11
**结论**：三条根因，全部与「默认模型是推理模型」相关。**其中两条是我们自己的配置/代码问题，不是模型本身的锅**。

上一轮故障（拒答 + 挂起）的复盘见 `biz-correctness-incident.md`，两者无重叠。

---

## 一、先回答「是不是模型的原因」

**部分是，但只是三分之一。**

| 结论 | 归属 |
|---|---|
| 模型是推理模型，正文前要先「思考」→ 首字天然慢 | **模型/选型**，不可改（账号下只有 2 个模型，且都是推理模型） |
| `max_tokens=1024` 被思考 token 挤占 → 正文截断 | **配置问题**，可改 |
| 截断后无任何日志与观测信号 → 无人察觉 | **代码问题**，可改 |
| 「只思考没正文」被判为供应商空流 → 回退重发 → 等待翻倍 | **代码问题**，可改 |

---

## 二、根因

### A. 模型是推理模型，思考阶段独占首字延迟

默认模型 `kimi-k2.6` 在正文之前会先产出一段**隐藏的** `reasoning_content`。
实测（同一问句「差旅报销流程是什么？请分点说明。」）：

| 配置 | 首个可见字 | 思考字数 | 正文 | finish_reason | 总耗时 |
|---|---|---|---|---|---|
| 思考开启（原配置） | 11123 ms | 535 字 | 1115 字 | stop | 28698 ms |
| `reasoning_effort=low` | 23785 ms | 1436 字 | 1463 字 | stop | 43585 ms |
| **思考关闭 + temp=0.6** | **1137 ms** | **0 字** | 875 字 | stop | 16992 ms |

**首字延迟相差约 10 倍。** 更糟的是 `langchain-openai` **不解析** `reasoning_content`
（其模块 docstring 明写："Non-standard response fields added by third-party providers
(e.g., `reasoning_content`, `reasoning_details`) are **not** extracted or preserved"），
所以这十几秒里前端**一个字符都收不到**——用户感知就是「卡死了」。

### B. 思考 token 与正文**共享** `max_tokens` → 正文被拦腰截断

这是「回答不完整」的**直接原因**。`max_tokens=1024` 不是「正文的长度上限」，而是
「思考 + 正文」的总额度。思考先吃掉 400~1000 字，正文写到 700~1300 字就撞顶。

实测多次命中 `finish_reason=length`：

```
kimi-k2.6  max_tokens=1024   首字 15790ms   正文  911 字   finish=length   ← 截断
kimi-k2.6  max_tokens=1024   首字 12394ms   正文 1299 字   finish=stop     ← 侥幸通过
kimi-k2.6  max_tokens=4096   首字 18732ms   正文 1046 字   finish=stop
```

**同配置时而截断、时而正常** —— 因为 1024 恰好卡在边界上。这解释了为什么用户
觉得「有时完整、有时不完整」。

### C. 截断完全静默（这才是最该修的）

`stream_answer_tokens` 只统计 `ttft / chunks / chars` 三项，**不读 `response_metadata`**。
于是被截断的答案与正常写完的答案，在日志里长得一模一样：

```
修复前：L4 生成完成：900 字 | 置信度 1.000 | 引用 1/5 个片段 | ttft=9964ms
修复后：L4 生成完成：900 字 | 置信度 1.000 | 引用 1/5 个片段 | ttft=9964ms | finish=length（已截断）
```

运维看不到任何异常，用户报「回答不完整」时无从定位。

### D. 「只思考、无正文」被判为供应商空流 → 回退重发 → 等待翻倍

思考把预算耗光时正文为 0，`produced=False` 触发「回退为一次性生成」。
但重试只会**再付一整个思考周期**，结果大概率相同。故障现场：

```
2026-09-11 20:18:31  开始生成（query=VPN 连接不上怎么办？）
2026-09-11 20:18:59  流式输出为空（疑似供应商空流），回退为一次性生成   ← 已等 28s
2026-09-11 20:19:29  span=generate_answer 耗时=57687ms                  ← 又等 28s
```

**一次这样的回退，把用户等待从 28 秒拉长到 57.7 秒。**

## 三、修法

### 配置（`.env`）

| 项 | 原值 | 新值 | 理由 |
|---|---|---|---|
| `LLM_DISABLE_THINKING` | 不存在 | `true` | 关闭思考阶段，首字 11123ms → 1137ms |
| `LLM_TEMPERATURE` | `1` | `0.6` | **与上项强耦合**：关思考后该模型只接受 0.6 |
| `LLM_MAX_TOKENS` | `1024` | `4096` | 思考与正文共享额度，1024 恰好卡在截断边界 |
| `LLM_TIER_PRO_MODEL` | `kimi-k2.7-code` | `kimi-k2.6` | 该模型**强制开启思考**（传 `thinking=disabled` 返回 400），与上项直接冲突 |

> `.env` 里原有的两处注释与事实相反，一并更正：
> ① 「kimi-k2.7-code 生成慢」——实测它比 kimi-k2.6 **快**（首字 4016ms vs 11123ms）；
> ② 「Pro 档已换成 kimi-k2.6」——实际值仍是 `kimi-k2.7-code`，注释改了值没改。

### 代码

**`app/config.py`** — 新增 `LLM_DISABLE_THINKING`（默认 `false`，保持对任意供应商兼容），
并纳入 `dump_config()` 快照。

**`app/providers/llm.py`** — 开关为真时经 `extra_body` 透传 `{"thinking": {"type": "disabled"}}`。
不在代码里判断模型名：该参数是供应商特定的，换模型要能一键关掉。

**`app/rag/generator.py`**
- `StreamStats` 新增 `finish_reason` 字段与 `truncated` 属性；
- `stream_answer_tokens` 逐帧读取 `response_metadata.finish_reason`，
  命中 `length` 时打 WARNING（含正文长度与两条修复建议）；
- **区分两种「空」**：
  - 空内容 chunk + **有**终止帧 → 预算耗尽，**不回退**（回退只会重付一个思考周期）；
  - 空内容 chunk + **无**终止帧 → 真·异常断流，**仍回退**（保留原有容错）。

**`app/api/chat.py`** — 把 `finish_reason / truncated` 挂进 `generate_answer` span 与
SSE `meta` 事件，前端可据此提示「回答未写完」。

## 四、验证

### 端到端（同一问句「差旅报销流程是什么？」）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 首 token | 27444 ms | **1306 ms** |
| 生成耗时 | 27911 ms | **8829 ms** |
| 端到端 | 28298 ms | **9592 ms** |
| 答案字数 | 49 字 | **454 字**（含引用 [1][2][4][5]） |
| 可观测性 | 无 | `finish_reason=stop`、`truncated=false` |

### 真实服务（直连 `127.0.0.1:8001`，非 TestClient）

修复后两次实测：首字 1720 ms / 3503 ms，端到端 18445 ms / 9653 ms，
答案 487 字 / 281 字，均为 `truncated=false`，`finish_reason=stop`。

> 首次请求里检索占 6.5s、路由占 3.0s（分类器超时降级），第二次恢复正常
> （检索 0.7s、路由 0.1ms）。**这两项与本次故障无关**，是 embedding 侧的一次性波动。
>
> 事后逐段计时，把这两项也钉清楚了：
> - 向量缓存冷加载 **88ms**（7.1MB / 325 条），可忽略；
> - 查询 embedding 单次 **270~414ms**（首次含 TLS 握手，实测冷启 2032ms、热态 352ms）；
> - 词面索引首次构建 **19ms**。
>
> 所以那 6.5s 是 embedding 供应商偶发变慢，**不是我们的缺陷**，也不在可修范围内。

### 质量没有被拿去换速度（A/B 对照）

改配置一次动了三样东西（关思考、`temperature` 1.0→0.6、`max_tokens` 1024→4096），
所以「快了」必须验证**不是靠牺牲准确性换的**。

**全量评测集**（27 条 `app/rag/eval_cases.yaml`，真实调用）：

| 指标 | 结果 |
|---|---|
| 拒答 | 0 / 27 |
| 被截断 | 0 / 27 |
| 关键词覆盖 | 27 / 27 |
| 平均忠实度 | 0.561 |
| 平均首 token / 端到端 | 2467 ms / 6816 ms |
| 报错 | 0 / 27 |

**同题 A/B（4 条最难的）**：速度 2.7~9.1 倍，但忠实度**四条全部略降**（平均 0.51 → 0.45）。
这个数字必须查实，不能只报速度。

`score_faithfulness` 是**精确率**（`|答案二元组 ∩ 上下文二元组| / |答案二元组|`），
分母在**答案侧** → 答案越长、越补充解释，分数越低。于是做三级控制：

**① 等长对照**——把两个答案都截到较短者的长度再算：

| 问题 | 全篇 旧→新 | 等长 旧→新 |
|---|---|---|
| 报销流程怎么走 | 0.664 → 0.626（-0.038） | 0.644 → 0.626（**-0.018**） |
| 客户是怎么分级的 | 0.559 → 0.472（-0.087） | 0.559 → 0.514（**-0.045**） |

差距缩小约一半 → 至少一半来自长度稀释。

**② 采样噪声带**——同配置重复生成 3 次，看指标自然波动：

| 配置 | 忠实度样本 | 均值 | 极差 |
|---|---|---|---|
| 新（关思考 / 0.6） | 0.534 / 0.486 / 0.361 | 0.460 | **0.173** |
| 旧（思考 / 1.0） | 0.524 / 0.587 / 0.586 | 0.566 | 0.063 |

**同配置下的自然极差 0.173，是等长残差（0.018 / 0.045）的 4~10 倍。**
即：单次 A/B 那点差距**落在噪声里，不足以判定降质**。

**③ 长度相关性**——把 6 个样本按字数排序，忠实度几乎单调递减：

| 字数 | 278 | 371 | 393 | 403 | 414 | 549 |
|---|---|---|---|---|---|---|
| 忠实度 | 0.587 | 0.586 | 0.524 | 0.534 | 0.486 | **0.361** |

Spearman ρ = **-0.94**（n=6）。这个指标测的更像「简洁度」，而不是「有据可依」。

**结论**：忠实度差异主要由**指标对长度的敏感性**解释，不是新配置在编造内容；
且新配置答案更长（455 字 vs 347 字），这恰恰是用户要的「回答完整」。

**仍然存疑（如实记录，不粉饰）**：新配置 3 次均值 0.460 vs 旧 0.566，差 0.106；
n=3、t≈1.9、p≈0.16，**统计不显著**，且与长度混淆，
**无法排除**「关思考后依据纪律略松」。要定论需要「等长 + 多样本」对照，
本次未做（账号 max RPM=3，每次生成 20s 间隔，成本高）。
另观察到关思考后方差更大（极差 0.173 vs 0.063），推测思考阶段起了「先规划再落笔」的稳定作用；
若后续要压方差，可试**保留思考但调低 `reasoning_effort`**（本项未验证；
早前实测 `reasoning_effort=low` 反而更慢：首字 23785 ms、思考 1436 字）。

## 五、顺带修掉的：索引重建的 O(n²) 写放大

排查「慢」时在检索链路上发现的独立缺陷，**与回答无关，只影响全量重建索引**。

`EmbeddingCache.put_doc_vec` 每写入一条就把**整个缓存**序列化后覆盖落盘，
而 `CachedAPIEmbeddings.embed_documents` 是**逐条**调用它的 → O(n²) 写放大。

实测（缓存 7MB / 325 条，写入 176 条文档向量）：

| 写法 | 耗时 |
|---|---|
| 逐条写（旧） | **23.77 s**（单条 135ms） |
| 批量写（新） | **0.141 s** |
| | **168x** |

**修法**：`put_doc_vec(text, vec)` → `put_doc_vecs(texts, vecs)`，一次调用写一批、
只落盘一次；`embed_documents` 改为收集完缺失项后**一次性回写**。

> 刻意**只保留批量接口、不提供单条接口**：只要单条接口存在，就有人会在循环里调它，
> 写放大就会回来。回归测试里留了对照用例固化这一点。

## 六、遗留

1. **首字约 1.2~1.5s**（真实 2281 字 prompt 实测 1187/1532ms），主要成本是模型预填充；
   端到端 4.9~10.2s，随答案长度变化。这是当前模型档位的正常水平。
   要再降只能换更小的模型或升级账号配额（现 **max RPM=3**）。
2. **思考内容被丢弃**：`langchain-openai` 不解析 `reasoning_content`。若将来要保留
   推理能力，需换 provider 专用包（如 `ChatDeepSeek`）或改走原生 SDK，
   才能把「思考中」流给前端，避免长时间无输出。
3. **`.env` 与 `.env.example` 的耦合说明**：`LLM_DISABLE_THINKING` 与 `LLM_TEMPERATURE`
   必须配套改，代码不做模型名判断，配错会以 400 明确报错（错误信息自解释）。
4. **路由分类器超时降级会白等 3s**（`ROUTING_CLASSIFIER_TIMEOUT_MS`）。
   日志中仅出现 1 次且发生在冷启动期，暂未处理；若线上复现频率上升，值得把
   超时收紧或让分类器复用检索阶段已算好的 query 向量（部分路径已复用）。
5. **忠实度的「等长 + 多样本」对照未做**（见第四节）：现有证据指向「指标长度敏感性」，
   但 n 太小，没有把「关思考后依据纪律略松」这个可能性排除干净。若要收口，
   需要固定前缀长度、每配置 ≥5 次采样，再比较均值置信区间。属**验证深度**的欠账，
   不是已知缺陷。
6. **探测污染的缓存条目**：早期直连上游探测时，`EmbeddingCache` 里写入了约 10 条
   `probe:` 前缀的无用条目（占 325 条里约 3%）。未擅自清理——删缓存要重新消耗
   embedding 配额（账号 RPM 受限）。如需清理，删掉 `data/embedding_cache.json` 中
   键含 `probe:` 的条目即可，不影响已入库文档向量。
7. **第一人称「我」未映射到 `user_id`**（上一轮遗留）：多用户场景下「我的年假」
   不会按用户隔离。当前为单用户环境，暂不构成实际问题。
