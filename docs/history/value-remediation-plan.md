## 三、R2 · 拒答出口统一（含两轮标定实验）

### 证据：两轮阈值标定实验（第二轮推翻了第一轮）

**第一轮 n=8 / n=8** 时结论是「完全可分」；**扩样到 35 / 35 后出现重叠**——
小样本的"完全可分"是假象。这正是当初标注「仅作方向性判断」的原因，现予更正。

**第二轮：库内 35 条 / 库外 35 条**（库外再分「明显无关 17」与「企业语境难例 18」），
各取 Top1 分数（真实 bge-m3）：

| 组 | dense 余弦（vec） | RRF 融合分（fused） |
|---|---|---|
| 库内（应可答） | 0.5296 ~ 0.7244（中位 0.6350） | 0.0158 ~ 0.0164 |
| 库外·明显无关 | 0.2834 ~ 0.4816（中位 0.3806） | — |
| 库外·企业语境难例 | 0.3673 ~ **0.5693**（中位 0.4520） | — |
| 可分性 | ⚠️ **部分重叠**（3 条难例越界） | ❌ **两轮均几乎完全重叠** |

**关键结论不变的部分**：`fused` 分在两组间**始终几乎完全重叠**（两轮一致），
证明它确实不携带相关性强度信息——这是 R2 的根因，不受样本量影响。

**关键结论被修正的部分**：dense 余弦**不是完全可分**，但重叠项有清晰的语义特征（见下）。

### 根因：用错了尺子

`estimate_confidence`（`app/rag/generator.py:142-164`）拿 **Top1 的 RRF 融合分**做归一化：

```python
fused_max = (DENSE_WEIGHT + LEXICAL_WEIGHT) / (RRF_K + 1)
base = min(1.0, top["fused"] / fused_max)
```

但 **RRF 的设计意图恰恰是「忽略分数强度、只看排名」**——这是它跨 embedding 供应商稳健的原因，也是它
**不携带相关性强度信息**的原因。上表证实了这一点：库内与库外的 fused 分几乎完全重叠。

于是「把这把只量顺序的尺子读数当归一化置信度」，等价于**从一个不含该信息的量里读该信息**。
后果实测：无关问句拿到 **0.89**，永远够不着 `REFUSE_THRESHOLD=0.25`。

`app/core/prompts.py:18-99` 的 `answer` 提示词第 3 条又约定「若参考内容不足以回答，直接回答『知识库中没有相关信息』」——
**拒答因此下移到了生成层**，而那里没有结构化信号回传，`refused` 保持 `False`。

### 重叠的 3 条不是噪声——它们指出了另一个缺口

越界的 3 条库外难例：

| 问题 | vec | Top1 来源 |
|---|---|---|
| 出差可以坐头等舱吗 | 0.5693 | 员工手册（差旅章节） |
| 我的年终奖是多少 | 0.5432 | 员工手册（薪酬构成） |
| 公司的股权激励计划怎么参与 | 0.5392 | 招聘与人才发展制度（激励与认可） |

三者都**语义上真的贴近库内主题**（差旅标准 / 薪酬制度 / 激励制度）——高分不是噪声。
它们的真实性质是：**问的是"实例数据"，而库里只有"制度条文"**。

- 库里**有**「薪酬构成有哪些项目」（制度）→ 该答
- 库里**没有**「我的年终奖是多少」（个人实例）→ 该走工具通道或澄清

这条边界**原理上无法用主题相关性阈值区分**，因为两者的语义表示高度重叠。

因此 R2 的正确目标不是「让所有库外问题都被拒答」，而是：

1. 用绝对阈值挡掉**完全跑题**的问题（这占绝大多数，且零误杀）；
2. 剩下的「主题相关但问实例」交给**另一个出口**（工具通道 / 澄清），即 R3 的领域。

> 这也再次印证了三件事必须分开出口：**「抽不出参数」≠「库里没有」≠「不该走这条链」**。
> 把后两者用同一个置信度阈值处理，就会在这里卡住。

### 方案（推荐 A，B 为过渡）

**A · 治本**：给 `estimate_confidence` 引入 **Top1 的 dense 余弦**作为绝对判据（fused 继续用于排序，两者分工明确）。

```python
# 排序仍用 fused（RRF 的本职）；「有没有证据」看 vec 绝对值
VEC_EVIDENCE_FLOOR = 0.52        # 标定值，见下表
base = min(1.0, top["fused"] / fused_max)
if float(top.get("vec", 1.0)) < VEC_EVIDENCE_FLOOR:
    base *= 0.3                  # 证据不足 → 压到阈值以下（0.25），触发前置拒答
```

压到阈值下即可，不必归零——保留区分度，日志里仍能看出「差多少」。

**阈值取值的权衡**（第二轮 35/35 样本实测）：

| 阈值 | 误杀库内 | 漏杀库外 | 评价 |
|---|---|---|---|
| 0.50 | 0 | 5 | 更保守，拒答更激进 |
| **0.52** | **0** | **3** | **推荐：零误杀** |
| 0.54 | 1 | 2 | 开始误杀，不划算 |
| 0.56 | 4 | 1 | 误杀明显 |

**取 0.52 的理由**：误杀（能答的答不了）直接损害可用性，漏杀只是少拦一条——
且**漏杀的部分仍有生成层提示词兜底**，用户不会因此拿到错误答案。

即这是**两层防护，而非替代**：检索层挡掉能挡的（零成本），生成层兜住剩下的（已在运行）。

bootstrap（2000 次重采样）显示「最大化准确率」的阈值中位在 0.5496，
但**准确率不是这里的正确目标函数**——按误杀优先原则应取 0.52。
正式定值前建议再扩到 ≥100 条/组，并重点覆盖**个人实例类**问句（最易越界的一类）。

**B · 过渡**：保持 A 的同时，在 `generate_answer`（`app/rag/generator.py:339-389`）生成后增加一步
「模型是否自称无答案」的检测。**但纯字符串匹配很脆弱**（换模型/改 prompt 即失效），
若要做得可靠，必须改提示词让模型输出**结构化标记**再解析——属于额外成本，建议只在 A 无法及时上线时用。

> **不推荐**：把 `SCORE_THRESHOLD`（`app/config.py:365-374`，API 模式下为 `None`）直接设成绝对阈值。
> 那是**过滤片段**用的，而这里要的是**整体判定无依据**——同一批片段可能每一条都不够格，
> 但「全都不过滤」和「整体没证据」是两件事。混用会让检索结果变少，却不改变拒答判定。

### 验收

- **库内 35 条零误杀**（这是硬约束——误杀直接损害可用性）。
- **明显无关的 17 条全部 `refused=True`，且不调用 LLM**（走前置拒答路径，零成本）。
- **3 条企业语境难例仍交由生成层兜底**——这是**预期行为而非失败**：
  它们需要的是「制度 vs 实例」的出口（R3），不是更严的阈值。
  验收时应**断言它们 `refused=False`** 并在注释里写明原因，防止后人误以为是漏网之鱼而收紧阈值。
- 新增回归测试，含**反向验证**：把 `VEC_EVIDENCE_FLOOR` 改回不生效，明显无关样本必须重新变成 `refused=False`。

### 风险与依赖

- ⚠️ **样本量仍不算大**：0.52 已由 35/35 样本支撑（零误杀），但正式定值建议扩到 **≥100 条/组**，
  并重点覆盖两类边界：**个人实例类问句**（最易越界）、**措辞与文档差异大的合法问句**（最易被误杀）。
- ⚠️ **口径必须记住**：`REFUSE_THRESHOLD=0.25` 与 `VEC_EVIDENCE_FLOOR=0.52` 是**两个不同量纲**的数
  （前者是归一化置信度，后者是余弦分），**不要合并成一个常量**，也不要拿一个去调另一个。
- ⚠️ **阈值与 embedding 模型绑定**：0.52 是 bge-m3 的标定值。**换 embedding 供应商必须重新标定**——
  余弦分的绝对水平随模型变化，这是本方案唯一的硬耦合点。
- 依赖：判定逻辑改动会影响 `/chat/ask` 的拒答率与前端徽标，**上线前要用评测集跑一遍拒答率变化**。

## 四、R3 · 工具通道授权与 ACL 贯通（阻塞于拍板）

### 证据

- `query_user_info`（`app/tools/user_tool.py:69-86`）签名只有一个 `user_identifier`，
  **不收请求方身份**、无鉴权、无审计日志。
- `source_acl.resolve_allowed_sources`（`app/core/source_acl.py:24-48`）产出的白名单，
  只在检索路径被消费（`app/rag/retriever.py:184-208` 的 `filter_by_allowed_sources`）；
  工具节点（`app/graph/nodes.py:158-212`）**完全不读** `allowed_sources`。
- 即：**检索做到了按部门隔离，工具通道是敞开的**——任何登录用户可查任意员工信息。

### 方案

1. **工具签名加请求方**：`query_user_info(user_identifier, requester_id)`，由 `tool_invoke_node` 从 `state["user_id"]` 传入。
2. **在节点层做授权判定**，而不是工具内部：工具保持纯查询，授权策略集中在 `source_acl` 一侧，
   避免策略散落到每个工具。
3. **加审计日志**：谁、何时、查了谁、结果如何（含被拒记录）。

### 验收

- 越权查询（A 用户查 B 用户）被拒绝且**留下审计记录**。
- 回归测试覆盖「授权通过 / 拒绝 / 豁免角色」三类。

### 拍板点（这是阻塞项，不是技术问题）

- **谁能查谁？** 自查询 / 直属上级查下属 / HR 查全员——需要组织架构数据，当前没有。
- **员工库怎么来？** 当前是 5 条硬编码（`app/tools/user_tool.py:25-60` 的别名表）。
  接真实 HR 系统需要权限与对接工作量，**超出代码范畴**。
- **是否保留该能力？** 若不接真实数据源，按 R1 标注为「示例能力」即可，
  R3 可整体推迟——**这是成本最低的合理选择**。

## 六、不建议现在做的

- **R3 若拿不到真实 HR 数据源** → 不要为了「看起来完整」而加一层没有数据支撑的授权框架。
  当前最诚实的做法是 R1 的「标注为示例」。
- **不要为了提升置信度指标去调 `REFUSE_THRESHOLD`**。0.25 这个值不是问题所在，
  问题在于喂给它的输入（fused 归一化）本身不含所需信息。**调阈值治不了用错尺子。**
- **不要补做「查询表单」类工具**。全仓库当前不存在该能力，且它属于「答案不在文档里」的一类，
  在 R3 的授权问题解决前，新增同类工具只会扩大同一个合规面。
