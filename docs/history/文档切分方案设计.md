# 文档切分（Chunking）方案设计

> 适用项目：`langgraph-enterprise-bot`（企业级 LangGraph RAG 助手）
> 文档类型：中文企业制度 / FAQ / 技术手册
> 版本：v1.0 · 2026-09-05
> 本文为**调研与策略设计**，不含实现代码。

---

## 0. 结论摘要

### 0.1 一句话结论

**本项目切分环节的主要矛盾不是「块太大或太小」，而是「切分边界落在了错误的位置」——当前 69% 的片段跨小节合并，把多个主题塞进同一个向量。正确解法是「结构感知边界 + 章节路径上下文头」，而不是调 `chunk_size` 或上语义切分。**

### 0.2 核心依据（本项目实测）

| 指标 | 实测值 | 说明 |
|---|---|---|
| 语料规模 | 3 篇 / 6427 字 | 员工手册 2414、IT支持指南 2169、产品FAQ 1844 |
| 文档结构 | 22 个一级章、80 个小节 | 层级为 `第X章` / `一、` → `X.Y` / `Qn：` |
| 当前产出 | 26 片段，均值 250 字，中位 260 字 | 24/26 落在 200–300 字，**长度分布本身是健康的** |
| **跨小节合并率** | **18/26（69%）** | 一个片段里同时含「3.3 邮件归档 + 四、办公设备 + 4.1 设备领用」 |
| 无标题片段 | 4/26 | 长小节被二次切分后，后半段丢失章节归属，无法溯源 |
| 当前块长换算 | 250 字 ≈ 250–375 tokens | 正好落在业界公认的 256–512 甜区 |

**结论**：块长无需大改。**边界**和**上下文归属**才是问题。

### 0.3 方案选型：三档建议

| 优先级 | 措施 | 预期收益 | 成本 | 建议 |
|---|---|---|---|---|
| **P0 必做** | 结构感知边界（按章/节切，不跨章）+ 章节路径上下文头 + 元数据扩展 | 消除主题混杂、片段可溯源、词面路命中更准 | 低（纯规则，无模型调用） | **立即做** |
| **P1 可选** | 父子双层索引（子块检索、父块生成） | 当前语料下父/子仅 1.9×，收益有限 | 中（索引 +69%、检索与生成链路改造） | **语料到百篇级再上** |
| **不做** | 语义/嵌入相似度切分、LLM 命题级切分、Late Chunking | 见 §7 取舍理由 | 高（10–50× 索引成本） | 成本收益不成立 |

### 0.4 推荐落地参数

| 参数 | 当前值 | 建议值 | 理由 |
|---|---|---|---|
| 目标块长 | 300 字 | **220–260 字** | 对齐「小节合并到目标长度」的自然粒度，仍在 256–512 token 甜区 |
| 硬上限 | 300 字 | **340 字** | 允许个别长小节略微超出，避免二次切碎 |
| 下限 | 40 字（`INDEX_MIN_CHUNK_CHARS`） | **60 字** | 低于此值与同章相邻小节合并 |
| 重叠 overlap | 60 字（20%） | **结构路径下 0**；降级递归路径保留 10–15% | 结构边界本身在自然语义边界上，无需字符级重叠修补；上下文归属由上下文头解决，更精准且零冗余 |
| 分隔符优先级 | `\n\n → \n → 。！？； → ， → 空格 → 空串` | **章锚点 → 节锚点 → 段落 → 句子 → 标点 → 空格 → 空串** | 当前分隔符不识别中文章节结构，是跨小节合并的直接原因 |
| 长度计量 | 字符（`len`） | **字符（保持）** | 中文 1 字 ≈ 1–1.5 token（bge-m3），字符计量可控且与 bge-m3 的 8192 上限无冲突；换模型时再切 token 计量 |

## 1. 现状盘点

### 1.1 当前实现链路

```
data/*.txt ──> doc_loader.load_all_documents()     # 支持 .pdf/.md/.markdown/.txt
           ──> L1 prepare.prepare_documents()      # 归一化 → 清洗 → 去重 → 元数据
           ──> L2 indexer.chunk_documents()        # RecursiveCharacterTextSplitter
                                                   #   + _merge_short_chunks()
           ──> indexer.index_chunks()              # 向量化 → 写入 + 词面倒排索引
```

关键实现细节（影响后续设计）：

- **切分器**：`RecursiveCharacterTextSplitter`，`length_function=len`（按字符计数）
- **短片段治理**：已有 `_merge_short_chunks()`，把 <40 字碎片向前合并，软上限 `300 × 1.3 = 390`。实测光杆标题 0 条，说明该逻辑**有效，应保留**
- **chunk_id**：`uuid5(source + sha1(content)[:16])`，内容哈希而非位置序号 —— 这是正确的增量语义设计，**必须保留**
- **去重**：L1 层字符级 Jaccard（阈值 0.95）+ 精确指纹去重

### 1.2 三个具体缺陷

**缺陷 1：跨小节主题混杂（主因）**

当前分隔符优先级为 `\n\n → \n → 。 → ！ → ？ → ； → ， → 空格 → 空串`。语料中小节间以 `\n\n` 分隔，切分器把相邻的「小节标题 + 正文」块贪心合并到 300 字，而单小节正文平均仅 78 字 —— 于是 **4 个小节被塞进一个片段**。

实测样本：

```
[IT支持指南 #4  243字] 3.3 邮件归档 / ...超期邮件将自动进入归档存储... /
                      四、办公设备 / 4.1 设备领用 / 新员工入职时由...
```

一个向量同时编码「邮件归档」「办公设备」「设备领用」三个主题，任何单一主题的问题都只能拿到一个被稀释的相似度分数。

**缺陷 2：切分尾段丢失章节归属**

4/26 片段不含任何标题。这些是长小节被 `。` 二次切分后的**后半段** —— 向量里既没有章节信息，前端溯源也显示不出来源位置。

**缺陷 3：无结构元数据**

当前元数据仅 `source / file_name / file_type / char_count / fingerprint / chunk_index / chunk_chars`。**没有章节路径**，因此：
- 无法做元数据过滤（例如「只在薪酬章节内检索」）
- 无法做章节级去重或版本对比
- 引用溯源只能显示文件名，不能显示「第三章 3.2 年休假」

## 2. 主流切分方案梳理

### 2.1 全景定位

按「复杂度 / 质量」曲线，主流方案分三档：

| 档位 | 方案 | 核心思路 | 索引成本倍数 |
|---|---|---|---|
| 基线 | 固定长度、递归字符 | 按长度 + 分隔符优先级机械切分 | 1× |
| 结构感知 | 标题/段落结构化、语义/嵌入相似度 | 用文档结构或语义突变点决定边界 | 1×（结构） / ~14×（语义，需逐句 embedding） |
| 上下文保持 | 父子块 / Small-to-Big、Late Chunking、LLM 命题级 | 解耦「检索单元」与「生成单元」 | 2–3×（父子） / 10–50×（LLM） |

### 2.2 逐类详解

#### （1）固定长度切分（Fixed-Size）

- **原理**：按固定字符/token 数硬切，可选重叠
- **适用**：日志、流水数据、无结构纯文本、基线对照
- **优点**：实现简单、索引规模可预测、速度最快
- **缺点**：在句子中间截断，语义残缺；对结构化文档破坏严重
- **参数**：`chunk_size`、`chunk_overlap`
- **业界评价**：Vecta/FloTorch 2026 基准中以 67% 准确率位列第二（512 tokens，带重叠）—— **作为基线并不差**，但前提是文本本身无结构

#### （2）递归字符切分（Recursive Character）

- **原理**：按**分隔符优先级列表**递归尝试（段落 → 行 → 句子 → 词 → 字符），尽量在自然边界切分
- **适用**：通用文本、绝大多数场景的默认起点
- **优点**：保留段落/句子完整性、纯字符串运算极快、无外部依赖
- **缺点**：仍是规则启发式，**不理解文档层级**；分隔符表不含结构锚点时，会把不同章节合并（本项目正是此问题）
- **关键参数**：
  - `chunk_size`：目标块长
  - `chunk_overlap`：相邻块重叠，取 `chunk_size × 10–20%` 为工程黄金区间
  - `separators`：**优先级列表，是这类方案最有价值的调优点**
  - `length_function`：**默认按字符计数，不是 token** —— 最常见的坑
- **业界评价**：Vecta/FloTorch 2026 基准冠军（512 tokens，69%）；NVIDIA 2024 基准 512–1024 最优。**胜在「块长可预测」而非「最聪明」**

> ⚠️ **字符 vs token 陷阱**：LangChain 的 `RecursiveCharacterTextSplitter` 默认 `length_function=len` 按字符计数。设 `chunk_size=512` 实际是 512 **字符**，约 128 英文 token —— 会静默低估真实 token 消耗。中文场景若换成按 token 计量，需改用 `from_tiktoken_encoder()` 或自定义 `length_function`。

#### （3）按标题/段落的结构化切分（Structure-Aware）

- **原理**：按文档原生结构（Markdown `#`/`##`、HTML 标签、章节编号、Q&A 对、代码函数）切分，元素超限才二次切分
- **适用**：技术文档、API 文档、产品手册、法律合同 —— **本项目正是此类**
- **优点**：块与文档逻辑单元对齐、结构信息可注入元数据、支持元数据过滤
- **缺点**：依赖文档结构质量；对格式混乱文档会退化到无结构
- **关键参数**：标题层级映射、单元素硬上限、是否继承父级标题
- **业界证据**：MDPI Bioengineering 2025 临床研究显示，对齐逻辑主题边界的自适应切分达 87% 准确率，固定长度仅 13%（医学文档，提升 74 个百分点）。**文档有结构时，结构感知与固定长度的差距是数量级的**

#### （4）基于语义/嵌入相似度的切分（Semantic Chunking）

- **原理**：先按句切分 → 逐句 embedding → 计算相邻句余弦相似度 → 在相似度骤降处切分
- **适用**：主题跳转明显的长文档（论文、长报告、访谈稿）
- **优点**：块内主题一致性最高，理论上检索质量最优
- **缺点**：
  - 需为**每个句子**调用 embedding，预处理成本是固定切分的 10–50 倍，速度约 14× 慢
  - **块长不可控**：易产生极小碎片
  - 对代码块/表格敏感（无句子边界，会打乱相似度计算）
- **关键参数**：`breakpoint_threshold_type`（percentile / standard_deviation / interquartile）、阈值、**必须设最小长度下限**
- **业界评价（重要反直觉结论）**：
  - Vecta/FloTorch 2026：语义切分 54%，**七种策略中垫底**。原因是产出的片段平均仅 43 tokens —— Chroma 测出其检索召回率 91.9% 为全场最高，但**片段太小，LLM 拿不到足够上下文，答案反而错**
  - Vectara NAACL 2025（该领域唯一同行评审论文）：固定长度在三项评测任务上**全面优于**语义方法
  - 实践经验：有团队用语义切分替换递归切分后，召回率**下降 8%**（技术文档中的代码块与表格破坏了句子相似度）

> 📌 **教训**：语义切分不是「更高级所以更好」。它优化的是「块内主题一致性」，却可能牺牲「块的信息完整性」，而后者的权重更高。**上线前必须在目标语料上 A/B 验证**。

#### （5）LLM 驱动的命题级切分（Proposition / Agentic Chunking）

- **原理**：用 LLM 把文本拆成**原子命题**（每条陈述一个独立事实，无代词指代），再按相关性聚合成块
- **适用**：高价值、低容量语料（法律条款、合规条文、核心产品知识）
- **优点**：检索粒度最细，指代消解彻底（不会出现「它的有效期是 90 天」这种脱离主语的片段）
- **缺点**：**成本最高、延迟最长**；严重依赖 LLM 能力与 prompt 质量；引入 LLM 幻觉风险到离线环节
- **业界评价**：Vecta 基准中「在某些任务上略有提升」，但考虑 10–50× 成本，性价比不成立。**仅在块长极不均、且预算充足时考虑**

#### （6）父子块 / Small-to-Big

- **原理**：解耦两个互相冲突的目标 ——
  - **子块（小）**：用于**检索**，定位精准
  - **父块（大）**：用于**生成**，上下文完整
  - 检索命中子块后，回填其父块给 LLM
- **适用**：层级清晰的结构化文档（手册、论文、API 文档、法律合同）
- **优点**：同时获得高召回精度与完整生成上下文；RAGFlow / Dify 均将其作为一等公民能力
- **缺点**：存储两份（父块可只存原文不建向量以节省）、链路复杂度上升、父子比设计不当会退化
- **关键参数**：
  - 父子粒度比：业界常见 `父 2000 tokens / 子 200–400 tokens`（约 5–10×）；RAGFlow 建议父块提至 1000–2000 tokens
  - Dify 父块模式：段落模式（`\n\n` 分隔，上限 500 tokens）/ 全文模式（整文档，上限 10000 tokens）
- **业界证据**：RAGFlow 官方举例 —— 用户问「违约责任」，子块精确命中「违约金为合同总额 20%」，但缺少「一般违约还是根本违约」的限定条件；回填父块后 LLM 才能准确判断

#### （7）附：Late Chunking（迟分块）

- **原理**：先用长上下文 embedding 模型对**整篇文档**编码，再从 token 级表示上切出各块向量
- **优点**：保留长程上下文，缓解「先切分导致上下文丢失」
- **缺点**：**依赖支持长上下文的 embedding 模型与配套索引方案**，框架支持度有限
- **建议**：方向有价值，但**基础 RAG 未跑稳时不引入**

### 2.3 横向对比矩阵

| 方案 | 语义完整性 | 块长可控性 | 实现复杂度 | 索引成本 | 适用文档 | 本项目适配度 |
|---|---|---|---|---|---|---|
| 固定长度 | ✕ | ★★★ | ★ | 1× | 无结构/日志 | ✕ 语料有清晰结构 |
| 递归字符 | ○ | ★★ | ★ | 1× | 通用文本 | ○ 作为降级路径 |
| **结构化（标题/章节）** | **★★** | **★★** | **★★** | **1×** | **手册/制度/FAQ** | **✓✓ 首选** |
| 语义相似度 | ★★★ | ✕ | ★★★ | ~14× | 主题跳转的长文档 | ✕ 成本收益不成立 |
| LLM 命题级 | ★★★ | ★ | ★★★★ | 10–50× | 高价值低容量 | ✕ 测试期不做 |
| 父子块 | ★★★ | ★★★ | ★★★ | 2–3× | 层级清晰的文档 | ○ P1，百篇级再上 |
| Late Chunking | ★★ | ★★ | ★★★★ | 高 | 长文档 + 特定模型 | ✕ 暂不引入 |

### 2.4 关键参数：怎么定

#### chunk_size

**核心权衡**：`块越小 → 向量语义越聚焦，检索精度越高，但上下文不足` / `块越大 → 上下文完整，但语义稀释，相关性得分下降`。

**业界收敛值**（多基准交叉验证）：

| 来源 | 结论 |
|---|---|
| Vecta/FloTorch 2026（7 策略 × 50 篇论文 × 90.5 万 tokens） | 递归 512 tokens 最优，69% |
| NVIDIA 2024（5 数据集） | 512–1024 tokens 最优；page-level 0.648 但仅适用分页文档 |
| Microsoft Azure | 推荐 512 + 25% overlap |
| Arize AI | 300–500 为速度/质量最佳平衡 |
| Redis/Pinecone | 64–128 tokens 利于事实型召回（recall@1 提升 10–15pp）；512–1024 利于宽泛问题 |
| 2025 多数据集分析 | 64–128 tokens 利于简练事实答案；512–1024 利于需要广上下文的任务；**最优值随 embedding 模型而变** |

**中文换算参考**：英文约 1 token ≈ 4 字符；中文约 1 token ≈ 1–1.5 汉字（BERT 系中文分词器接近 1 字 1 token，BPE 系更高效）。
→ **通用中文：500–800 字符；专业文档（法律/医疗/论文）：300–500 字符；FAQ/客服短文：200–400 字符。**

**本项目取值**：语料是「专业制度 + FAQ」，且 query 以事实型为主（「年假有多少天」「VPN 连不上怎么办」）→ 取 **220–260 字**（约 220–390 tokens），落在甜区内且偏事实型一侧。

#### chunk_overlap

- **作用**：防止关键信息被边界腰斩（例如「方案 A 总成本 230 万元，低于方案 B」恰好被切开）
- **推荐比例**：`chunk_size × 10–20%` 为工程黄金区间；结构清晰的文档可降至 10%；技术文档/代码可到 15–25%
- **超过 30% 的代价**：索引膨胀 40%+，Top-K 中大量重复内容，反而稀释有效信息密度（「换汤不换药」现象）
- **本项目的特殊结论**：采用**结构感知边界后，overlap 可以降到 0**。因为边界已落在章节/小节的天然语义边界上，不存在「切断一个完整论述」的风险。真正需要补的不是相邻字符，而是「这块属于哪一章」—— 用**章节路径上下文头**解决，比字符重叠更精准且零冗余。

#### 分隔符优先级（separators）

这是**递归类切分器最被低估的调优点**。默认 `["\n\n", "\n", " ", ""]` 是英文语感，中文和结构化文档必须定制：

| 场景 | 推荐优先级 |
|---|---|
| 英文通用 | `\n\n` → `\n` → `. ` → ` ` → `` |
| 中文通用 | `\n\n` → `\n` → `。` → `！` → `？` → `；` → `，` → ` ` → `` |
| **中文制度/手册（本项目）** | **章节锚点（`第X章` / `一、`）→ 小节锚点（`X.Y` / `Qn：`）→ `\n\n` → `\n` → `。！？；` → `，` → ` ` → ``** |
| 代码 | `\n\nclass ` → `\n\ndef ` → `\n\n` → `\n` → ` ` → `` |

### 2.5 反直觉结论：为什么简单方法常常赢

综合多个 2025–2026 基准，一个稳定出现的现象是：**递归/固定切分等"笨"方法，端到端准确率常常优于语义/命题等"聪明"方法**。

三个原因：

1. **块长可预测性** —— embedding 模型与检索器都是针对 256–512 token 区间优化的。块长一致时整条链路行为可预测；语义切分的块长方差极大（实测 43–2000+ tokens），检索器无法公平比较
2. **碎片化陷阱** —— 语义/命题方法产出 3–5× 的块数量。更多块 = 更多 embedding、更多存储、更多噪声。**高召回 ≠ 正确答案**：43 token 的片段能精准召回，但 LLM 拿它拼不出答案
3. **成本复利** —— 块数增加会在 embedding、存储、检索、重排每一层放大成本

> 📌 **给本项目的直接启示**：不要为了「看起来更先进」上语义切分。**先解决边界问题（结构感知），再谈更复杂的方案。**

## 3. 切分工具与库调研

### 3.1 先分清两类职责

## 4. 业界开源项目的共性经验

### 4.1 RAGFlow（工业级深度文档 RAG）

**切分模板（Task-Based Chunking）** —— 按文档类型选策略，而非一刀切：

| 模板 | 适用 | 切分逻辑 |
|---|---|---|
| General | 混合内容（默认） | 按标题感知切分，尊重段落边界 |
| Naive | 纯文本、简单文档 | 固定 token 窗口 + 重叠 |
| Paper | 学术论文 | 摘要/章节/参考文献分别处理（**自动剔除 References，避免关键词污染检索**） |
| Book | 长文档、手册 | 保留章节层级 |
| **Q&A** | **FAQ 内容** | **按问答对匹配，一对一块** |
| Table | 表格/CSV/XLSX | 行级粒度 |
| Resume | HR 简历 | 实体感知（姓名/技能/日期） |

**关键实践（v0.23+）**：

1. **语义沉降（Semantic Inheritance）**：Manual 模板下，即使叶子节点只有 50 字，也把其 `H1 → H2` 路径上下文**自动拼进 Chunk 元数据**，保证「无论被检索到何处，其概念边界和上下文都绝对完整」
2. **父子切分（Parent-Child Chunking）**：父块保完整语义单元，子块做精确召回；命中子块自动关联父块。开启后父块建议提至 **1000–2000 tokens**
3. **图片/表格上下文窗口**：图文在真实文档中常相伴，纯图/表 chunk 自己检索不到。取图表上下 N token 的文本一并入块（**边界按标点优化以保持语义连贯**）
4. **坐标回溯**：每个 chunk 绑定 `[page_num, x_min, y_min, x_max, y_max]`，引用时前端高亮定位 —— 「有据可查」
5. **检索侧协同**：BM25 `k1=1.6, b=0.75`；**标题字段 3 倍加权（`title^3`）**；dense 用 HNSW（M=16, ef_construction=200，召回 ≥98%）；RRF `k=60` 融合

### 4.2 Dify（通用 vs 父子分段）

| 维度 | 通用分段 | 父子分段 |
|---|---|---|
| 存储结构 | 独立扁平片段 | 树状层级（父块 + 子块） |
| 检索单元 | 分段本身 | 子块 |
| 返回 LLM | 命中的独立分段 | **子块关联的父块全文** |
| 上下文完整性 | ✕ 可能割裂跨片段逻辑 | ✓ 保留父子从属关系 |
| 父块模式 | — | 段落模式（`\n\n`，上限 500 tokens）/ 全文模式（上限 10000 tokens） |

**选型结论**：无层级短文本（新闻/评论）→ 通用；**强结构文本（手册/论文/API 文档）→ 父子**。

### 4.3 Unstructured（`chunk_by_title`）

- 先 `partition` 出元素（Title / NarrativeText / Table / ListItem…），再按标题合并
- 典型参数：`max_characters=1500`、`new_after_n_chars=1200`
- 更新优势：只需对变更文件重新 partition，**标题层级未变的块可复用**，更新范围可缩到 10% 以内

### 4.4 Anthropic Contextual Retrieval（上下文增强的权威依据）

给每个块用 LLM 生成 50–100 token 的上下文描述并前置，再做 embedding 与 BM25 索引：

| 配置 | Top-20 检索失败率 | 累计降幅 |
|---|---|---|
| 基线（仅 embedding） | 5.7% | — |
| + BM25 混合 | 5.0% | 17.5% |
| + 上下文嵌入 | 3.7% | 35% |
| + 上下文 BM25 | 2.9% | 49% |
| + 重排 | **1.9%** | **67%** |

> 📌 **对本项目最关键的一条**：**「给块补上下文」的收益（35%）大于「加 BM25」（17.5%）**。而本项目语料的章节标题是**结构化、免费、零延迟**的现成上下文 —— 无需调 LLM，直接用章节路径即可拿到这 35% 中的大部分。这是 P0 方案的核心依据。

### 4.5 提炼：六条共性经验

| # | 共性经验 | 本项目落地方式 |
|---|---|---|
| 1 | **按文档类型选切分模板，不一刀切** | 制度类（章节树）/ FAQ 类（Q&A 对）走不同切分路径 |
| 2 | **把结构路径写进块内容或元数据**（语义沉降） | 章节路径上下文头 + `heading_path` 元数据 |
| 3 | **表格/图片/代码单独成块，不跨块切**，并补周围文本 | 表格整表成块 + 标题/说明文本入块 |
| 4 | **标题字段在检索侧加权**（`title^3`） | 上下文头前置即等效加权，零改造 |
| 5 | **父子索引解耦「检索精度」与「生成上下文」** | P1 阶段再上 |
| 6 | **元数据要能支撑过滤与溯源**（页号/坐标/章节） | 扩展元数据字段（§5.5） |

## 5. 本项目完整切分策略

### 5.1 设计目标与约束

**目标**：

1. 消除跨小节主题混杂（当前 69% → 目标 < 10%）
2. 每个块都携带可溯源的章节归属（无标题块 4 条 → 0 条）
3. 支持章节级元数据过滤，为后续权限/时效过滤留扩展点
4. 保持增量入库幂等性（现有 `chunk_id` 内容哈希设计不变）
5. **不引入任何模型相关的硬编码**，解析/切分链路模型无关

**约束**：

- 语料以中文为主，无 PDF 表格等复杂版面（当前）
- 下游用途：**事实型问答为主**（制度查询、IT 故障排查），要求精确命中 + 引用溯源
- 检索链路已是 dense(0.7) + lexical(0.3) 双路 RRF 融合，Top-K=5，候选集 `min(max(5×4, 30), N)`
- 测试阶段模型会更换，**任何模型特定参数不得写死在切分链路**

### 5.3 阶段 0：预处理清洗（L1 增强）

现有 L1 已覆盖：NFKC 归一化、控制字符清除、页码/分隔线噪声、空白压缩、精确去重、Jaccard 近重复去重、元数据注入。**保留全部逻辑**，在此基础上增强：

| 新增项 | 处理 | 理由 |
|---|---|---|
| **文档头元数据抽取** | 从文档首部识别「标题 / 版本 / 生效日期 / 更新日期」 | 当前语料三篇都有明确的头块（`版本：V3.2 生效日期：2026-01-01`），是天然的过滤维度 |
| **结构锚点保护** | 清洗阶段**不得**破坏章节编号行的行首位置（`^第X章`、`^X.Y`、`^Qn：`） | 结构解析依赖行首锚点；空白压缩若把 `3.2 年休假` 与上文合并到同一行，锚点就失效了 |
| **列表/编号项保护** | `第一步、第二步` / `1) 2)` / `一是、二是` 等列举结构，优先整体保留 | 操作步骤类内容被切开会直接导致答案缺步骤 |
| **URL / 邮箱 / 主机名保护** | 不作为切分断点，且清洗时不拆行 | 语料含 `https://it.company.com`、`vpn.company.com` 等，被切断会生成错误指引 |
| **表格块识别（预留）** | Markdown 表格以整表为原子单元 | 引入 PDF/Word 后启用 |

### 5.4 阶段 1：结构感知切分（核心）

#### 5.4.1 层级识别规则

用**行首锚点正则**识别（模型无关、零成本），按优先级：

| 层级 | 识别模式（行首） | 语料示例 | 命中数 |
|---|---|---|---|
| L1 章 | `第[一二三四五六七八九十百]+章` 或 `^[一二三四五六七八九十]+、` | `第三章 假期管理`、`一、账号与密码` | 22 |
| L2 节 | `^\d+\.\d+` 或 `^Q\d+[：:]` | `3.2 年休假`、`Q8：知识库支持哪些文档格式？` | 80 |
| L3 条 | `^\d+[、.]` 或 `^[（(]\d+[）)]` | `第一步`、`（1）` | 少量 |

**降级判定**：若一篇文档中 L1/L2 锚点命中数为 0 → 标记 `structure="flat"`，回退到递归字符切分（保留 10–15% overlap）。**保证任何新文档格式接入都不会产出垃圾块。**

#### 5.4.2 切分算法（三步）

**Step 1 · 章节切分（硬边界）**
按 L1 锚点切分，**使用向前预查（lookahead）保留标题行本身**。跨章绝不合并。

**Step 2 · 节内合并（软边界）**
章内以 L2 节为原子单元，贪心合并：
- 累加到 **目标长度 220 字** 即停
- 但允许单个节把当前块撑到 **硬上限 340 字**（避免把长节二次切碎）
- 单节 > 340 字时，按句子（`。！？；`）二次切分，**切出的每一段都补上下文头**

**Step 3 · 上下文头拼接**
每个块的正文前置拼接：

```
{文档标题} > {章标题} > {节标题}
{正文}
```

示例：

```
IT支持指南 > 二、VPN 远程接入 > 2.3 VPN 常见故障
若提示"连接超时"，请检查本地网络是否正常...
```

#### 5.4.3 参数与实测验证

在真实语料上模拟该算法（`target=220, hard=340`）：

| 方案 | 块数 | 均值 | 中位 | 最小 | 最大 | <80字 | 跨章 | 索引膨胀 |
|---|---|---|---|---|---|---|---|---|
| **当前（递归 300/60）** | 26 | 250 | 260 | 74 | 296 | 1 | **18/26 跨小节** | 基准 |
| 纯按小节切（反例） | 80 | 78 | 86 | 6 | 167 | 34 | 0 | +208% |
| **结构感知 220/340** | **44** | **~152** | **~145** | **58** | **226** | **4** | **0** | **+69%** |

**读法**：
- 「纯按小节切」是**反面教材** —— 80 块、均值 78 字、34 块低于 80 字，正是 Vecta 基准中语义切分落败的同一个碎片化陷阱。**说明「结构感知」不等于「按最小结构单元切」，必须做长度治理**
- 结构感知 220/340 把跨章率降到 0，块长中位数 145 字（含上下文头后有效语义更完整），索引 +69% 是可接受代价

> ⚠️ 注意：模拟中「带标题开头 0/24」是 `CHAP.split` 吞掉了标题行的**脚本假象**，真实实现必须用 lookahead 保留标题。

#### 5.4.4 为什么 overlap 可以设为 0

传统 overlap 解决的是「**边界可能切断一个完整论述**」。结构感知切分下：
- 边界落在章/节/句的自然语义边界上，不会切断完整论述
- 需要补的不是「相邻几句话」，而是「这块属于哪一章」—— 由**上下文头**精准提供

字符级 overlap 的代价是**索引膨胀 + Top-K 内容重复**（业界观察：overlap > 30% 时检索结果「换汤不换药」）。用上下文头替代，零冗余且信息更准。

**降级路径（structure=flat）例外**：递归切分仍保留 10–15% overlap。

|---|---|---|---|---|
| `source` | 块 | ✓ | 现有 | 溯源、增量删除（`delete_by_source`） |
| `file_name` | 块 | ✓ | 现有 | 前端展示 |
| `file_type` | 块 | ✓ | 现有 | 解析策略选择 |

| `doc_title` | 文档 | ✓ | 文档头抽取 | 上下文头首段、前端溯源 |
| `doc_version` | 文档 | 推荐 | 文档头抽取（`版本：V3.2`） | 版本对比、过期标注 |
| `doc_effective_date` | 文档 | 推荐 | 文档头抽取（`生效日期：2026-01-01`） | **时效过滤**（制度类文档的核心过滤维度） |

1. **元数据是检索期的过滤维度，不是装饰** —— 每个字段都要能回答「我什么时候会用它过滤」
2. **父子索引的 `parent_id` 与 `chunk_role` 标为 P1**，避免现在就背上复杂度
3. **PDF 相关字段预留但不实现**，引入 PDF 时一次到位

### 5.6 特殊元素处理

| 元素 | 当前语料 | 处理策略 | 依据 |
|---|---|---|---|
| **表格** | 无（预留） | **整表成块**，不跨块切；表头在切分后**重复**到每块；表上方标题/说明文本一并入块 | Docling HybridChunker 的「表头重复」实践；RAGFlow 的图文上下文窗口 |
| **代码块 / 配置片段** | 无（预留） | 按函数/类边界切（AST 或缩进），不按字符切 | 代码被切一半即语法无效，比不召回更糟 |
| **图片** | 无（预留） | 图片本身不建向量；**取上下 N token 的说明文本作为其检索代理** | RAGFlow v0.23 图文上下文窗口；扫描件需先 OCR |
| **列表/步骤** | 有（`第一步、第二步`） | **整体保留**，不拆分；整体超限时在列表项边界切，且补上下文头 | 操作步骤被切开 = 答案缺步骤 |
| **Q&A 对** | 有（`Qn：`） | **一问一答为一个原子单元**，Q 与 A 不分离；Q 文本进上下文头 | RAGFlow 的 Q&A 模板；Dify FAQ 场景建议「200 词答案切成 3 段注定缺上下文」 |
| **长句/长条款** | 有 | 按句二次切时，**后段必须补上下文头**，避免「无头片段」 | 当前 4/26 无标题片段的根因 |
| **扫描件 PDF** | 无（预留） | 先 OCR（Docling/MinerU），OCR 置信度低的块打 `low_confidence` 标记 | 低质量 OCR 文本进索引是噪声源 |
| **页眉页脚/水印** | 已有处理 | 保持 L1 现有清洗逻辑（页码行、分隔线正则） | 已验证有效 |

### 5.7 阶段 2：父子双层索引（P1）

**触发条件**（满足任一即启动）：
- 语料扩展到 **100 篇以上**，或单篇文档超过 **5000 字**
- 评测中出现「片段命中正确但答案不完整」的案例占比 > 20%

**设计**：

| 项 | 取值 | 理由 |
|---|---|---|
| 子块（检索单元） | 结构感知切分产物（均值 ~152 字） | 精确召回 |
| 父块（生成单元） | **章级**（均值 288 字，最大 525） | 语义完整 |
| 父子比 | **实测 1.90×** | 见下方取舍说明 |
| 父块是否建向量 | **否**，仅存原文 | 节省索引；父块通过 `parent_id` 回填 |
| 索引膨胀 | 子块 +69%（父块不入向量） | 可接受 |

> ⚠️ **诚实评估**：业界推荐父子比约 5–10×（父 2000 / 子 200–400 tokens）。本项目语料的章本身就很短（均值 288 字），父子比只有 **1.90×** —— **当前语料下父子双层的收益有限，这是不建议现在就上的核心原因**。语料扩展到长文档（单章 > 800 字）后，父子比自然拉大，收益才会显现。

**与现有检索链路的对接点**：
- `retrieve()` 返回子块后，按 `parent_id` 批量取父块
- 生成阶段（`build_context`）用父块组装上下文，**引用编号仍指向子块**（精确定位 + 完整上下文兼得）
- 词面倒排索引**只建子块**（短子块对 BM25 精确匹配更有利）

### 5.8 chunk_id 与增量一致性

**保持现有的内容哈希 ID 设计**：`chunk_id = uuid5(source :: sha1(content)[:16])`。

该设计已解决业界最常见的「边界偏移雪崩」问题：位置型 ID 在文档前插一段后会导致后续所有块 ID 变化，本应不变的块被误删重写。**内容哈希让「内容未变的块」ID 稳定。**

**增量策略**：

| 场景 | 处理 |
|---|---|
| 单文档更新 | `delete_by_source` 全清该 source → 重新切分写入（现有 `add_document` 逻辑，保持） |
| 判断是否需要重建 | 文档级 `fingerprint` 比对，未变则跳过 |
| IDF 重算 | 全量建索引时 `refit_idf=True`；增量时 `False`（现有逻辑，保持） |

> 📌 若后续上父子索引，父块 ID 建议同样基于内容哈希，子块 `parent_id` 指向父块 ID —— 这样父块内容未变时，子块的关联关系也保持稳定。

### 5.9 配置化清单

所有参数走 `config.py` + `.env`，**不写死模型相关值**：

| 配置项 | 建议默认值 | 说明 |
|---|---|---|
| `CHUNK_TARGET_CHARS` | `220` | 结构感知切分的目标块长 |
| `CHUNK_HARD_MAX_CHARS` | `340` | 硬上限，超出才按句二次切 |
| `CHUNK_MIN_CHARS` | `60` | 下限，低于此值与同章相邻节合并 |
| `CHUNK_TARGET_TOKENS`（预留） | `None` | 换模型后可切 token 计量 |
| `CHUNK_CONTEXT_HEADER` | `true` | 是否注入章节路径上下文头 |
| `CHUNK_FALLBACK_OVERLAP_RATIO` | `0.12` | 降级递归路径的 overlap 比例 |
| `STRUCTURE_CHAPTER_PATTERNS` | 见 §5.4.1 | 章锚点（可扩展为配置文件） |
| `STRUCTURE_SECTION_PATTERNS` | 见 §5.4.1 | 节锚点 |
| `INDEX_MIN_CHUNK_CHARS` | `60`（现 40） | 短片段治理阈值 |
| `PARENT_CHUNK_ENABLED` | `false` | P1 父子索引开关 |

## 6. 质量评估方法

### 6.1 离线块质量指标（切分后立即算）

| 指标 | 计算方式 | 目标值 | 现状 |
|---|---|---|---|
| **块长分布** | 各区间的块数占比 | 80% 落在 100–300 字；**< 80 字的块 ≤ 5%** | 当前 1/26 低于 80 字 ✓ |
| **块长离散度** | 标准差 / 均值 | **< 0.6** | 当前 ~0.35 ✓ |
| **结构纯度** | 含 ≥2 个不同小节标题的块占比 | **≤ 10%** | 当前 **69%** ✗ |
| **无归属率** | 不含任何章节标题且无上下文头的块占比 | **0%** | 当前 **15%（4/26）** ✗ |
| **空块/噪声块率** | 去空白后长度 < 10 字的块占比 | **0%** | 当前 0% ✓ |
| **重复块率** | 块内容精确重复数 / 总块数 | **≤ 2%** | 当前 0% ✓ |
| **索引膨胀率** | 新方案块数 / 基线块数 | **≤ 2.0×** | 目标方案 1.69× ✓ |

> 📌 **结构纯度**是本方案最关键的一个指标，也是当前最大的短板（69%）。它是「主题混杂」的直接量化。

### 6.2 检索命中率验证（核心验收指标）

复用现有 L5 评估层（`app/rag/evaluator.py` + `app/rag/eval_cases.yaml`），指标为 `hit_rate` 与 `MRR`。

**Step 1 · 扩充评测集**（当前仅 4 条，统计意义不足）

目标：**30–50 条**，覆盖：

| 类别 | 示例 | 建议条数 |
|---|---|---|
| 制度查询（数值型） | 年假有多少天 / 产假多少天 / 加班费怎么算 | 10 |
| 流程查询（多步骤） | 报销流程怎么走 / VPN 怎么连接 | 8 |
| 故障排查 | VPN 连接超时怎么办 / 密码锁定了解除 | 8 |
| 产品 FAQ | 知识库支持哪些格式 / 私有化部署要求 | 6 |
| **跨章节推理** | 试用期转正需要哪些条件（涉及 1.2 + 转正评审） | 5 |
| **应拒答** | 公司股价是多少（知识库外） | 5 |

**评测集字段**（现有 `EvalCase` 已支持）：

- `question`
- `expect_keywords`（Top-K 中任一片段包含任一即命中）
- `expect_source`（限定来源文件）
- **建议新增 `expect_section`**（限定章节）—— 有了 `heading_path` 元数据后，可把「命中正确章节」也作为判定条件，**精度高于关键词匹配**

**Step 2 · A/B 实验流程**

固定其他变量（embedding、检索权重、Top-K、prompt），只切换切分策略：

| 组 | 配置 |
|---|---|
| 基线 A | 递归 300/60（当前） |
| 实验 B | 递归 300/60 + 仅加上下文头（**隔离上下文头的独立贡献**） |
| 实验 C | 结构感知 220/340（不加上文头） |
| **实验 D** | **结构感知 220/340 + 上下文头（推荐方案）** |

每组跑全量评测集，记录 `hit_rate` / `MRR@5` / 平均块长 / 块数。

**Step 3 · 参数敏感性扫描**（在推荐方案上微调）

- 目标块长三档：`180 / 220 / 280`
- 硬上限三档：`300 / 340 / 400`

**关键**：**固定 overlap=0**（结构路径下），如检索指标明显劣化再考虑加回。

### 6.3 生成质量验证（避免「高召回错答案」陷阱）

Vecta 基准的核心教训是：**召回率高不等于答案对**。因此必须同时看生成端指标。现有 `evaluator.py` 已提供：

| 指标 | 现有函数 | 作用 |
|---|---|---|
| `score_faithfulness` | ✓ | 答案是否忠于上下文（幻觉检测） |
| `score_citation_coverage` | ✓ | 引用覆盖率（能否溯源） |
| `hit_rate` / `MRR` | ✓ | 检索命中质量 |

**新增观察项**：

- **答案完整率**：人工抽检 20 条，判断答案是否包含全部关键步骤（针对流程类问题）
- **拒答准确率**：应拒答的 5 条是否被正确拒绝（切分变细后，拒答阈值可能需要重新校准）

### 6.4 线上监控

| 信号 | 来源 | 异常判据 |
|---|---|---|
| 引用覆盖率 | `score_citation_coverage` | 覆盖率下降 → 检索到的块与答案不匹配，可能是切分过细 |
| 拒答率 | 生成层 `refused` 标记 | 拒答率突增 → 块变细导致置信度下降，需下调拒答阈值 |
| 用户反馈 | `record_feedback` / `feedback_stats` | 负反馈集中在某类问题 → 定位到具体章节的切分 |
| 块长分布漂移 | 索引统计 | 新增文档后分布偏离 → 新文档结构未识别（`structure=flat` 占比上升） |

### 6.5 验收阈值（明确门槛）

| 指标 | 门槛 | 否则 |
|---|---|---|
| 结构纯度（跨小节率） | ≤ 10% | 未达标，检查锚点正则 |
| 无归属率 | 0% | 未达标，上下文头逻辑有漏 |
| `hit_rate` | **不低于基线 A**（至少持平） | 回滚 |
| `MRR@5` | 相对基线 **提升 ≥ 5%** | 检查是否切分过细 |
| `score_faithfulness` | 不低于基线 | 回滚 |
| 索引膨胀 | ≤ 2.0× | 调高目标块长 |

## 7. 取舍理由

### 为什么不做语义/嵌入相似度切分

1. **成本**：需为**每个句子**调用 embedding，预处理成本 10–50×，速度约 14× 慢
2. **效果证据相反**：Vecta/FloTorch 2026 中语义切分 54% **垫底**；Vectara NAACL 2025（该领域唯一同行评审论文）中固定长度**全面优于**语义方法
3. **失败机制明确**：语义切分产出平均 43 tokens 的碎片 —— 召回 91.9% 全场最高，但 **LLM 拿不到足够上下文，答案反而错**
4. **本项目的替代方案更优**：语料有**免费、精确、零延迟**的结构信号（章节编号），语义相似度是在用昂贵的方式推测一个已经写在那里的答案

### 为什么不做 LLM 命题级切分

1. 成本 10–50×，且**测试阶段模型会更换** —— 换模型意味着命题切分结果不可复现，索引一致性受损
2. 把 LLM 幻觉风险引入离线索引环节，与「可溯源」的设计目标冲突
3. Vecta 基准显示其收益「marginal」

### 为什么不做 Late Chunking

依赖支持长上下文的 embedding 模型与配套索引方案，框架支持度有限。**基础 RAG 未跑稳时不引入** —— 本项目的检索命中率基线尚未建立（评测集仅 4 条），此时引入无法验证收益。

### 为什么 overlap 可以降到 0

见 §5.4.4。核心：结构感知边界已落在自然语义边界上，上下文归属由**上下文头**解决比字符重叠更精准且零冗余。**降级路径仍保留 10–15% overlap。**

### 为什么 P1（父子）现在不上

父子比仅 **1.90×**（业界推荐 5–10×），收益有限；成本是索引 +69% + 检索/生成链路改造。**等语料中有长文档（单章 > 800 字）后再上，届时父子比自然拉大。**

### 风险与回滚

| 风险 | 影响 | 缓解 |
|---|---|---|
| 锚点正则漏识别（新文档格式不同） | 退化为 flat，走递归路径 | 降级路径已设计；监控 `structure=flat` 文档占比 |
| 上下文头稀释向量语义 | 短块中标题占比过高 | 上下文头**不参与** `chunk_chars` 计量；A/B 验证（实验 C vs D） |
| 块变细导致置信度下降、拒答率上升 | 正常问题被拒答 | 监控拒答率，必要时下调拒答阈值 |
| 索引膨胀 69% | 检索耗时上升 | 当前 44 块规模可忽略；到万级再评估 |

**回滚策略**：所有改动由 `CHUNK_*` 配置项控制，**关闭配置即可回到递归路径，无需改代码**。
