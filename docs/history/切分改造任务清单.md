### 1.2 逐个评估：适用场景 / 可借鉴 / 不适用原因

#### A. LangChain 包拆分
- **适用场景**：单体包需要按「抽象 vs 实现」分层，且外部有大量 `from X import Y` 调用点。
- **可借鉴**：
  - **薄兼容层（thin re-export）**：切断依赖后，旧导入路径仍指向新实现（`langchain.chat_models.ChatOpenAI` → 条件导入 `langchain_community`）。改造期间调用方零感知。
  - **依赖方向单向下行**：新层只依赖更抽象的层，绝不反向。
  - **弃用有明确时间表**：不是「先删再说」，而是 emit 警告 → 下个 major 才移除。
- **不适用于本项目的原因**：本项目是单仓库单体应用（~40 文件），不发包、无外部调用方，包级拆分是过度设计。只需借鉴其**兼容层与依赖方向**，不做包拆分。

#### B. Pydantic v1→v2 ⭐ 推荐
- **适用场景**：改造必须保证对外接口与现有行为不变，且希望分批推进、随时可停。
- **可借鉴（本项目直接采用）**：
  - **声明式迁移映射**（`pydantic/_migration.py`，已核实源码）：把「旧路径 → 新路径」落成 4 类字典 —— `MOVED_IN_V2`（搬迁）/ `DEPRECATED_MOVED_IN_V2`（搬且弃用）/ `REDIRECT_TO_V1`（无对应，重定向到旧实现）/ `REMOVED_IN_V2`（明确移除并给出解释）。**本项目元数据字段演进直接照搬这个四分类**。
  - **双命名空间共存**：新旧实现同时可用，新旧索引可同时构建 → 天然支持 A/B 影子对比。
  - **分批迁移**：先整体切到 `pydantic.v1`（行为不变），再逐批把模型迁到 v2。**本项目对应：先整体切到「策略注册表 + recursive 策略」（行为零变化），再逐个启用新策略。**
  - **自动 codemod**：机械化替换用工具，不手改。
- **不适用于本项目的原因**：`bump-pydantic` 这类 codemod 工具对 40 文件的项目收益不大，手工改更可控；且本项目无类型系统迁移，不需要「V1/V2 模型不可混用」的强边界。

#### C. LlamaIndex v0.10 拆分
- **适用场景**：集成数量爆炸、依赖冲突严重、需要按需安装。
- **可借鉴**：**冻结 legacy 快照用于对照** —— `llama-index-legacy` 钉死在 0.9.48，任何时刻都能切回去做 A/B 对比。**本项目对应：冻结一份「基线切分产物快照」作为回归基准（见 Phase 0 T0-2）**。
- **不适用于本项目的原因**：拆到 700+ 独立包、跨仓库命名空间、自研 CLI codemod —— 规模比本项目大两个数量级，照搬是严重的过度工程。**只取「冻结基线」一个点。**

#### D. Haystack 预处理组件化 ⭐ 推荐
- **适用场景**：同一环节存在多种可替换算法，需要按配置选择、逐个演进。
- **可借鉴（本项目直接采用，同构度最高）**：
  - **策略目录化**：11 个切分器各自独立模块 + `_import_structure` 声明式注册表 + `LazyImporter` 按需加载。本项目照此建立 `app/rag/chunker/` 策略目录。
  - **三参数同构**：Haystack `DocumentSplitter(split_by=..., split_length=200, split_overlap=0, split_threshold=0)`（已核实源码）—— `split_length` / `split_threshold` / `split_overlap` **与本项目设计的 `CHUNK_HARD_MAX_CHARS` / `CHUNK_MIN_CHARS` / overlap 完全同构**，验证了我们「目标块长 + 硬上限 + 下限」三参数设计是行业通行做法，不是自创。
  - **`split_by` 单元枚举**：page/passage/period/word/line/sentence/token —— 说明「切分单元」应作为一等配置项。
- **不适用于本项目的原因**：Haystack 2.0 整体是**破坏式重写**（`farm-haystack` → `haystack-ai`，两版本不能共存），这正是本项目要避免的路径 —— **只取其目录与策略组织方式，不取其大版本重写式迁移**。

### 1.3 推荐参考（Top 3）及理由

| 排序 | 案例 | 为什么最值得参考 |
|---|---|---|
| **1** | **Pydantic v1→v2** | 唯一一套「**对外接口全程不变 + 分批迁移 + 随时可停**」的完整机制。其声明式迁移映射（四分类）可以直接搬来管理本项目元数据字段的演进；「先整体切到兼容层、再逐批迁移」的两步法，正是本项目 Phase 2→Phase 3 的设计蓝本。 |
| **2** | **Haystack 预处理组件化** | **与本项目改造对象同构度最高**（都是文档切分）。其策略目录 + 声明式注册表 + `split_length/split_threshold/split_overlap` 三参数，几乎就是本项目要建的东西的现成答案。且规模适中（组件级而非包级），可直接照搬。 |
| **3** | **LangChain 包拆分** | 提供「**薄兼容层 + 依赖方向单向下行 + 弃用有明确时间表**」三件套。本项目 `app/providers/` 抽象层重构**已经用过同一手法**（旧文件改为 re-export 薄兼容层），沿用可保证代码风格一致、团队认知一致。 |

**明确不推荐照搬**：LlamaIndex 的多包拆分与 CLI codemod（规模不匹配）、Haystack 2.0 的破坏式大版本重写（违反「行为不变」约束）。

### 3.2 基线快照（实测，作为改造前后的唯一对照）

```
输入：12 个文件 → 13 条记录（PDF 计 2 页）
产出：124 个 chunk

块长分布：mean=238  median=246  min=42  max=298
落在 [150,350] 字：117/124 = 94%
< 80 字的碎片块：4 个

跨小节合并率：98/124 = 79%   ← 核心问题（设计文档原记录 69%，语料扩充后恶化）
块首 40 字内有章节锚点（有归属）：101/124 = 81%
```

**问题实证**（第 2 个 chunk 的实际内容，跨了章边界）：

```
'1.3 密码重置\n忘记密码时...域账号连续输错 5 次将被锁定 30 分钟。\n\n
 二、VPN 远程接入\n\n            ← 跨到了下一章
 2.1 VPN 申请\n因出差或居家办公...'      ← 又跨了一节
```

一个 chunk 里塞进了 `1.3`（一章内的小节）+ `二、`（下一章）+ `2.1`（下一章的小节）—— 这正是向量语义被稀释、检索命中后答案张冠李戴的直接来源。

> **注意**：设计文档 v1.0 写的「69%」和「26 个 chunk」是在**旧 3 文件语料**上测的。语料扩充后绝对数值已变，**本清单所有验收门槛一律以 §3.2 的实测基线为准，不再引用 v1.0 数字**。

## 5. 详细任务卡

### Phase 0 · 前置（v1.0 完全缺失，必须最先做）

---

#### T0-1 · 无 git 安全网：文件级备份 + 变更登记
> **约束变更（用户确认）**：本项目**不接 git、不上传远端**（2026-09-07）。因此「独立提交并回退」无法依赖 `git revert`，必须换一套等价保障。

- **目标**：在没有版本控制的前提下，为后续每个任务提供「可回退 + 可追溯」的等价能力。
- **涉及文件**：新建 `scripts/backup.sh`、新建 `artifacts/backup/`、新建 `CHANGELOG-chunking.md`
- **改造步骤**
  1. `scripts/backup.sh <task-id>`：把将要改动的文件按 `artifacts/backup/<task-id>/<原路径>` 原样拷贝一份（保留目录结构）
  2. `CHANGELOG-chunking.md` 登记每次变更：任务号 / 改动文件 / 改动摘要 / 验证命令 / 结果
  3. **三层回退保障**（缺一不可）：
     | 层 | 手段 | 覆盖场景 |
     |---|---|---|
     | L1 | **配置开关**（`CHUNK_*`） | 新逻辑有问题 → 关开关立即恢复 |
     | L2 | **文件级备份**（`artifacts/backup/`） | 改动本身有 bug → 拷回原文件 |
     | L3 | **基线护栏**（T0-2） | 静默行为漂移 → 测试失败告警 |
- **验收标准**：`scripts/backup.sh T1-1` 能把 `app/config.py` 拷到 `artifacts/backup/T1-1/app/config.py`；`CHANGELOG-chunking.md` 有登记模板。
- **风险**：备份目录忘了同步更新 → 在每次改动**之前**执行备份，写入任务卡固定流程。
- **回退**：备份是纯新增，删除即可；因不改业务代码，零业务风险。
- **独立验证**：`bash scripts/backup.sh T0-1 && find artifacts/backup -type f | head`

> ⚠️ **因为失去了 git，T0-2 的基线护栏重要性从「重要」升级为「唯一自动化回归检测手段」**，不可跳过。

---

#### T0-2 · 基线快照与回归护栏
- **目标**（借鉴 LlamaIndex 冻结 `llama-index-legacy`）：把改造前的产物**冻结为可复现的基准**，任何时刻都能切回去对照。这是后续所有 A/B 的对照组。
- **涉及文件**：新建 `scripts/baseline_snapshot.py`、新建 `tests/test_chunking_baseline.py`、新建 `artifacts/baseline_chunks.json`（提交入库）
- **改造步骤**
  1. `scripts/baseline_snapshot.py`：跑完整 `load → prepare → chunk`，输出 JSON（每块的 `source` / `chunk_index` / `chunk_chars` / `content_sha1` / `chunk_id`）
  2. 生成 `artifacts/baseline_chunks.json` 并提交
  3. `tests/test_chunking_baseline.py` 断言基线关键指标：块数 = 124、`content_sha1` 集合与快照一致、跨小节率 = 79%（±2pp）、块长 mean = 238（±10）

- **成本现实（已核实）**：`.env` 配了 `EMBEDDING_API_KEY` → `USE_REAL_EMBEDDING=True` → 走真实 bge-m3（SiliconFlow）。**每组的成本 = 1 次全语料 `embed_documents`**（查询向量有缓存 `EMBEDDING_CACHE_QUERY_TTL=600`，跨组可复用）。
- **⚡ 优化：两阶段 + 提前停止**（把 9 次全量评测压到 2 次）
  - **阶段 1（零 API 成本，秒级）**：对全部候选配置算**纯结构指标** —— 跨节率 / 块长分布 / 块数 / 归属率。**不建索引、不调 embedding**，纯 Python 字符串统计。

    3. 只有 D > A 达标时，才补跑 B / C 做归因（隔离「上下文头」与「结构感知」的独立贡献）
  - **收益**：最坏情况 4 次全量 → 最好 2 次；参数扫描 9 组全量 → 2 组全量（见 T4-3）

  | **D** | structure + 上下文头 | 推荐方案 | 2（必跑） |
  | **B** | recursive + 仅上下文头 | 隔离「头」的贡献 | 2（条件） |
  | **C** | structure（不加上文头） | 隔离「结构」的贡献 | 2（条件） |

  | 数值型制度查询 | 抽 5 条 | 最容易因切分变细丢数字 |
  | 多步骤流程查询 | 抽 3 条 | 最容易因跨节被截断 |
  | 跨章节推理 | 抽 2 条 | 检验上下文头是否真正生效 |
  - 合计 **15 条**（对比 A / D 两组 = 30 次 LLM 调用，而非 60+ 次）
- **改造步骤**：对比 A / D 两组的 `faithfulness` / `citation_coverage`；人工抽检答案完整率；5 条拒答用例的拒答准确率。
- **验收标准**：faithfulness / citation_coverage 不低于 A 组；**拒答准确率 5/5**；若任一层劣化则扩大该层到全量复测。
- **风险**：块变细 → 单块信息量下降 → 置信度降低、拒答率上升 → 若发生，下调拒答阈值并**只在该层**复测。
- **回退**：`artifacts/backup/T4-4/` 拷回阈值相关文件。

### 8.1 本轮优化清单（相对 v2.0 初稿）

| # | 优化点 | 优化前 | 优化后 | 收益 |
|---|---|---|---|---|
| **O1** | **去掉 git 依赖** | T0-1 建 git 仓库 | 文件级备份 + 变更登记 + 三层回退（配置 / 备份 / 护栏） | 契合实际约束；三层保障比单纯 git 更贴合「随时可停」 |
| **O2** | **参数扫描与评测解耦** | 9 组网格 × 全量检索评测 | 9 组只算**零成本结构指标** → 筛 1–2 个候选才跑全量评测 | **全量评测 9 次 → 1–2 次** |
| **O3** | **A/B 提前停止** | 固定跑 4 组 | 先跑 A/D；**D 无增益则跳过 B/C** | 全量评测 **4 次 → 2 次**（最好情况） |
| **O4** | **生成端分层抽样** | 全量 30+ 条 × 2 组 ≈ 60+ 次 LLM | 按信息量分层抽 15 条（拒答 5 条**全留**）≈ 30 次 | **LLM 调用减半，高危用例仍全覆盖** |
| **O5** | **回退手段去 git 化** | 多处 `git revert` | 统一改为 `artifacts/backup/<task-id>/` 拷回 | 与 O1 配套，全文已无 git 残留 |

**成本对比（全量评测次数是唯一烧配额的环节）**

```
优化前：T4-2 四组(4) + T4-3 九组(9) + T4-4(30+ LLM)  ≈ 13 次全量 + 60 次 LLM
优化后：T4-2 两组(2~4) + T4-3 候选(1~2) + T4-4(15 LLM) ≈ 3~6 次全量 + 30 次 LLM
                                                        ↓ 约降低 60~70%
```

**为什么阶段 1 的「结构指标」可以不花钱**：跨节率 / 块长分布 / 碎片率 / 归属率 / 膨胀比**全部是纯字符串与正则统计**，不需要 embedding、不需要索引、不需要 LLM，秒级可跑完 9 组。它们足以筛掉明显不合适的参数（例如碎片率爆表或膨胀超 2×），只有进入决赛的候选才值得付费用检索指标去区分。
