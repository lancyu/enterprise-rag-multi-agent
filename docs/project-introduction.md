## 一、这个项目是什么

### 1.1 一句话定位

一个**企业内部的智能问答服务**：员工用自然语言提问（"年假有多少天""报销流程怎么走"），
系统从企业自己的制度文档里找到依据，再让大模型**带着出处**给出回答；
找不到依据时**老实说找不到**，而不是编一个。

### 1.2 它想解决的三个真问题

| 问题 | 普通做法的问题 | 本项目的做法 |
|---|---|---|
| 大模型不知道公司内部规定 | 直接问模型 → 一本正经胡说 | **RAG**：先检索公司文档，再让模型照着回答 |
| 回答没有出处，不敢信 | 只能靠感觉判断真假 | **引用编号**：每句话标注 `[1][2]`，可点回原文档 |
| 模型不会说"我不知道" | 硬编一个答案 | **置信度拒答**：证据不足直接说"知识库没找到" |

### 1.3 核心技术栈

| 层次 | 选型 | 说明 |
|---|---|---|
| Web 框架 | **FastAPI** | 异步、自带 OpenAPI 文档 |
| 工作流引擎 | **LangGraph** | 把问答拆成 8 个节点组成的有向图 |
| 大模型 | **OpenAI 兼容协议**（默认 Moonshot / Kimi） | 换供应商只改 `.env` |
| 向量检索 | **Milvus** / **Chroma** / 内置内存库 | 三后端可切（`VECTOR_DB_TYPE`），默认内存库零依赖即可跑 |
| 词面检索 | **自研 BM25 倒排索引** | 不引入 Elasticsearch，250 行搞定 |
| 缓存/会话 | **Redis**，不可用时降级进程内内存 | 保证任何环境都能启动 |

## 二、整体架构

### 2.1 分层总览

```
┌─────────────────────────────────────────────────────────────┐
│  ① 接口层        app/api/            8 个 router，收 HTTP 请求 │
├─────────────────────────────────────────────────────────────┤
│  ② 编排层        app/graph/          LangGraph 8 节点有向图    │
├─────────────────────────────────────────────────────────────┤
│  ③ 调度层        app/core/           意图路由 / 模型选型 / 级联 │
├─────────────────────────────────────────────────────────────┤
│  ④ RAG 五层      app/rag/            准备→索引→检索→生成→评估  │
├─────────────────────────────────────────────────────────────┤
│  ⑤ 能力层        app/providers/      大模型 / 向量 / 精排      │
│                  app/db/             向量库 / Redis           │
│                  app/memory/         长短期记忆                │
│                  app/tools/          员工 / 假期余额查询       │
│                  app/utils/          加载 / 缓存 / 校验 / 日志  │
└─────────────────────────────────────────────────────────────┘
                          ▲
                          │ 全局配置：app/config.py（718 行）
                          │ 贯穿所有层：app/core/tracing.py（全链路 span 树）
```

**为什么要分这么多层？** 核心目的是**可归因**：
用户说"答得不对"，你能立刻判断是**语料脏**（L1）、**切片差**（L2）、
**召回错**（L3）、**模型胡说**（L4）还是**指标没测出来**（L5）——
而不是把整个系统当成一个黑盒瞎调。

### 2.2 一次请求的完整生命周期（带行号）

以 `POST /chat/ask` 问「年假有多少天？」为例：

| 步骤 | 做什么 | 代码位置 |
|---|---|---|
| 1 | 生成 trace_id、鉴权、按 IP 限流 | `app/main.py` |
| 2 | 进入问答接口，解析请求体 | `app/api/chat.py` |
| 3 | 按用户身份算出可访问的文档白名单 | `app/core/source_acl.py` |
| 4 | 从 Redis 取最近 10 轮对话历史 | `app/memory/chat_history.py` |
| 5 | **启动 LangGraph 工作流** | `app/graph/workflow_graph.py` |
| 5.1 | 节点① `memory_load` —— 加载长期记忆与多轮历史，注入后续提示词 | `app/graph/nodes.py` |
| 5.2 | 节点② `router` —— **路由 Agent**：一次模型调用判定场景（五选一），越界就地拦下 | `app/core/router_agent.py` |
| 5.3 | 条件边 —— 按场景分发，五路互斥 | `app/graph/edges.py` |
| 5.4 | 节点③④⑤⑥ —— 五个子 Agent 中的某一个执行（见 §2.4） | `app/core/sub_agents.py` / `tool_agent.py` |
| 5.5 | 节点⑦ `generate_answer` —— 受控生成（引用 + 置信度 + 拒答） | `app/rag/generator.py` |
| 5.6 | 条件边 + 节点⑧ `human_fallback` —— 异常才转人工 | `app/graph/edges.py` → `app/graph/nodes.py` |
| 6 | 结束 trace，把 span 树落盘 `logs/trace.jsonl` | `app/core/tracing.py` |
| 7 | 保存本轮两条消息到 Redis | `app/memory/chat_history.py` |
| 8 | 若历史过长，压缩归档（异步不阻塞响应） | `app/memory/__init__.py` |

> 另有流式接口 `POST /chat/ask/stream`（`app/api/chat.py`），逐 token 以 SSE 推送。
> 它 **invoke 的是同一套装配函数编译出的「前置子图」**（`build_pre_generation_graph`，
> 只比完整图少一个 `generate_answer`，证据出口改为通向 `END`），因此**不是**
> 另一套手工复刻的链路——历史上一度是，那正是 §4.2 技术债里记过的那笔。

### 2.4 LangGraph 9 节点工作流（五 Agent 协作）

定义在 `app/graph/workflow_graph.py`，节点实现全在 `app/graph/nodes.py`，
分发规则在 `app/graph/edges.py`。**权威设计文档见
[`docs/multi-agent-architecture.md`](multi-agent-architecture.md)**，本节只给速览。

```
                        ┌──────────────┐
                        │ memory_load  │ ⓪ 请求初始化：记忆加载 + 上下文准备
                        └──────┬───────┘
                               ▼
                        ┌──────────────┐
                        │    router    │ ① 路由 Agent：一次模型调用判场景
                        │  唯一入口     │    越界在此拦下（边界规则只有一份）
                        └──────┬───────┘
                 ┌─────────────┴─────────────┐
                 │  scene_route_edge（五路互斥）│
   ┌─────────┬───────┴──┬──────────┬─────────┬──────────┐
   ▼         ▼          ▼          ▼         ▼
┌────────┐┌─────────┐┌─────────┐┌──────────┐┌────────┐
│smalltalk││out_of_  ││simple_  ││complex_  ││  tool  │
│  ② 闲聊 ││scope ③  ││rag ④    ││rag ⑤     ││  ⑥ 工具│
│模板直出 ││常量话术 ││单次检索 ││拆解+多检索││FC 调用 │
└───┬────┘└────┬────┘└────┬────┘└─────┬────┘└───┬────┘
    │          │          │            │         │
    │          │          └─────┬──────┘    tool_route_edge
    │          │                ▼                │（四路）
    │          │        ┌──────────────┐   ┌─────┴─────┬──────────┬─────────┐
    │          │        │generate_     │   ▼           ▼          ▼         ▼
    │          │        │answer ⑦      │ 反问用户  决策失败   不支持FC  有证据
    │          │        │受控生成      │  → END   → ⑧人工兜底 →simple_rag →生成
    │          │        └──────┬───────┘
    │          │     answer_route_edge
    └──────────┴───────┬───────┴──────►【END】
                       ▼
                ┌─────────────┐
                │human_fallback│ ⑧ 人工兜底（阻断幻觉）
                └──────┬──────┘
                       └────────────►【END】
```

**四个条件分支**：`scene_route_edge`（路由五路）、`tool_route_edge`（工具四去向）、
`answer_route_edge`（生成出口）、以及直答出口直达 `END`。

**三个「看似可省但不能省」的位置约定（改动前必读）**：

1. **降级决策必须落在「边」上，不能藏进节点**——`tool_node` 只负责写
   `tool_degraded=True`，改道哪个分支由 `tool_route_edge` 决定。
   拓扑完整地留在拓扑里，读图的人才能看见它每天都在生效。
2. **闲聊与越界必须直达 `END`**——两者都不该走检索（只会命中垃圾片段），
   也不该走生成（无文档会触发「知识库中没有找到…」的拒答文案，
   把「你好」答成「我不知道」）。它们的答案由**模板/常量**直接给出。
3. **边界判定只写在路由 Agent 一处**——子 Agent 不重复写越界逻辑。
   改一处即全局生效，也才能用一条测试钉住「它只有一份」。

**实现原理（小白版）**：

- **lifespan** 是 FastAPI 的"开机自检"钩子。它做三件事：① 先把 Redis 连接预热
  （否则自检会误判成降级模式）；② 用一个**线程池**去跑 `run_self_check`
  （因为自检里有同步阻塞操作，直接跑会卡住整个异步事件循环）；
  ③ 做安全体检——比如"开了鉴权却没配密钥"直接报 error，因为
  **"开着鉴权但谁都能过"比不开更危险**，管理员会以为已经防护好了。

- **中间件** 是"所有请求的必经之路"。这里只有一条，顺序是
  **先注入 trace_id → 再鉴权 → 最后限流**。为什么鉴权在限流前？
  未授权的请求不该消耗下游资源（包括限流计数）。

- **全局异常处理器** 只返回一句通用文案 + trace_id。
  为什么不回显异常原文？因为它可能含文件路径、内网地址、依赖版本等内部信息。
  返回 trace_id 既不让用户看到内部细节，又能让运维在 `logs/trace.jsonl` 里精确定位。

**设计取舍**：
`AUTH_EXEMPT_PATHS` 里的 Dify 接口有自己的 Key 校验，所以两条鉴权链**不能互相替代**。
CORS 如果配了 `*` 又要带凭据，浏览器会直接拒绝——典型的"本地能跑、上线跨域全挂"，代码里已自动关闭凭据。

**实现原理（小白版）**：

配置用的是最简单粗暴也最可靠的方案——**模块级常量**。
`import config` 的那一刻，`os.getenv` 把所有环境变量读进来存成常量，
之后整个程序读的都是内存里的值，零 IO、跨模块绝对一致。

代价是：**改 `.env` 必须重启服务**。代码里注释反复强调这一点，
因为"改了配置没重启"是最常见的排查陷阱。

三个解析辅助函数解决三个具体麻烦：
- `_env`：`KEY=`（等号后是空）时不会让 `int('')` 崩掉，统一回落默认值。
- `_env_bool`：统一认定 `0/false/no/off` 是假，避免每个模块各写一套判断。
- `_env_list`：逗号切分并丢弃空项。

`effective_score_threshold`（`config.py:265-275`）是个有意思的设计：
检索阈值**按 embedding 模式自适应**。为什么？因为不同向量模型的分数尺度天差地别——
OpenAI 的常落在 0.3~0.9，bge-m3 常落在 0.05~0.15。
如果套一个固定阈值，换个模型检索就全空了。
所以：本地哈希向量给 0.08，真实神经向量返回 `None`（只排序、不做绝对过滤）。

`dump_config` 会输出可安全打印的配置快照，密钥一律过 `mask_secret` 脱敏。
`/health` 接口返回的就是它——这样你能随时确认"服务实际加载的配置到底是什么"。

**设计取舍**：
`SCORE_THRESHOLD` 用 `Optional`，`None` 有「未配置」的语义，**不能用 0 代替**——
留空表示"按 embedding 模式自动选"，写 0 则表示"任何分数都不够"，两者天差地别。
历史坑：有一批融合权重只在消费方用 `getattr(config, X, 默认值)` 读取，config 里根本没定义，
导致改 `.env` 完全无效——现已在 `config.py:279-299` 补齐为真实配置。

**实现原理（小白版）**：

- **非流式 `/chat/ask`**：一问一答，等全部生成完再一次性返回。
  内部把整个 LangGraph 工作流丢进线程池跑（`asyncio.to_thread`），
  避免阻塞事件循环。返回体里带来源片段、引用、置信度、`finish_reason`、完整 span 树。

- **流式 `/chat/ask/stream`**：用 SSE（Server-Sent Events）逐字推送，
  用户能看到字一个个蹦出来，体验好得多。响应头加 `X-Accel-Buffering: no` 是
  防止 Nginx 之类的反向代理把内容缓冲住、导致"流式"变成"等半天然后一次性出现"。

- **`collect_soft_warnings`**：把"不影响本轮能否作答"的小故障
  （比如检索时某一路召回失败）收集起来，落日志并对前端只暴露**数量**。
  为什么不暴露原文？因为可能含内网地址和文件路径。

**⚠️ 已知技术债（重要）**：
流式接口**没有复用编译好的工作流图**，而是在 `event_stream` 里手写了一遍节点调用顺序。
这意味着图拓扑一改，两处都得改。历史上就漏过 `error_route_edge`（人工兜底）和寒暄直出，
导致同一个问题在流式和非流式下答案不一致。
而且**级联兜底在流式下不可用**（token 已经推给用户了，没法整段替换），
只能在 `route_decision` 里记一个 `skipped: streaming`。

**设计取舍**：
`soft_warnings` 必须与 `need_human` 严格分开。前者只观测、绝不参与路由；
后者是致命错误、决定是否转人工。曾经把可降级的检索抖动写进 `error_msg`，
结果在答案生成之后触发转人工，把好答案覆盖掉了。

**Dify 接入的坑（小白版）**：

**实现原理（小白版）**：
LangGraph 的状态就是一个**在节点之间传递的大字典**。
每个节点收到 state，返回一个"只包含改动字段"的字典，LangGraph 自动合并（后写覆盖）。

所以新增可观测字段必须**同时**改 `GraphState`（10-63）和 `create_initial_state`（66-98），

**为什么异常要分两条通道**：
`error_msg`/`need_human` 参与路由（决定要不要转人工），
`soft_warnings` 只做观测（记录但不影响流程）。

#### 📍 `app/core/router_agent.py`（1-323）—— 路由 Agent（入口 + 边界管控 + 常量门面）

| 组件 | 行号 | 说明 |
|---|---|---|
| `RouteDecision` | 122-150 | 判定结果：场景 + 理由 + 来源 + 越界话术 |
| `route_query` | 153-215 | 主入口：组装提示词 → 调模型 → 解析 |
| `_parse_route` | 225-252 | 从模型输出里抠出场景名，不在闭集内即拒绝 |
| `_fallback_route` | 285-317 | 模型不可用时的**确定性规则兜底** |

**Phase 0 起它多了一个身份：常量门面。** 通道闭集与越界话术
（`SCENE_*` / `SCENES` / `DEFAULT_SCENE` / `OUT_OF_SCOPE_ANSWER`）
**不再在这里定义**，改由 `app/core/routing/catalog.py` 定义、此处 `from ... import` 转出。
`app/graph/edges.py`、`nodes.py` 与既有测试仍从本模块取这些名字——**一个 import 都没动**。

为什么要绕这一下：改动前"通道闭集"事实上存在于两处（路由包一份、本模块一份），
谁先改谁就制造**静默不一致**，而越界话术若出现第二份定义就不再可审计。
现在定义只有一份，门面只负责转出；并有两条测试从两个角度钉住它——
一条按**首句文本**扫源码确认话术只有一个产生点（`test_out_of_scope_answer_is_defined_once`），
一条用 `is`（**同一性，不是相等**）确认转出的就是同一个对象。
同值两份之所以不能接受，正因为它会静默漂移：`==` 全绿，而事实已经错了。

**为什么边界管控放在入口**：越界问题在消耗检索 / 工具 / 生成预算**之前**就被拦下，
而且整句锚定的正则只有一份。子 Agent 不重复写越界逻辑，
所以「边界规则只有一份」这件事可以用一条测试钉住（扫提示词注册表找唯一 owner）。

**为什么越界回复是常量**：只被**判别**、不被**生成**的回答不可能有幻觉，
而且每次一字不差、可审计。同理，闲聊回复也是模板，不走模型。

**为什么 `DEFAULT_SCENE` 不许是 `tool` / `out_of_scope`**：路由失败时宁可走检索
（最坏是"没找到"，语义上诚实），也不能把用户问题判成越界（等于无理由拒绝服务），
更不能猜成工具（会去动业务数据）。

#### 📍 `app/core/routing/`（1-1809）—— 混合意图路由（四层漏斗）

七个文件，一条漏斗。**每个文件只回答一个问题**——这是它与被删掉的八模块规则路由
最本质的差别（那套的失效方式是"改 A 坏 B"，复盘见 `docs/history/intent-routing-redesign.md`）。

| 文件 | 行号范围 | 只回答一个问题 |
|---|---|---|
| `app/core/routing/catalog.py` | **1-423** | "有哪些意图？" —— 唯一的定义处（意图即数据） |
| `app/core/routing/signals.py` | **1-245** | "这句话是哪种句式？" —— 正则判据与三态抽取 |
| `app/core/routing/anchors.py` | **1-275** | "能不能整句锚定？" —— 层①，零成本 |
| `app/core/routing/fusion.py` | **1-423** | "各候选各得几分、怎么融合？" —— 层② |
| `app/core/routing/gating.py` | **1-115** | "分数够格吗？和次优通道拉开了吗？" —— 层③ |
| `app/core/routing/arbitration.py` | **1-143** | "实在拿不准时问模型" —— 层④，唯一花钱处 |
| `app/core/routing/router.py` | **1-369** | "按顺序串起来，并守住时间预算" —— 编排 |

**四层漏斗，命中即短路**（写的是设计意图，**不是"已经接管生产"**）：

```
① 锚定（0 成本）       整句正则：寒暄 / 身份 / 越狱 / 员工属性句式
②a 词面打分（0 成本）  Σ len(命中关键词)，专名与字段名优先
②b 语义打分（有条件）  词面判不了才升级 —— 见下方"惰性升级"
③ 门控（0 成本）       地板（绝对证据够不够）+ 边际（与次优通道拉开没）
④ 灰区仲裁（一次 LLM）  只有灰区才发生；失败或超时则保守兜底
```

**惰性升级：把"省 LLM 调用"做彻底。** 最初的草案是"第 2 关无条件算一次 embedding"。
那等于**把省下的 LLM 调用换成了一次网络往返**——目标没达成，只是把账单从
一个口袋挪到另一个口袋。现在改成：词面分足够好就直接出结论、**根本不碰 embedding**；
词面判不了才升级到语义；语义也判不了才进灰区问模型。
有一条测试直接断言这条性质：`test_lexical_decisive_never_touches_embedding`
断言 embedding 调用次数恰好是 `(0, 0)`——**"不会发生"要能被证伪，才算设计约束。**

**时间预算是"不许开始"，不是"超时重试"。** 每一步动手之前先算
`剩余 = 截止时刻 - 现在`，不够就**不启动**这一步；启动仲裁时还要把等待上限再收窄为
`min(自身上限, 剩余)`。于是总耗时有证明：**≤ `ROUTE_BUDGET_MS`**。
少写这一步的后果很具体：首版没把剩余预算传下去，冷启动实测出现过 3.2 秒——
"预算"退化成了一个没有约束力的注释。

**门控为什么不能用 RRF 融合分。** RRF 分只由**排名**决定，rank1 与 rank2 的差
恒为 ~1.6%，与"领先一大截"还是"咬得很紧"毫无关系，拿它比阈值结果非黑即白。
所以边界划得很清楚：**融合分只用来排序与展示，门控一律用同层同量纲的绝对差。**
这条是踩出来的——门控一度按融合分排序，于是"融合分第一名在绝对证据上其实输给第二名"，
gap 为负、边际永远不通过，本该直接判对的请求白花一次 LLM 调用。

**门控做在"通道"层级而不是"能力"层级。** `employee_attr` 与 `leave_balance`
同属 `tool` 通道，它俩打平对用户毫无影响，不值得为它多花一次调用；
而 `simple_rag` 与 `complex_rag` 跨通道打平，确实该进灰区。
**同一个数字在不同层级上的含义是不同的**——这是"边际"这个概念最容易做错的地方。

> ⚠️ **Phase 0 的边界**：以上全部只被 `POST /routing/intent-preview` 触发，
> 生产入口仍是 `router_agent.route_query` 的一次模型调用。
> 这样安排是为了**先把判定依据看清楚，再动生产链路**。

| `_decide` | 561-662 | 每轮的判断：继续调工具 / 直答 / 收口 |

**⚠️ 直答出口的判据是 `not used_tools`（一次都没**成功**取到证据），不是 `attempted`（提过调用）**

这条差别对应一条真实链路：

```
用户：「我的年假还剩几天」→ 模型硬填了一个用户没说过的姓名 → 落地校验拒绝
      → 模型改口：「请问你叫什么名字？或者直接告诉我工号」
```

按 `attempted` 判断，这句追问会被**丢掉**，本轮退化成「零证据 → L4 拒答」，
用户看到「知识库中没有找到相关信息」——而他实际只缺一个称呼。

**服务端没有登录态，工号只能来自用户原话或工具返回值**：`employee_id` 出现在
schema 里（模型要填），但它**不是**授权事实——没有身份可对账。护栏因而落在
**姓名**上（`GROUNDED_ARGS` 只登记 `find_employee_by_name.name`）：正常路径下
工号要先经该工具换取，而这个参数必须能在用户原话里定位。

这条设计是刻意的取舍：**没有身份就不假装有身份**。遇到「**我的**年假」这类问法，
模型的正确行为是向用户索要姓名或工号，而不是猜一个工号去查库。要恢复"直接查我"，
正确做法是接真实 SSO 并把工号作为服务端事实注入，而不是让模型去猜。

#### 📍 `app/core/request_ctx.py`（1-213）—— 请求级上下文

三类数据：**query 向量**（139-146）、**来源白名单**（152-159）、**本轮证据**（178-214）。
共同点是「当前请求的事实，不该出现在函数签名里」。

**⚠️ 本模块唯一反直觉、且踩过一次坑的地方**：`ContextVar.set()` 在工具内部是**无效**的。
LangChain 的 `Runnable.invoke` 会执行 `contextvars.copy_context()`，再在那个**副本**里
调用工具函数——在工具内 `set` 的值，调用方读不到。

症状极其隐蔽：`search_knowledge` 明明检索到 5 条片段，`agent_node` 里
`get_retrieved_docs()` 却是空的 → 生成层拿不到证据 → 置信度 0 触发拒答，
用户看到「知识库中没有找到」。**而工具日志显示检索成功。**

修法是把「可变对象」放进 ContextVar：`copy_context()` 复制的是**映射**，
值仍是同一个对象引用，因此对对象内部状态的修改两边都可见。

#### 📍 `app/core/tracing.py`（1-161）—— 全链路追踪

| 组件 | 行号 | 说明 |
|---|---|---|
| `SpanNode` | 38-58 | span 节点 |
| `span` | 83-106 | **contextmanager**：进入/退出自动记录 |
| `begin_trace` | 112-123 | 开启一次请求的根 span |
| `end_trace` | 126-139 | 结束并持久化整棵 span 树 |
| `_persist` | 142-161 | 落盘 `logs/trace.jsonl` |

**实现原理（小白版）**：
用 `with span("xxx"):` 包住一段代码，进入时记开始时间并把新节点**压栈**，
退出时（`finally`）弹栈并回填耗时。
**父子关系不用手动指定**——栈顶就是父节点，于是嵌套的 `with` 自动长出树形结构。

`trace_id` 和 span 栈都存在 **`contextvars`** 里。为什么不用全局变量或层层传参？
因为 `contextvars` 能跨 FastAPI 的事件循环和线程池**自动透传**，
不用在每个函数签名里加一个 `trace_id` 参数。

**⚠️ 关键约束**：`begin_trace` / `end_trace` **必须在执行工作流的同一个线程里调用**——
`contextvars` 是按"上下文"隔离的，跨线程读不到对方 set 的值。

**设计取舍**：落盘失败静默吞掉。可观测性永远不能反过来影响主流程。
耗时用 `perf_counter`（单调时钟），不受系统时间调整影响。

### 4.5 RAG 五层 `app/rag/`

#### 📍 L1 `prepare.py`（1-200）—— 数据准备

| 组件 | 行号 |
|---|---|
| `normalize_text` | 49-64 |
| `content_fingerprint` | 67-69 |
| `jaccard_similarity` | 77-82 |
| `is_near_duplicate` | 85-87 |
| `enrich_metadata` | 101-115 |
| `prepare_documents` | 121-173 |
| `quality_report` | 188-200 |

**流水线**：归一化 → 清洗 → 长度校验 → 精确去重 → 近重复去重 → 元数据注入。

**实现原理（小白版）**：
- **归一化必须先做 NFKC 全角转半角**。否则全角空格会逃过后续的空白压缩，
  导致同一份内容被指纹判成两篇不同文档。
- **精确去重**用 sha1 内容指纹，哈希表 O(1) 查找。
- **近重复检测**用**字符级 Jaccard 相似度**：把两段文字的字符各自做成集合，
  算交集除以并集，≥0.95 判重。
  为什么不用向量相似度？因为这一步**还没有 embedding**，
  而且 Jaccard 对空格、换行这类排版差异天然不敏感。

**设计取舍**：近重复是 O(n²) 两两比对，只在批次内做。
文档涨到万级要换 MinHash 分桶。页码、分隔线这类噪声必须在入口剔掉，
否则会被后续切片放大成大量低信息向量。

**实现原理（小白版）**：
这是"结构感知切分"的**识别**那一半。文档里的标题其实是有层级的：

- **L1 章**：`第三章 假期管理`、`一、总则`
- **L2 节**：`3.2 年休假`、`Q8：...`、`## 6 报销`
- **L3 条**：`1、`、`（1）`

逐行扫描，碰到标题就**压栈**。压栈前先把所有层级 ≥ 当前的新节点弹出，
剩下的栈顶就是父节点。于是"面包屑"路径自然拼出来：
`第三章 假期管理 > 3.2 年休假`。

所有正则都**行首锚定**（`^` + MULTILINE）——宁可漏判不可误判，
否则正文里一句"第三章所述情形…"会被当成标题。

**设计取舍**：纯正则、与模型无关，新增文档格式只改配置不改代码。
**永远不抛异常**——任何意外都降级为 `structure="flat"`，
由调用方回退到递归切分。

**实现原理（小白版）—— 结构感知切分的"合并"那一半**：

光有章节还不够，因为很多小节只有一两句话，切出来全是碎片。
所以拿到小节块流后做**缓冲合并**：
维护一个缓冲区，相邻小节往里拼，一旦超过目标长度就吐出去另起一块
（"小块攒够长度再成块"）。

三条硬规则：
1. **跨章必切**——章节号一变立刻吐出。防止两章内容混进同一个向量（章级串味）。
2. **单块超硬上限**——直接用递归切分器拆碎。
3. **重叠固定为 0**——章节边界天然隔离语义，不需要靠重叠兜底。

另外还有 `_merge_short_chunks`（81-120）治碎片：
像"3. 考勤"这种只有标题没正文的块，向量化后是纯噪声、还会挤占 Top-K。
规则是短于 40 字就"向前收养"拼进上一块。

**为什么要"父子块"（small-to-big）**：
子块（约 300 字）粒度细、匹配准，适合用来**检索**；
但喂给大模型的上下文太短，信息不完整。
所以额外维护一份"父块"（整个小节，约 550 字）。
检索命中的是子块，喂给模型的是父块。

**实现方式有讲究**：不用"父块也向量化"的双索引方案
（向量数量翻倍、embedding 成本翻倍，而且父块粒度粗、检索反而不准），
而是**旁路存储**：只让子块进向量库，父块存在 `parent_store.py` 的 JSON 里，
命中子块后拿 `parent_id` 直接查表把完整上下文捞回来。**向量零增长、成本零增长**。

**`_chunk_id` 为什么用内容哈希而不是位置序号**：
位置型 ID 在前面插一段后全体会偏移，导致"伪增量"——
明明内容没变，ID 却变了，于是重建。
内容哈希让未变片段的 ID 保持稳定。

**设计取舍**：`refit_idf` 显式区分全量/增量——
全量建索引才重训 IDF，增量入库沿用旧 IDF，否则历史向量会失去可比性。
`attach_parents` 必须在**向量化之前**调用，否则 `parent_id` 进不了向量库，检索时无从回捞。

#### 📍 L3 `lexical.py`（1-266）—— 自研 BM25 倒排索引

| 组件 | 行号 | 说明 |
|---|---|---|

| `_tokenize` | 53-71 | 分词：单字 + 相邻二元组 |
| `LexicalIndex` | 90-249 | 索引主体 |
| ├ `add` | 139-150 |

| ├ `_recompute_avg_len` | 180-189 | 缓存平均长度 |
| ├ `_bm25` | 197-213 | **BM25 打分** |
| └ `search` | 215-240 | 检索 |

**实现原理（小白版）**：

先讲**倒排索引**。正常思路是"文档 → 里面有哪些词"，
倒排反过来："词 → 哪些文档里有它"。这样查"年假"时，
直接查表拿到所有含"年假"的文档，不用把每个文档都翻一遍。
复杂度从 O(全部文档) 降到 O(命中的文档数)。

**中文没有空格怎么分词**？这里取"单字 + 相邻二元组"：
"年假申请"会切成 `年`、`假`、`申`、`请`、`年假`、`假申`、`申请`。
单字保证"年假"能命中"年休假"（跨字组合覆盖不到），
二元组让连写的"年假"拿到更高权重。高频虚词（的/了/是/有多少）在建表时就剔除。

**BM25 是什么**？它是词面检索的行业标准打分公式，相比早期的 TF-IDF 多了两个调节项：

```
score = Σ  IDF(qi) × [ tf × (k1+1) ] / [ tf + k1 × (1 - b + b × dl/avgdl) ]

IDF = log(1 + (N - df + 0.5) / (df + 0.5))
```

- **IDF（逆文档频率）**：`N` 是文档总数，`df` 是含这个词的文档数。
  出现在越多文档里的词越不值钱。不加权的话，"的/员工/系统"这类高频词
  会淹没"年假/VPN/报销"这些真正有区分度的词。
- **`k1 = 1.5` 控制词频饱和**：一个词出现 10 次，并不代表相关性是出现 1 次的 10 倍，
  所以让 tf 的贡献逐渐饱和。
- **`b = 0.75` 做长度归一化**：避免长片段仅因为字数多就占便宜。

**为什么比纯向量检索强**？向量擅长"语义相近"（"怎么请假"能命中"休假申请流程"），
但对**专有名词和精确字符**不敏感。BM25 恰好补这一块——
用户问"年假"，就必须命中写着"年休假"的那一节。

**设计取舍**：`avg_len` 曾经用 `@property` 每次打分都重算全量平均，
整体退化成 O(N²)。现在改成增删时缓存、打分时 O(1) 读取。

**实现原理（小白版）—— 混合召回**：

三路并行跑（用线程池）：
- **dense 路**：把问题转成向量，去向量库找最像的片段。擅长语义改写。
- **lexical 路**：查上面的 BM25 倒排索引。擅长专有名词、制度条款的精确字符。
- **rewrite 路**：把问题改写成几种说法再召回，默认关闭。

两路的**互补性是融合有效的前提**，缺一路就退化成单模态。

**RRF 是什么？为什么不用加权求和？**

融合公式很简单：

```
RRF_score(文档) = Σ  权重 / (k + 该文档在这路的排名)      k = 60
```

比如某文档在向量路排第 1、词面路排第 3，它的分数就是
`0.7/(60+1) + 0.3/(60+3)`。

**为什么不用加权求和**？因为两路的分数**根本不在同一量纲**：
向量余弦相似度随供应商剧烈漂移（bge-m3 常落 0.05~0.15，OpenAI 常落 0.3~0.9），
BM25 分则是没有上界的正数。加权求和前必须先归一化，
而归一化参数会随语料变化漂移，极不稳定。

RRF **只看排名，完全不看分数绝对值**——所以对量纲免疫、
跨数据集稳健，这也是 Elasticsearch / OpenSearch 的默认做法。

**词面分还有三层小设计**（`lexical_score` 68-90）：
① 过滤虚词（否则"有/多/少"让所有片段一起冲到满分，排序失效）；
② 用**查询覆盖度** `|查询词∩文档词| / |查询词|` 而不是匹配个数，避免长查询占便宜；
③ 连续子串精确命中额外 +0.3（"年假"应严格优于只字符重合的"年休假"）。

**查询向量复用**：query 向量在 `retrieve` 主线程算一次，
存进 `request_ctx`，之后"检索"和"动态路由打分"两处直接复用，
省掉一次约 400ms 的 embedding 网络往返。
能成立的前提是 `ThreadPoolExecutor.submit` 会**复制提交线程的上下文**，
所以子线程能读到主线程 set 的值（反过来不行）。

**父块回捞**（`_attach_parent_content` 221-243）只**新增** `parent_content` 字段，
绝不动 `content` / `score` / `fused`。所以这个开关对检索指标**零影响**，
只影响喂给模型的上下文完整度——是"能安全开关的增强"的范本。

**设计取舍**：阈值过滤用 `fused` 而不是向量 `score`
（词面路独立后，词面高分片段会被向量分误杀）。
软回退时必须写**真实的 fused 分**，写 0 会让归一化置信度恒为 0。

**"迷失在中间"是什么**：研究发现模型对长上下文的**开头和结尾**注意力明显高于中部。
而检索结果本来就是按相关性降序排的，最相关的在开头——这没问题，

这是**性价比最高的 RAG 优化**：纯函数、零模型调用、零延迟。
放在 `build_context` 而不是 `retrieve`，是为了不污染供评测和前端展示的客观分数顺序。

**三个控制点**：

1. **引用编号**：拼上下文时给每段加 `[1][2][3]` 前缀，并要求模型标注依据。
   没有编号制度，多份文档的信息会混在一起说，出了错无法定位。

2. **幻觉抑制**：提示词明确"只用参考内容，不足则直说没有"。
   这是成本最低的手段，比事后校验划算得多。

3. **优雅拒答**：置信度低于 `REFUSE_THRESHOLD`（默认 0.25）且没有工具结果时，
   直接回"知识库中没有找到"，宁可转人工也不硬凑。

**置信度怎么算**（`estimate_confidence` 142-164）：
拿 Top1 的 RRF 融合分，除以**理论上限** `(稠密权重 + 词面权重) / (RRF_K + 1)`。
为什么这么算？因为 RRF 分只取决于排名，上限是个常数，
所以这个比值**跨 embedding 模型可比**——而原始向量分做不到（不同模型尺度不同）。

再叠加三档修正：
- 软回退片段 ×0.6（证据本身就弱）
- 词面分 ≥ 0.5 加 0.1（检索确实对上了）
- 有工具结果加 0.2（确定性业务数据）

**流式统计为什么要拆 `ttft_ms`**（45-79）：
总耗时拆成"首 token 延迟"和"后续逐块产出"，因为**两者慢的根因完全不同**——
前者是网络或供应商排队，后者是模型吐字速度或输出过长。
不拆开就只能笼统地说"慢"，无法归因。

**截断检测**（285-305）：读每帧的 `finish_reason`，
如果是 `length` 就说明撞上了 `max_tokens` 上限，打 WARNING 并挂到 span 和响应体上。
这个字段是后加的——**在此之前截断完全静默**，
被截断的 900 字和正常写完的 900 字在日志里长得一模一样，
用户报"回答不完整"时根本查不出来。

**"空响应"要分两类**（313-320）：
- 空内容 + **有**终止帧 = 推理模型把预算全烧在思考上 → **不回退**（回退只是再烧一次，实测把 28s 拉成 57.7s）
- 空内容 + **无**终止帧 = 真的断流 → **仍回退**重试

**设计取舍**：`chat_history` 必须是调用方**已经裁剪好**的窗口，
这一层只格式化不裁剪。两处都裁剪会让 `SHORT_TERM_WINDOW` 配置静默失效。

**两个检索指标**：

  命中用例数 / 总用例数。衡量"召回下限"。
- **`MRR`（平均倒数排名）**：首个命中的片段排第几名，取倒数。

**忠实度 `score_faithfulness` 怎么算**（233-246）：
把答案切成相邻两字一组（bigram），看有多少组在参考内容里出现过。

**⚠️ 重要陷阱**：它是**精确率**——分母是**答案**的 bigram 数，不是参考内容的。
所以**答案越长、越补充解释，分数反而越低**（因为会出现更多参考内容里没有的二字组合）。
实测 6 个样本里，答案字数与忠实度的 **Spearman 相关系数 = -0.94**，
这个指标相当程度上在测"简洁度"而不是"有没有依据"。

**用它的正确姿势**：它是零成本的幻觉粗筛，只适合看"有没有大面积编造"，
**不能当精细质量分**，更不能拿它直接判"质量退化"——做 A/B 对比时必须先做长度控制。

**设计取舍**：评测用例外置成 YAML（原先硬编码 4 条在源码里），业务方可直接扩覆盖。
但字段缺失会**主动抛 `EvalCaseInvalid`**——配置错误要显式暴露，不能静默降级。

**三个关键设计**：

1. **不自己重试，把失败交给上层降级**（`_build_raw_model` 193-221 显式写 `max_retries=0`）。
   自研的限流退避包装器 `_RateLimitRetryModel` 已随重构删除——它是为"免费档
   RPM=3"写的，改用不限流模型后前提不复存在。SDK 默认会对超时/连接错误静默
   重试 2 次，实测会把 `LLM_TIMEOUT=30` 放大到 **101 秒**，用户看到的就是
   "一直加载"。**重试策略只能有一层，而现在那一层是"不重试"。**
   快速失败之后：检索失败就诚实回答（记 `soft_warnings`），生成失败转人工。

2. **限流判定保留下来，但只用于分类，不驱动任何重试**（`_is_rate_limit` 170-190）。
   为什么留着？启动自检要区分「限流导致的失败」与「真正的配置错误」——
   前者标 skip，后者必须暴露。

3. **限流判定用三层精确匹配**（`_is_rate_limit` 170-190）：
   先看 `status_code == 429`，再看异常类名是否含 `RateLimit`，
   最后才用正则匹配"错误码语境下的 429"。
   **禁止用 `"429" in str(exc)` 这种裸子串**——request id 或内容哈希里
   碰巧出现 429 就会被误判成限流，把一个不可恢复的错误拖进退避白等。

**推理模型的思考开关**：
`thinking` 这个字段不在 OpenAI 标准协议里，用 `extra_body={"thinking": {"type": "disabled"}}` 透传，
由 `LLM_DISABLE_THINKING` 配置控制。
**为什么不按模型名判断**？因为模型名是部署方随手填的字符串，写死必然漏。
这属于参数配置问题，应由配置控制、由报错暴露。

**流式四级策略**（`_stream` 232-271）：
正常逐块透传 → 未产出内容前失败可回退整段生成 → 超时不回退 → 已产出部分再失败直接抛（避免内容重复）。

#### 📍 `app/providers/embeddings.py`（1-278）—— 向量化

| 组件 | 行号 | 说明 |
|---|---|---|
| `LocalHashEmbeddings` | 48-133 | **本地哈希向量**（无 Key 也能跑） |
| ├ `fit` / `_load_idf` | 98-107 / 72-81 | IDF 训练与加载 |
| └ `_embed` | 113-127 | 核心向量化 |
| `APIEmbeddings` | 136-175 | 远程 API |
| `CachedAPIEmbeddings` | 178-224 | 带缓存的代理 |
| `get_embeddings` | 230-259 | 工厂（自动降级） |

**LocalHashEmbeddings 的原理（小白版）**：

没有外部 API 时怎么造出"可用"的向量？三步：

1. **词袋（bag-of-words）**：把文本看成词的集合，忽略语序。
   分词规则是中文取"单字 + 相邻二元组"、英文数字按词。
2. **Hashing Trick（哈希技巧）**：正常做法要给每个词分配一个编号（建词表），
   但词表占内存、而且遇到新词就没编号。
   这里直接用 `md5(词)` 取模落到 512 维中的某一维——**不建词表**，
   省内存、天然支持没见过的词。代价是不同词可能撞到同一维。
   为此用哈希的第 5 个字节决定这次贡献的**正负号**（signed hashing），
   让碰撞的部分相互抵消；再加一个 salt 做第二组哈希进一步压碰撞。
3. **IDF 加权**：权重 = `(1 + log(词频)) × IDF`，最后做 L2 归一化。

**IDF 是什么**：`log((总文档数+1)/(含该词的文档数+1)) + 1`。
含义是"越少文档出现的词越有区分度"。
不做加权的话，"的/员工/系统"这类到处都有的词会淹没"年假/VPN/报销"。
IDF 表在全量建索引时训练一次并持久化，查询时复用同一套权重。

**能力边界（诚实说明）**：本地哈希的语义泛化能力明显弱于神经向量，
只够支撑"字面/近义短语重叠"型的企业制度检索。
它的价值是**保证无 Key 时全链路能跑通**（CI、离线演示）。

**切换机制**（`get_embeddings` 230-259）：
先尝试真实接口并做一次健康检查，失败就自动落到本地哈希并打印 `mode=local-hash`。
注意 `get_embedding_mode()` 返回的是**实际初始化成功**的模式，不是配置值——
这样运维能一眼看出当前真正在用哪个。

#### 📍 `app/providers/rerank.py`（1-102）—— 精排

cross-encoder 是"把问题和文档**放在一起**过一遍模型"打分，
比双塔式的向量相似度准，但慢得多（每对都要跑一次模型），
所以只对前 N 条候选做，且**默认关闭**。

**三个后端如何切换、以及连不上时会怎样**：

三个类暴露**完全相同的 7 个方法**（`add` / `search` / `delete_by_source` / `count` /
`clear` / `list_sources` / `get_texts`），工厂按 `VECTOR_DB_TYPE` 选一个返回，
上层 RAG 引擎不感知底层差异——换库只改环境变量，不碰业务代码。

接口是**鸭子类型**（没有 ABC/Protocol），漏实现一个方法不会在 import 期报错、
只会在跑到那条路径时才炸，所以用 `tests/test_vector_store_backends.py` 把 7 个方法钉死。

失败行为分三档，这是本模块最容易踩坑的地方：

| 情形 | 行为 | 为什么 |
|---|---|---|
| `VECTOR_DB_TYPE` 写错（如 `mlivus`） | **抛 `ValueError`** | 配置错误是确定性的，越早暴露越好 |
| 配了生产后端但连不上，`VECTOR_DB_STRICT=false`（默认） | 降级为内存库 + 启动日志打 **ERROR** | 保住可用性，且不让「前台慢」和「后端连不上」互相掩盖 |
| 同上，但 `VECTOR_DB_STRICT=true` | **拒绝启动** | 否则数据会悄悄写进本地内存库，而运维以为在用 Milvus |

**为什么 `VECTOR_DB_TYPE` 要归一化 + 校验**：读取时统一 `strip().lower()`，
所以 `.env` 里写 `" Milvus "` 也能识别；非法值直接报错。
不做这两件事时，一个拼写错误会让服务安静地退回内存库——
「配置写错了」和「本来就配的内存库」表现完全一致，排查时没有任何线索。

**为什么要有 `_loopback_proxy_hint`**（338-364）：gRPC 会读取 `http_proxy` /
`https_proxy` 环境变量。公司网络普遍配全局代理，此时连 `localhost` 的 Milvus
会被代理转发并收到 502，而 pymilvus 只报
「illegal connection params or server unavailable」——真正的原因藏在
一行 stderr 里，极易被误判成「Milvus 没启动」。该函数在连接失败时补一条
「把本机地址加进 `NO_PROXY`」的告警，把这条弯路堵掉。

**原子写是怎么做到"写一半断电也不损坏"的**（`_atomic_write` 50-68）：

三步：
1. 把内容写进**同目录**的临时文件 `xx.tmp-<pid>`；
2. 对临时文件 `fsync`——强制把内存缓冲刷到磁盘
   （不做这步，rename 之后内容可能还在内存里，断电照样丢）；
3. `os.replace(tmp, 目标)` 替换。

`os.replace` 在同一文件系统内是**原子操作**：
外部任何时刻看到的，要么是旧的完整版、要么是新的完整版，不存在"半截文件"。
之后再 `fsync` 一下父目录——因为 POSIX 规定 rename 本身也要刷目录项才算真正持久化。

**为什么需要这个**：旧实现把数据文件和元数据文件分两次裸写，
没有 fsync 也没有原子替换，一旦崩在中间就是"两个文件对不上"的死局。

**`_quarantine` 隔离损坏文件**（125-149）：
加载时校验 `文本数 / 元数据数 / ID 数 / 向量行数` 四者长度是否一致，
不一致就判定上次写入被中断，把损坏文件**改名**为 `.corrupt-<时间戳>` 保留下来。
旧行为是直接重置成空库——用户只看到"知识库空了"，
既没有告警，也失去了抢救和排查的机会。

**检索算法**：内存版用 numpy 矩阵做**暴力检索**（向量已经 L2 归一化，点积即余弦相似度）。
取 Top-K 用 `argpartition`（O(N)）而不是 `argsort`（O(N log N)），
但**必须对候选再做一次排序**——因为 RRF 融合依赖排名顺序，
把无序的 partition 结果直接交出去会让排名失真。

**设计取舍**：三个后端对外接口完全一致，上层无感，靠 `VECTOR_DB_TYPE` 一个开关切换。
内存版适合万级片段、Chroma 扛十万级单机、Milvus 扛百万级分布式。
Milvus 后端有两个刻意设计：**集合惰性创建**（维度在首次写入时从向量长度推断，
换 embedding 模型不会踩"维度不符"）、**构造期主动探测连接**
（`MilvusClient` 构造是惰性的，不探测的话"服务没起"要等第一次检索才暴露，
工厂也就无法降级）。后端起不来时**降级而不是启动失败**——
服务照常可用，日志留明确告警，避免前台可用性与后端配置问题互相掩盖。

③ **只读三层强制**——连接层 `mode=ro` + 代码层只有 `SELECT` +

#### 📍 `cache.py`（1-119）—— 缓存

| 组件 | 行号 |
|---|---|
| `_cache_key` | 29-30 |
| `EmbeddingCache` | 33-107 |
| ├ `get_query_vec` | 64-77 |
| ├ `put_query_vec` | 79-85 |
| ├ `get_doc_vec` | 88-92 |
| └ `put_doc_vecs` | 94-107 |

**两层缓存**：
- **查询向量**：内存里做 LRU + TTL。key 带模型名（换 embedding 模型后自动失效）。
  用 dict 的插入顺序天然实现 LRU——命中后先 `pop` 再插回末尾完成续期。
- **文档向量**：按内容哈希存，无 TTL（内容不变则向量永不变），整体 JSON 落盘。

**⚠️ 为什么只提供批量接口 `put_doc_vecs`，刻意不提供单条接口**：
因为落盘是"整个缓存序列化后覆盖写"。
一旦存在单条接口，就一定会有人在循环里调用它，形成 **O(n²) 写放大**。
实测缓存 325 条 / 7MB 时单次写 135ms，
全量重建 176 篇光序列化就要 **23.8 秒**；改成批量后 **0.141 秒（168 倍）**。

**没有单条接口，就没有被逐条调用的机会。** 这是用 API 设计来防止误用的典型例子。

## 五、小白必读：核心概念速通

### 5.1 什么是 RAG

**RAG = Retrieval-Augmented Generation（检索增强生成）**。

大模型的知识来自训练数据，它**不知道你公司的内部规定**。
直接问它"年假多少天"，它会根据网上见过的通用情况编一个答案——这就是"幻觉"。

RAG 的思路很朴素：**先查资料，再回答**。
就像开卷考试，先翻书找到相关段落，再照着回答。

流程是三步：
1. **检索**：把用户问题转成向量，在文档库里找最相关的几段；
2. **增强**：把找到的段落塞进提示词，连同问题一起发给模型；
3. **生成**：模型只依据这几段回答，并标注引用编号。

好处：答案有据可依、可溯源、可以拒答。
坏处：检索错了模型再强也没用——所以**检索质量是 RAG 的上限**。

### 5.2 什么是 Embedding（向量化）

计算机不认识文字，只认识数字。Embedding 就是**把一段文字变成一串数字**（比如 512 个浮点数）。

关键在于：**意思相近的文字，它们的数字串也相近**。
"怎么请假"和"休假申请流程"字面上完全不同，
但转成向量后距离很近，所以能被检索到。

**怎么衡量两个向量"相近"？** 用**余弦相似度**——就是两个向量夹角的余弦值，
范围 -1 到 1，越接近 1 越相似。
如果事先把所有向量都归一化成单位长度（长度=1），那么余弦相似度就等于**点积**，
计算会快很多。本项目在入库前就做了这步归一化。

### 5.3 什么是向量数据库 / 向量检索

存了几万个向量，来了一个查询向量，怎么最快找到最像的？

- **暴力检索**：挨个算一遍相似度，取最高的 K 个。
  简单准确但要全表扫描，适合万级数据。本项目的内存后端用的就是这个，
  并用 `argpartition` 把复杂度从 O(N log N) 降到 O(N)。
- **HNSW 等近似算法**：建一张多层图，像跳表一样快速逼近最近邻。
  快得多，但结果是近似的。Chroma 用的就是这个，适合海量数据。

### 5.4 什么是 BM25 / 倒排索引

纯向量检索有个短板：**对精确字符不敏感**。
用户问"VPN 连不上"，向量可能召回一堆"网络问题"相关的段落，
但真正需要的"VPN 配置"那一段反而排不进去。

所以再配一路**词面检索**：

- **倒排索引**：把"文档→词"反过来存成"词→文档"。
  查一个词时直接拿到含它的所有文档，不用翻遍全部。
- **BM25**：给这些文档打分排序。核心思想是
  "**少见的词更有信息量**"（IDF）、"**同一个词重复出现不会无限加分**"（词频饱和 k1）、
  "**长文档不该因为字多就占便宜**"（长度归一化 b）。

两路结果怎么合并？见下一节。

### 5.5 RRF：为什么用排名融合而不是分数相加

两路召回各给出一份排序名单，怎么合并成一份？

**直觉做法**：把两边分数加权相加。**问题是分数不可比**——
向量相似度可能是 0.78，BM25 可能是 12.4，量纲完全不同。
要相加就得先归一化，而归一化参数会随语料和模型变化漂移。

**RRF 的做法**：干脆**不看分数，只看排名**。

```
得分 = Σ  权重 / (60 + 排名)
```

排第 1 名得 `1/61`，排第 100 名得 `1/160`。
这样不管各路分数是什么量纲，都能直接融合。
60 这个常数让排名差异变得平缓——避免"第 1 名和第 2 名差距被过度放大"。

这就是 Elasticsearch、OpenSearch 等主流系统默认的融合方式。

### 5.6 什么是 LangGraph 工作流

LangGraph 把一次请求拆成若干个**节点**，节点之间用**边**连接成有向图。

- 每个节点是一个普通函数：`state -> state`（收状态，返回改动的字段）
- **条件边**是一个返回字符串的函数，用返回值决定下一步走哪个节点
- 图编译后就变成一个可执行对象，`invoke(state)` 就跑完整个流程

**为什么用图而不是写一个大函数？**
因为可以**把每个环节独立出来**：单独观测耗时、单独降级、单独替换。
比如"检索失败"不该导致整个请求失败，图上可以让它继续走到"生成"环节给一个诚实的回答。

### 5.7 四层意图路由：为什么不全交给大模型

> ⚠️ **本节的前半部分记录的是重构前的机制，已被「路由 Agent」取代。**
> 现在入口只有一次模型调用（`app/core/router_agent.py::route_query`）判定场景，
> 五路互斥；模型不可用时由 `_fallback_route` 兜底为 `simple_rag`。
> 下面这套自造漏斗的代码与测试已移入
> `_archive/removed-selfbuilt-routing-20260915-1314/`，保留本节的目的是
> **记住当初为什么造它、以及它为什么被推翻**（详见 `docs/history/intent-routing-redesign.md`）。
>
> 🔁 **但"四层漏斗"这个思路后来以另一种形态回来了**：`app/core/routing/` 是**新写的一套**
> （见 §4.4），它在 **Phase 0 只服务预演接口 `/routing/intent-preview`，
> 尚未接管生产**。读本节时请分清两件事——
> **第一套失败在"规则互相牵制 + 意图写死在代码里"**，
> 所以第二套的第一条设计原则就是"意图即数据"；本节记下的教训，正是第二套要避开的东西。
> 切换计划见 `docs/intent-routing-hybrid-design.md` §8.1。

用户的问题分成几种**能力**，走不同的通道：

| 能力 | 通道 | 例子 | 走哪条路 |
|---|---|---|---|
| `smalltalk` | smalltalk | "你好" | 模板直出，不检索不调模型 |
| `employee_lookup` | tool | "张三在哪个部门" | 调员工信息工具 |
| `hr_policy` / `finance_policy` / `it_support` / `company_policy` | knowledge | "年假有多少天" | 走 RAG 检索文档 |

**四层漏斗，命中即短路**：

```
① 确定性锚定（免费）  整句锚定的寒暄 / 员工属性句式
② 融合打分（一次 embedding）  词面（关键词，免费）+ 语义（向量，走缓存）
③ 边际门控（纯计算）  第一名够不够格 + 是否与第二名拉开差距
④ 灰区仲裁（一次 LLM，罕见）  候选清单由目录动态渲染；失败则保守兜底
```

为什么不全交给大模型？两个理由：

1. **配额是硬约束**：本项目账号每分钟只能调用 3 次大模型，
   一次分类就要吃掉三分之一配额——用户每问两句就撞限流。
2. **绝大多数输入根本不需要模型**：句式固定的话，规则与关键词又快又准还可复现。

代价与对策：
- 规则「写窄」的代价是漏判 → 交给灰区与兜底，而不是硬猜；
- 关键词覆盖不到的换说法 → 由语义层补，仍然零大模型调用；
- **只有真正拿不准（两个通道咬得很紧）才问模型**，这是唯一会花配额的地方。

关键认识：**「不确定」不该被强行消解成某个标签。**
固定阈值分不清「谁都不像」与「两个都像」，所以要同时看**绝对分**和**第一二名的差距**
（边际）。这也是为什么门控做在**通道**层级——同通道的两个能力打平，
对用户毫无影响，不值得为它多花一次调用。

排查「这句话为什么被路由到这里」：看响应体里的 `scene` / `scene_reason` /
`scene_source` 三个字段（`_meta_common` 统一透出，流式与非流式都有）。
`scene_reason` 是路由 Agent 给出的判定理由，`scene_source` 说明它来自模型还是兜底。

> 旧实现靠 `/routing/intent-preview` 观测候选得分表；该端点随自造路由一并删除。
> **生产链路上**现在确实没有"候选得分"这个概念——只有一个模型调用加一条兜底。
> 不过新漏斗（§4.4）的 `POST /routing/intent-preview` 又把它带回来了，
> 区别在于它这次是**只读预演**：不参与生产判定，专门用来在切换之前
> 把"这句话会被判成什么、凭什么"逐层看清。

### 5.8 全链路降级：任何依赖挂了都能跑

这个项目有个贯穿始终的设计哲学：**每一个外部依赖都自带一条"不可用就降级"的路径**。

| 依赖 | 挂了会怎样 |
|---|---|
| 大模型 API | 降级为本地 Mock 规则模型 |
| Embedding API | 降级为本地哈希向量 |
| Redis | 降级为进程内内存字典 |
| Milvus / Chroma | 降级为内存向量库（`VECTOR_DB_STRICT=true` 时改为**拒绝启动**） |
| 精排模型 | 直接跳过，原样返回 |
| PDF 解析器 | 三级降级：pdfplumber → pypdf → PyPDFLoader |
| OCR | 降级为只记录图片位置 |
| LLM 摘要 | 降级为原文截断快照 |
| LLM 事实抽取 | 降级为正则规则抽取 |
| 路由打分器 | 降级为默认档位 |

结果是：**在完全离线的 CI 环境里，整条"意图识别 → 检索 → 生成"链路依然能跑通。**
生产环境配好 Key 后，业务代码一行都不用改。

代价是：降级本身可能掩盖问题。所以每个降级都通过 `get_*_mode()`
**如实上报当前实际模式**（而不是配置值），运维能一眼看出来。
向量库这一路做得更进一步：`/health` 同时返回 `vector_db`（实际生效）与
`vector_db_requested`（配置要求），两者不一致就是发生了降级；
启动日志会为此单独打一条 ERROR，前端徽章也会把它标成橙色并注明「已降级（配置 xxx）」
（`app/static/index.html` 的 `initBadges` / `renderTest` / 配置卡片三处）。

### 附录 C：行号会漂移，用脚本校验

**代码一改，本文行号就会失效**——而且文档不会报错，只会悄悄变错。
所以配了一个校验脚本，把复核自动化：

```bash
python scripts/verify_doc_linenos.py
```

它对本文的 **478 条行号声明**逐条回验（AST 静态解析，不 import、无副作用），
覆盖十类写法：

| # | 声明类型 | 例子 |
|---|---|---|
| 1 | 符号行号（含类方法 / 嵌套函数 / 模块级常量） | `search` 246-488 |
| 2 | 文件总行数（区间式） | `app/main.py` **1-226** |
| 3 | 文件总行数（附录裸数字式） | `config.py` 639 |
| 4 | 章节 / 全量小计（散文式） | `### 3.2 app/api/ — HTTP 接口层（1,390 行）` |
| 5 | 模块标题里的行号范围 | `#### 📍 app/config.py（1-639）` |
| 6 | 松散单元格里的符号行号 | `prompts.py` 中的 `render` 198-207 |
| 7 | 散文引用（**必须精确命中某个符号**） | `app/core/tracing.py:126-139` |
| 8 | 通用文件行数（含非 Python、无反引号） | `README.md`（495 行）、`app/config.py`（718 行） |
| 9 | 区域行号表（裸区间） | `241-337` 向量数据库配置 |
| 10 | 散文引用精确性（见第 7 类） | `app/core/router_agent.py:153-215` |

全部一致时退出码 0，有不一致时打印具体行号并返回 1——
作为质量门禁之一请在本地执行（原 CI 配置已随开源外壳移除）。

**本文当前状态：478 条声明全部与源码一致**（`scripts/verify_doc_linenos.py` 退出码 0）。
多 Agent 重构删掉了一批模块，本文对应章节已按新架构重写——这类「文件没了」的失效
是校验器唯一无法自动修的，必须人工重写，也正是它最该报出来的。

> **为什么有十类而不是三类？** 因为最初只覆盖了第 1～2 类，于是
> 附录整块（第 3 类）、章节小计（第 4 类）、模块标题（第 5 类）、
> 区域表（第 9 类）全都**静默通过**。校验器只认它「认得出」的写法，
> 认不出的写法不会报错、只会被跳过——所以「全部一致」这个结论，
> 必须先用「覆盖面是否完整」来证伪。这次补齐后，一次性暴露出
> 十余处已经漂移很久的数字（`config.py` 632 行却写着 612、
> 区域表止于 583、`prompts.py::render` 109-118 却写着 103-112 等）。
>
> **第 10 类是最隐蔽的一次教训**：散文引用原先只校验「不越界」，
> 但代码在中间插入几十行后，一个旧范围往往**仍然界内**，于是静默通过、
> 却已指向另一个函数。模型路由重写后，本文 24 条散文引用里有 **9 条**
> 这样悄悄漂移（节点④ 还指向 `model_router.py:526-653`，
> 而主入口 `route_model` 早已移到 `709-848`）。
> **越界是硬错，不精确是静默漂移——后者更常见也更难发现。**

如果只是想重新生成一份结构骨架（用于新增模块时查行号）：

```python
"""生成代码结构骨架：文件 → 行数 → 类/函数定义及行号。"""
import ast, pathlib

for f in sorted(pathlib.Path("app").rglob("*.py")):
    if "__pycache__" in str(f):
        continue
    src = f.read_text(encoding="utf-8")
    tree = ast.parse(src)
    print(f"\n### {f}  ({len(src.splitlines())} 行)")
    def walk(node, depth=0):
        for child in node.body:
            if isinstance(child, (ast.FunctionDef, ast.AsyncFunctionDef, ast.ClassDef)):
                kind = "class" if isinstance(child, ast.ClassDef) else "def"
                print(f"{'  '*depth}{child.lineno:>4}-{child.end_lineno:<4} {kind} {child.name}")
                if isinstance(child, ast.ClassDef):
                    walk(child, depth + 1)
    walk(tree)
```
